# OfferLoop 五项求职训练 Skill 完整方案

> 历史设计稿：其中的旧目录、经历主档和旧题库方案已被 schema v4 取代，不得作为运行期契约。
> 当前唯一有效目录与读写规则见
> `skills/offerloop-workspace/references/artifact-contract.md` 和
> `skills/offerloop-workspace/references/homepage-contract.md`。

## Summary

新增五个正式 OfferLoop Skill：

1. `resume-deepthink`：追问式梳理实习/项目经历，输出简历建议和可用表达。
2. `interview-prep`：结合岗位、JD、投递简历和已有素材生成面试准备文档。
3. `mock-lab`：重新实现 OfferLoop 自有模拟面试，现有 CareerForge 版本仅作设计参考。
4. `talk-review`：根据 ASR/转写稿还原真实问答并生成面试复盘。
5. `pm-sense`：迁入产品思维训练逻辑，移除小红书发布、图片和排版，只输出 Markdown。

结构化面试专项 Skill 不在本期开发；五项 Skill 不实现结构化题库和评分模型，相关字段在真正出现专项需求时再设计。

所有可复用求职素材以飞书知识库为唯一长期存储位置：

- 运行前从飞书知识库读取简历、经历主档、历史训练和准备材料。
- 每次完整运行或用户明确提前结束后，自动创建一份 Markdown 格式的飞书文档。
- 不依赖本地文件、Skill 安装目录或旧聊天上下文保存长期素材。
- 求职记录、JD 和面试事件继续以三个 Base 为业务事实源；简历、素材和报告以知识库文档为内容事实源。

## Shared Artifact Architecture

### 飞书知识库目录

沿用现有一级目录，按需创建二级节点，不按目标岗位提前预留版本：

```text
03｜个人材料
├── 当前简历
├── 历史简历
├── 其他求职材料
└── 个人经历素材主档              # 第一次确认深挖结果时创建

04｜面试准备
├── 待准备
├── 准备完成
└── 通用准备材料

05｜面试复盘
├── 待复盘
└── 已完成复盘

06｜训练与题库
├── 简历深挖
├── 产品思维
│   └── 产品思维素材主档          # 第一次确认产品思维判断时创建
├── 模拟面试
├── 通用面试题
└── 笔试资料
```

初始化只创建或定位通用目录，不询问目标岗位、不创建互联网/央国企简历目录、不创建空白素材主档。文档和版本在第一次实际需要时懒创建。

### 飞书文档写入契约

每个最终产物使用 Markdown 生成，并创建为可在线阅读和编辑的飞书 Docx/Wiki 节点，不额外上传 `.md` 附件。

文档统一包含“产物信息”区：

- 产物类型、状态、生成时间和 `run_id`。
- 来源文档链接及读取时间。
- 关联的投递记录、岗位、JD、面试事件和简历版本；没有则留空。
- 已确认事实、未确认推断和外部证据分别标记。
- 生成 Skill 及其版本。

保存规则：

- 正常完成：保存为 `completed`，归入对应完成/训练目录。
- 用户明确提前结束：保存已有内容为 `incomplete`，归入待准备/待复盘或对应训练目录。
- 普通暂停：不产生正式文档。
- 写入失败：仍在对话中交付完整 Markdown，明确标记“未保存”，保留相同 `run_id` 供重试；不得谎报成功或静默写入本地长期副本。
- 重试时先按包含 `run_id` 的确定性标题精确查找，避免重复创建。

`run_id` 规则：

- 格式为 `<skill_name>-<yyyymmddHHMMSS>-<8位随机小写字母数字>`，例如 `resume-deepthink-20260723143012-a3f7k9mq`。
- 由 `artifact_contract.py` 在 Skill 首次请求创建产物时统一生成，Skill 自身不另行生成。
- 跨 Skill 全局唯一；同一用户在同一会话里连续切换两个 Skill 视为两次运行，得到两个不同的 `run_id`。
- `run_id` 只用于本次产物去重与重试，不跨运行期复用；同一 `run_id` 写入失败后重试仍沿用，成功写入知识库后再次运行生成新 `run_id`。
- 生成后立即在对话状态中保留，并写入最终 Markdown 的“产物信息”区；保存失败时必须在回复中显示该 `run_id`，供后续重试复用。

文档标题必须包含 `run_id`，统一格式如下：

- 简历深挖：`简历深挖｜<经历或简历名称>｜<YYYY-MM-DD>｜<run_id>`
- 面试准备：`<公司>｜<岗位>｜<环节>准备｜<YYYY-MM-DD>｜<run_id>`
- 模拟面试：`<公司或专项名称>｜模拟面试｜<YYYY-MM-DD>｜<run_id>`
- 面试复盘：`<公司>｜<岗位>｜<环节>复盘｜<YYYY-MM-DD>｜<run_id>`
- 产品思维：`产品思维｜<题目短标题>｜<YYYY-MM-DD>｜<run_id>`

### 长期主档与运行产物

采用“双层沉淀”：

- 每次运行都创建独立、不可被后续运行覆盖的会话产物。
- `个人经历素材主档`、`产品思维素材主档`属于长期汇总文档。
- 只有用户明确确认过的事实或答案才允许合并到长期主档。
- 模拟面试和真实复盘只能提出“建议回流项”，不能自动改写经历主档或简历。

### 素材解析顺序

Skill 运行前按以下顺序定位基础素材：

1. 用户明确提供的飞书知识库文档。
2. 面试事件关联的求职记录、JD、准备/复盘文档。
3. 求职记录明确绑定的投递简历文档。
4. 知识库中已登记的个人经历或产品思维主档。
5. 仍有多个候选或缺少必要材料时，请用户选择或补充。

不得：

- 按标题模糊命中后直接使用第一份文档。
- 自动把“最新简历”当成某次投递使用的简历。
- 因企业类型猜测简历版本或面试形式。
- 从本地 CareerForge Skill 目录读取用户素材。
- 把私人简历或 ASR 上传给外部研究网站。

`status` 只允许 `needs_setup`、`partial`、`ready`：没有任何新 Skill 的必需目录可用时为 `needs_setup`；至少一个可用但尚未全部可用时为 `partial`；五项全部通过定位和写权限检查后才为 `ready`。每个 Skill 运行时以自己的 `readiness` 为准，不因其他 Skill 尚未配置而被阻塞。

`offerloop-workspace` 负责发现、创建和登记目录节点；五个新 Skill 负责内容。长期主档第一次产生确认内容时，由对应生产 Skill 在已登记目录中创建正文，再通过 workspace 契约登记文档 token，不创建空白主档。节点缺失时先路由到 `offerloop-workspace`，不得自行按名称创建第二套目录。

在 `offerloop-workspace/scripts/` 下新增 `artifact_contract.py`。该脚本不直接访问飞书；
线上节点查询、创建和文档读写由 Agent 按 `lark-wiki`、`lark-doc`、`lark-base` Skill
执行，脚本只承担：

- 节点定位和配置校验。
- 文档命名与 `run_id` 生成与去重。
- 来源元数据标准化。
- 完成/未完成状态路由到对应目录。
- Markdown 产物基本校验。

脚本提供稳定子命令：

```text
artifact_contract.py new-run --skill <skill_name> --json
artifact_contract.py new-entity-id --kind <experience|fact|pm|question> --json
artifact_contract.py resolve-folder --kind <folder_key> --json
artifact_contract.py resolve-document --kind <document_key> --json
artifact_contract.py build-title --skill <skill_name> --run-id <run_id> [标题上下文] --json
artifact_contract.py find-by-run --candidates <json_file_or_stdin> --run-id <run_id>
artifact_contract.py register-folder --kind <folder_key> --node-token <token> --json
artifact_contract.py register-document --kind <document_key> --node-token <token> --json
artifact_contract.py validate-markdown --file <relative_path_or_stdin> --run-id <run_id>
```

五个新 Skill 从自身 Skill 根目录解析兄弟 `offerloop-workspace`，再通过命令行调用该脚本，**不做跨 Skill Python import**。新 Skill 自己的 `scripts/` 只放本 Skill 专属逻辑（如 ASR 解析和评价依据）。`offerloop-workspace` 拥有产物契约实现，新 Skill 只拥有自己的领域代码。不新建 `skills/_shared/`，不新增第 10 个 Skill。

## Five Skill Designs

### 1. `resume-deepthink`

触发边界：

- 用户希望深挖实习、工作或项目经历。
- 用户希望熟悉简历内容、补充事实、发现亮点。
- 用户希望获得简历修改建议或可直接使用的表达。
- 不负责排版、导出 PDF 或正式模拟面试。

输入：

- 飞书知识库中的当前简历或用户指定版本。
- 可选的目标 JD、个人经历素材主档和历史深挖文档。
- 用户逐题回答。

交互：

1. 读取指定简历和已有素材，列出待确认经历。
2. 每次聚焦一段经历，逐层追问背景、目标、职责、行动、决策、协作、困难、结果和反思。
3. 对模糊信息帮助回忆，但不暗示虚假数字。
4. 每段经历阶段收束，区分已确认事实、待确认信息和缺口。
5. 用户确认事实后生成修改建议和多种可用表达。

Markdown 产物：

- 原简历内容诊断。
- 每段经历的事实证据卡。
- 用户熟悉经历所需的完整叙述。
- 简历修改建议。
- 可直接使用的简历 bullet。
- 面试可用 STAR/CAR 素材。
- 待补证据、风险点和建议回流项。

保存：

- 会话文档保存到 `06｜训练与题库/简历深挖`。
- 经用户确认后，将事实合并到 `03｜个人材料/个人经历素材主档`。新增且不冲突的事实可追加；与现有事实冲突时必须展示旧值、新值、各自来源和确认时间，经用户明确选择后才替换。主档每条事实保留最近来源文档、确认时间和状态，不能用整段覆盖代替字段级合并。
- 不直接修改当前简历；需要正式生成或排版时交给 `resume-tailor`。

### 2. `interview-prep`

触发边界：

- 用户收到面试邀请，或明确要求为某公司、岗位、轮次生成准备材料。
- 只生成准备文档，不进入一题一题的模拟面试。
- 笔试事件不触发 `interview-prep`；如用户为笔试事件请求准备材料，提示改走 `06｜训练与题库/笔试资料`，不生成面试准备文档，不回填 `笔试` 子表。

输入：

- 笔面试中心事件及关联求职记录。
- 岗位 JD。
- 实际投递简历；未绑定时由用户选择。
- 个人经历素材主档、产品思维素材主档和历史复盘（均为可选，懒创建节点下可能尚不存在）。
- 公司、行业、岗位与公开面经研究。

主档缺失兜底：

- 发现任一主档不存在时不阻塞流程，继续用实际投递简历和 JD 生成准备文档。
- 在对话和产物“产物信息”区明确标注“经历主档缺失，证据覆盖有限；建议事后运行 `resume-deepthink` 补齐”。
- 不在主档缺失时自动创建空白主档，不从未经确认的简历/面经推断生成主档内容。

流程：

1. 确认公司、岗位、轮次、时间、面试形式和实际投递简历。
2. 从飞书知识库读取长期素材和相关历史文档。
3. 解析 JD 的必备能力、加分项和风险点。
4. 优先使用公司官网、招聘公告、财报、官方产品资料；面经只作为辅助证据。
5. 将岗位要求映射到用户真实经历和产品思维素材。
6. 生成针对本轮面试的准备文档。

Markdown 产物：

- 面试基本信息与来源。
- 公司、业务、岗位和行业研究。
- JD 能力模型及用户证据映射。
- 投递简历逐项潜在追问。
- 高频问题及回答素材选择。
- 回答提纲，不提供与用户无关的万能答案。
- 简历风险、经历缺口和压力追问。
- 产品/场景问题准备。
- 反问面试官的问题。
- 面试前检查清单与专项训练建议。

保存与回填：

- 完成文档保存到 `04｜面试准备/准备完成`。
- 提前结束的草稿保存到 `04｜面试准备/待准备`。
- 关联面试事件时，将文档链接回填到 `笔面试中心` 的「面试准备文档」字段。
- 回填目标为 `笔面试安排` 单表中已确认的面试记录；`笔试` 记录的「面试准备文档」「面试复盘文档」始终为空，不回填。
- 回填优先使用用户选定或事件解析返回的单表 `record_id`；事件链接或明确 record ID 的优先级高于任何内容匹配。`来源邮件ID`只用于发现候选事件和历史补偿查找，不作为已选事件的主要写入标识。
- `全部安排` 与各环节视图共享同一字段，不执行跨表回填或补偿。
- 独立准备任务（无邮件事件）只保存知识库文档，不猜测 Base 记录，不创建空事件。

### 3. `mock-lab`

实现原则：

- 在 OfferLoop 仓库中重新创建，不能依赖或复制本地 CareerForge `mock-interview`；后者只作为交互与边界设计参考。
- 可借鉴其“一题一答、过程中不反馈、结束后统一报告、支持追问和提前结束”等通用设计。
- 不沿用固定的“HR→业务主管→高管”三轮假设。
- 本期不实现结构化/半结构化专用评分模型。

触发边界：

- 用户明确要求模拟面试、面试陪练或专项练习。
- “生成面试准备文档”必须路由到 `interview-prep`。
- “梳理经历并改简历”必须路由到 `resume-deepthink`。

输入：

- 优先读取指定的面试准备文档。
- 无准备文档时读取面试事件、JD、实际投递简历和个人素材。
- 用户选择完整模拟、单轮模拟或专项训练。

交互：

1. 开始前说明范围、预计题数、语言和控制指令。
2. 题源按固定优先级组合：本次面试准备文档和用户指定题目 → `06｜训练与题库/通用面试题` 中的个人题库 → JD 能力模型动态生成题 → Skill 自带 `references/` 中的小型通用题型兜底。飞书个人题库存在时必须读取，不能被内置题型替代；内置 references 主要保存出题规则和无个人题库时的最低可用题型。开始前让用户选择“完整模拟 / 单轮模拟 / 专项训练”。
3. 评分：逐题只给定性评价与依据，不打结构化分数（与“本期不实现结构化评分模型”一致）。评分依据可引用本次回答、实际投递简历、经历主档、产品思维主档、准备文档等任何可用资料，不作来源限制。
4. 一题一题提问。
5. 回答后不即时评价；根据简历和回答最多追问三层。追问是模拟面试官就同一题的进一步提问，不属于评价或打分；每题最多追问三层，用户可随时要求跳过或不再追问。
6. 支持暂停、跳过和提前结束。
7. 结束后统一分析内容、结构、证据、表达、岗位匹配和临场表现。

Markdown 产物：

- 模拟配置和素材来源。
- 完整问题、追问和用户回答。
- 逐题定性评价与依据（不打分）。
- 回答中的亮点、证据不足和逻辑漏洞。
- 个性化改进回答，不生成通用模板。
- 综合能力画像。
- 下一轮训练清单。
- 建议回流到简历深挖或产品思维训练的具体问题。

保存：

- 保存到 `06｜训练与题库/模拟面试`。
- 不写入真实面试复盘字段。
- 不自动更新准备文档或经历主档。

### 4. `talk-review`

触发边界：

- 用户完成真实面试，并提供 ASR、转写稿或飞书文档。
- 不用于模拟面试报告。

输入：

- 用户手动将 ASR/转写稿上传到 `05｜面试复盘/待复盘` 节点下，Skill 只读不写。
- 用户直接在对话粘贴 ASR 文本时，视为本次输入；不自动单独保存原始 ASR，不向外部服务上传。最终复盘文档必须标记“来源为对话粘贴、无持久化原始转写文档”，避免以后误判为可回溯来源。
- 可选读取面试准备文档、实际投递简历、JD和面试事件。

流程：

1. 保留原始转写，标记说话人不确定和 ASR 疑似错误。
2. 划分问题、追问和回答边界。
3. 关联笔面试中心事件：用户直接提供事件链接或 record ID 时优先使用；否则从 ASR/转写稿抽取公司、岗位、轮次和时间等线索，通过 `recruiting-reminder` 提供的稳定 CLI `event_lookup.py resolve --json` 查询候选事件。该 CLI 独占公司规范化、排除已结束、岗位匹配和主子表 ID 解析规则，`talk-review` 不复制、不 import 这些业务规则。唯一命中仍需展示给用户确认；多次命中且无法区分时不得自动取第一条；查不到候选时降级为独立复盘任务，不回填 Base。
4. 对比准备文档，识别命中、遗漏和临场新增题目。
5. 按题评价内容、结构、证据、表达和岗位匹配。
6. 生成更好的回答与后续训练任务。
7. 新发现的经历事实必须让用户确认后，才能建议回流经历主档。

Markdown 产物：

- 面试概览。
- ASR 质量与不确定片段说明。
- 还原后的问题和追问链。
- 用户回答摘要与逐题评价。
- 准备命中和遗漏分析。
- 更好的回答结构和参考表达。
- 面试官关注点推断，并明确其不确定性。
- 简历修改建议。
- 产品思维、经历深挖和模拟训练任务。
- 下一轮面试行动清单。

保存与回填：

- 完成文档保存到 `05｜面试复盘/已完成复盘`。
- 提前结束的草稿保存到 `05｜面试复盘/待复盘`。
- 原始 ASR/转写稿原位保留在 `05｜面试复盘/待复盘`，不自动移动；用户手动上传的文档 Skill 只读不写。
- 关联事件时回填 `笔面试安排` 单表记录的「面试复盘文档」字段，不回填笔试记录。
- 回填优先使用已确认事件的单表 `record_id`；`来源邮件ID`只用于发现候选和历史补偿查找。
- `面试（轮次待确认）`使用同一条单表记录。
- 不自动修改实际投递简历、准备文档或长期素材主档。

### 5. `pm-sense`

迁移原则：

- 将现有本地 `product-thinking-coach` 作为逻辑参考，在 OfferLoop 仓库中建立独立版本。
- 保留“独立初答→点评→逐步追问→自主总结→外部研究→完善答案”的训练逻辑。
- 删除文章发布、标题标签、小红书卡片、图片、ZIP和视觉排版。
- 最终产物固定为 Markdown 飞书文档。
- 小红书可以作为用户观察和观点的可选研究来源，但不是必选来源，也不生成小红书发布物。

触发边界：

- 产品设计、产品策略、商业化、AI 产品、B/C 端、行业分析和发散性场景问题。
- 不承担一般组织协调、应急应变等结构化面试专项训练。
- 在模拟面试过程中不打断角色扮演进行教学；由模拟结束后的训练建议触发。

输入：

- 用户当前提出的问题或从面试准备、模拟面试、真实复盘生成的训练题。
- 飞书知识库中的“产品思维素材主档”和相关历史训练文档；主档存在时必须先读取，用于识别重复题目、可复用判断和长期薄弱项。
- 用户独立初答以及后续逐轮回答。
- 用户自主总结完成后检索到的公开外部证据。

交互：

1. 用户有题目时先要求独立初答；没有题目时提供三个开放题。
2. 初答前不提供框架和标准答案。
3. 点评最关键的两至三个逻辑问题。
4. 每轮只推进一至三个判断。
5. 用户自主总结后再进行外部研究。
6. 区分事实、官方口径、作者观点、假设和推断。
7. 最终生成适合面试表达和长期复用的素材卡。

Markdown 产物：

- 题目、题型和能力标签。
- 用户原始答案。
- 讨论中暴露的问题和确认后的判断。
- 外部研究证据及来源。
- 完整分析链路。
- 反方观点、边界条件和失败风险。
- 推荐方案及验证指标。
- 1分钟口语答案。
- 3分钟完整答案。
- 可能的面试官追问。
- 可迁移到其他题目的方法。
- 后续训练建议。

保存：

- 会话产物保存到 `06｜训练与题库/产品思维`。
- 经用户确认后，将核心判断、答案版本和能力标签合并到该目录下的“产品思维素材主档”。
- 不生成 HTML、PNG、图片排版、发布标题、标签或 ZIP。

## Implementation, Migration, and Tests

### 实施顺序

1. 扩展 `offerloop-workspace` 的产物契约、目录定位和 schema v3 配置。
2. 更新 `offerloop-setup` 的 `coaching` 预检、权限和渐进启用流程。
3. 实现 `resume-deepthink` 和 `pm-sense`。
4. 为 `recruiting-reminder` 增加稳定事件查询 CLI。
5. 依次实现 `interview-prep`、`mock-lab`、`talk-review`，接通准备/复盘文档回填和主子表一致性。
6. 更新安装器、README、首页模板、兼容性文档和发布验收。

### 安装与仓库契约

- 仓库 Skill 数由4个增加到9个。
- 安装器、manifest、冷安装验收和多 Agent 安装测试同步更新。
- 每个新 Skill 包含：
  - `SKILL.md`
  - `agents/openai.yaml`
  - 最少且必要的 `references/`
  - 仅在有确定性逻辑时添加 `scripts/`
- 不包含 README、变更日志、示例占位或图片发布资产。
- 五个新 Skill 的前置依赖统一指向 OfferLoop 的 `offerloop-workspace` 和所需飞书 Skill。

### 迁移

- schema v2 用户升级后保持原配置和数据不变。
- schema v2 → v3 升级流程：
  1. `offerloop-setup` 检测到 `schema_version` 为 2 且用户请求启用 `coaching` 能力时，提示“coaching 需要把配置升级到 schema v3”，等用户明确确认后再写。
  2. 在用户私有配置文件里追加 `artifact_storage` 字段，所有目录和文档 token 留空字符串，五项 `readiness` 均为 `false`，`status` 置 `needs_setup`、`save_policy` 置 `auto_on_completion`、`format` 置 `markdown_docx`。
  3. 将 `schema_version` 改为 3。
  4. 不自动创建任何飞书知识库节点，不移动历史文档；目录 token 在用户首次实际运行某个新 Skill 时由 `offerloop-workspace` 懒创建并回填配置。对应 Skill 的必需目录全部验证可写后，将该 Skill 的 `readiness` 更新为 `true`，再按整体情况把 `status` 更新为 `partial` 或 `ready`；长期主档文档仍在首次确认内容时创建。
  5. 用户拒绝升级时不阻塞 v2 既有能力（`collection` / `reminder` / `workspace`）的使用；`coaching` 预检报告 `needs_action` 并说明升级动作。
- 用户首次启用任一新 Skill 时：
  1. 只读检查固定目录和权限；
  2. 展示缺失节点；
  3. 经确认后创建通用节点并登记 token；
  4. 再开始正式训练。
- 已有同名节点出现多个候选时必须让用户选择，不能自动取第一个。
- 历史准备/复盘字段继续有效，不强制回填旧记录。

### 测试

- 仓库和安装器：
  - 9个 Skill 全部被发现、安装和校验。
  - 重复安装幂等，冲突升级仍备份用户已有 Skill。
  - 新 Skill 不包含 TODO、HTML/PNG/ZIP 发布资产或本地绝对路径。

- 产物契约：
  - 会话产物与长期主档正确路由到对应节点。
  - Markdown 标题、表格、转义和来源链接可被飞书正确创建、读取。
  - 五类标题均包含 `run_id`；写入成功但响应丢失后，按确定性标题重试不会重复创建。
  - 目录 token 与主档文档 token 分开解析，不能把主档文档当成父目录创建子节点。
  - 完成、提前结束、暂停和保存失败行为符合契约。
  - 长期主档只接受用户确认内容；冲突事实必须展示旧值、新值和来源，未确认时不得覆盖。

- 回填一致性：
  - `interview-prep` 完成且关联面试类事件时，「面试准备文档」写入已确认的 `笔面试安排` 记录；笔试记录的「面试准备文档」「面试复盘文档」始终为空。
  - `talk-review` 完成且关联面试类事件时，「面试复盘文档」写入同一条单表记录。
  - `面试（轮次待确认）`事件使用同一套单表回填规则。
  - 同一 record ID 与同一 `run_id` 重复回填不产生重复写入或覆盖冲突；`来源邮件ID`只用于发现候选事件和历史补偿查找。
  - `talk-review` 自动查候选事件时，多候选必须让用户选择，不得自动取第一条；查不到候选时降级为独立复盘，不创建空事件。
  - `talk-review` 与 `interview-prep` 通过 `recruiting-reminder` 的事件查询 CLI 获取候选和单表 record ID；测试保证两者没有复制公司/岗位匹配规则。
  - 独立准备/复盘任务（无邮件事件）只保存知识库文档，不创建 Base 记录。

- 素材读取：
  - 显式文档优先于默认主档。
  - 多份简历时要求用户选择。
  - 面试准备读取实际关联材料，不使用任意“最新版”。
  - 模拟面试优先读取面试准备文档和飞书个人题库，只有个人题库缺失时才使用 Skill 内置题型兜底。
  - 缺权限、文档不存在、节点重复时安全停止，不回退本地隐式资料。

- Skill 场景：
  - 简历深挖能从模糊经历得到确认事实、简历 bullet 和面试素材。
  - 面试准备能从事件、JD、简历和主档生成岗位化文档并回填。
  - 模拟面试过程中不泄露反馈，结束后生成逐题报告。
  - 面试复盘能处理说话人混乱和低质量 ASR，不把猜测当事实。
  - 对话粘贴 ASR 时，复盘文档明确标记没有持久化原始转写来源。
  - 产品思维教练坚持先独立初答，输出1分钟/3分钟答案且不生成发布物。

- 回归：
  - 原四个 OfferLoop Skill 的现有测试继续通过。
  - `job-collection` 和 `recruiting-reminder` 可在未启用 coaching 时独立运行。
  - 工作台、三张 Base 和旧知识库结构不因新功能失效。

## Assumptions

- 正式范围为五个新 Skill；结构化面试教练延期。
- Markdown 以飞书 Docx/Wiki 文档承载，不额外上传 `.md` 文件。
- 每次成功或明确提前结束后自动保存；普通暂停不保存正式产物。
- 每次运行保留独立文档，长期主档只在用户确认后更新。
- 用户可在启用 coaching 时一次性确认自动保存策略，无需每次重复确认创建最终文档。
- 所有知识库和文档操作默认使用飞书 user 身份，知识库保持私有。
- 外部研究只接收公开的公司、岗位和行业查询，不上传简历、ASR或个人素材。
- 本期不实现多简历版本管理、不在初始化询问目标岗位；相关字段保持可扩展，首次出现真实需求时再增加。
- 共享 artifact 契约以命令行方式被新 Skill 调用，不引入跨 Skill Python import，不新建 `skills/_shared/` 目录。
