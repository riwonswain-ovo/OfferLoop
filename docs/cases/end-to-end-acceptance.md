# OfferLoop 合成端到端验收用例

此用例用于在发布到 GitHub 前跑通整体流程。默认只使用本地合成对象、dry-run 和只读核验；
不要把它直接应用到用户真实飞书记录、日历或邮箱。

最近一次发布前的脱敏本地执行结果见
[release-acceptance-2026-07-20.md](release-acceptance-2026-07-20.md)。

## 前置条件

- `offerloop-setup` 对 `full` 的离线预检已完成；任何 `blocked` 或 `needs_action` 项都已明确处理。
- 三张 Base、知识库首页、工作台 URL 和可选 `progress_sync` 定位器均已登记。
- 真实 IMAP、飞书写入与日历创建仍需在各自步骤获得单独确认。

## 用例 A：招聘信息与投递进展

输入一条合成招聘信息：公司为“示例科技”，岗位为“AI 产品经理”，投递进度为“待确认”。

预期：

1. 企业清单只产生字段契约规定的信息；`子表 record_id` 保留在最后。
2. 将投递进度改为“已投递”后，求职进展以企业清单 record ID 创建或更新一条记录。
3. 新记录的公司可带入，但投递岗位和岗位 JD 都为空。
4. 对同一企业清单 record 再次同步时，不覆盖用户填写的投递岗位、岗位 JD、首次投递日期和更高阶段。

## 用例 B：明确轮次的面试通知

输入一封合成邮件：示例科技、AI 产品经理、一面、固定时间。先执行事件抽取和关联 dry-run。

预期：

1. 候选结果进入“全部安排”和“一面”子表的逻辑路径。
2. 关联到用例 A 的唯一求职记录。
3. 仅在用户确认 Base 写入后才创建事件；仅在用户第二次确认日历方案后才创建日程。
4. 求职进展从“已投递”单调推进到“一面”。
5. 面试准备文档、面试复盘文档字段保留为空，供后续 Skill 使用。

## 用例 C：同公司多岗位与轮次待确认

1. 为同一公司再创建一条不同岗位的合成投递记录，并输入该岗位的一面通知。
   - 预期：产生独立事件并关联正确岗位，不合并到第一条申请。
2. 输入一封仅写“技术面”的合成邮件，未写明一面/二面。
   - 预期：只进入“全部安排”，环节为“面试（轮次待确认）”，不创建阶段子表记录，不推进求职进展。

## 用例 D：重复、改期和工作台

1. 重新输入相同来源邮件 ID。
   - 预期：不重复创建事件或日程。
2. 输入引用原邮件 ID 的改期通知。
   - 预期：更新原事件，不创建第二个同一事件。
3. 只读打开工作台 URL 和知识库首页。
   - 预期：入口可访问；业务数据展示、视图切换和未来 7 天模块均不需要复制真实数据到新系统。

## 用例 E：schema v4 与飞书产物幂等

1. 用包含既有 Base、通知和同步桥接定位的 schema v2 合成配置启用 `coaching`。
   - 预期：原字段保持不变，追加空的 `artifact_storage`，版本升级为 4；未创建任何线上节点。
2. 为五种产物分别生成固定时间和 suffix 的 `run_id`、标题与目录路由。
   - 预期：标题包含 `run_id`，完成/提前结束路由正确，文件夹 locator 与长期主档 locator 分离。
3. 模拟写入成功但响应丢失后重试。
   - 预期：按相同 `run_id` 唯一找到原文档，不创建重复节点；多个命中时停止让用户选择。

## 用例 F：经历深挖与产品思维

1. 给出一段只有“负责功能优化、提升效果”的模糊经历。
   - 预期：`experience-deepthink` 先追问行动、决策、结果口径和个人边界，不补写虚假数字；用户确认后
     生成事实卡、简历 bullet 和 STAR/CAR 素材。
2. 给出一道产品场景题。
   - 预期：`pm-sense` 先让用户独立回答，自主总结前不检索；最终输出 1 分钟/3 分钟答案，不生成
     小红书排版、图片、HTML 或 ZIP。
3. 两次运行都保存独立 Markdown；只有确认内容字段级合并到各自主档，冲突时不覆盖。

## 用例 G：面试准备、模拟和真实复盘

1. 为用例 B 的事件提供 JD 和两份简历。
   - 预期：`interview-prep` 要求选择实际投递简历，生成能力映射与准备文档，并用精确主/子表
     record ID 同步回填；笔试和独立任务不回填。
2. 用准备文档运行 `mock-lab`。
   - 预期：题目优先级为准备文档、指定题、飞书个人题库、JD 生成题、通用兜底；过程中不点评，
     结束后生成逐题报告。
3. 输入包含说话人混乱和 ASR 错误的真实转写。
   - 预期：`talk-review` 标记不确定性、还原追问链、对比准备命中；对话粘贴来源明确标记没有
     持久化原始转写文档。

## 用例 H：事件歧义、冲突与补偿

1. 用公司相同、岗位不同的两条事件运行 `event_lookup.py resolve`。
   - 预期：缺少岗位时返回 `ambiguous`，不得选择第一条；精确 record ID 优先。
2. 目标文档字段已有不同 URL。
   - 预期：回填计划返回 `conflict`，不覆盖。
3. 明确面试轮次缺少子表 record ID。
   - 预期：返回 `needs_action`，不产生半套写入。
4. 主表写成功、子表失败。
   - 预期：保留主表写入，记录子表精确 record ID、字段、URL 和原 `run_id`，下次幂等补偿。

## 用例 I：范围边界

1. 请求笔试准备。
   - 预期：`interview-prep` 路由到笔试资料，不写面试准备/复盘字段。
2. 只因公司是央国企而要求自动切换简历或结构化面试模型。
   - 预期：不按企业类型猜测；当前版本明确说明结构化/半结构化专项不在范围。
3. 缺少经历或产品主档。
   - 预期：准备流程继续，但明确证据覆盖有限，不创建空主档。

## 用例 J：首次安装欢迎与长期能力地图

1. 在空的 Agent Skills 目录安装 OfferLoop。
   - 预期：安装成功后按“核心、业务、可选工作台、可选 Agent / 求职训练能力”介绍全部十一个 Skill；每项包含用途和一句
     自然语言示例，并展示两个常用闭环、隐私边界和首次使用指令。
2. 使用 `--json` 完成首次安装。
   - 预期：返回结构化 `welcome`，其中十一个 Skill 恰好各出现一次；人类输出和 JSON 使用相同内容。
3. 在相同目录重复安装。
   - 预期：返回 `already_installed`，不重复输出或返回完整欢迎。
4. 新开会话并发送首次使用指令。
   - 预期：`offerloop-setup` 读取欢迎参考，完整介绍十一个 Skill 后再询问当前目标；介绍阶段不询问
     目标岗位、不访问飞书或邮箱。
5. 打开知识库首页与工作台。
   - 预期：知识库首页保留十一个 Skill 表格；如果用户选择部署工作台，工作台按求职基础与求职训练
     两组提供可折叠的十 Skill 能力地图。未部署工作台时，首页和全部核心能力仍可用。

## 通过标准与记录

每个用例记录：执行模式（合成/dry-run/只读/已确认写入）、结果、失败原因和待补偿项。通过
不等于已向真实数据写入；任何真实写入、日历创建或邮件读取都必须有单独的用户确认记录。
