# AI 产品经理专项简历规则

本文件只在目标岗位以 AI 产品、AIGC、大模型、Agent、模型/数据平台或 AI+行业产品判断为核心时
读取。岗位名称含“AI”但 JD 实际偏销售、交付、运营或纯算法时，以真实 JD 建模并只采用相关
部分。

## 一、建立 AI 产品岗位画像

从 JD 判断招聘方实际要求的任务，不机械按岗位标题分类：

- **AI 应用与 Agent**：场景、交互、Prompt/Workflow/Agent、工具、人机边界和质量；
- **RAG 与知识产品**：知识治理、检索、引用、权限、评测和反馈；
- **模型/数据平台**：模型接入、API、评测、数据、成本、开发者或内部使用体验；
- **AI+行业产品**：行业流程、规则、专业风险、ROI、系统集成和组织落地；
- **训练/微调相关产品**：训练目标、数据、基座选择、实验、验收和上线治理。

复合岗位保留真实任务组合。不能因为 JD 提到 Agent 或大模型，就把所有经历改写成 AI 项目。

## 二、选择经历与证明角度

每段入选经历只选择一条主证明角度：

1. 场景与 AI 适用性判断；
2. AI 产品方案与关键取舍；
3. 数据、Prompt、RAG、Agent 或训练链路；
4. 评测、Bad Case 和可靠性治理；
5. 跨算法/研发/业务落地；
6. 用户采用、业务价值或成本结果。

同一经历可以有辅助角度，但不要在 2–4 条 bullet 中重复罗列完整架构。

## 三、AI Bullet 结构

从以下五层中选择最有证据的两至三层形成一条 bullet：

```text
业务问题/用户任务
→ 本人的产品判断或取舍
→ 真实采用的 AI、规则、程序与人工组合
→ 本人可验收交付
→ 已确认结果或成熟度
```

要求：

- 开头优先写候选人的决策或动作，而不是“项目支持某功能”；
- 技术方法必须说明服务了哪个业务环节；
- 结果只写材料确认的证明范围；
- 没有结果数字时写真实交付物、验证方式、用户反馈或阶段结果；
- 一条不需要覆盖全部五层，也不强制包含数字。

## 四、技术名词门禁

写入以下名词前，从用户选择的经历材料中找到直接证据：

| 表达 | 至少应有的证据 |
|---|---|
| Agent / 智能体 | 动态判断、工具/行动或循环；只有固定步骤时写 Workflow |
| 多 Agent | 独立职责、上下文/权限或协作机制；角色命名不够 |
| RAG | 外部知识检索进入生成链路，并有数据源与验证 |
| Agentic RAG | 根据反馈发生换源、重检索、工具调用或验证，不只是 Query Rewrite |
| Prompt 优化 | 版本、失败样本、改动理由与验证，不是只写过提示词 |
| 微调 / LoRA | 训练目标、数据、基座、实验和结果；仅了解概念不写 |
| MCP / API | 项目中真实接入或设计的外部能力、输入输出和边界 |
| 上线 / 生产 | 真实用户或流量、运行、监控和故障治理 |

证据只支持“参与方案设计”时，不升级为“实现”或“搭建”。

## 五、成熟度动词

使用项目材料中的正式阶段；需要统一表达时参考：

- **概念/方案**：分析、定义、设计、规划、提出；
- **原型**：绘制、制作、验证交互；
- **Demo/PoC**：搭建验证链路、跑通、对比、记录；
- **MVP**：交付最小闭环、验收核心场景；
- **试点**：推动试点、收集真实反馈、迭代；
- **生产运行**：上线、运营、监控、治理。

“从 0 到 1”“主导”“全链路”仍需额外证明职责范围和决策权，不能由阶段自动推出。

## 六、指标与结果

AI 项目可能同时存在：

- 能力/系统：准确、召回、排序、稳定、延迟、成本；
- 产品使用：采纳、重试、修改、任务完成、满意；
- 业务：效率、成本、收入、风险、质量；
- 安全：幻觉、越权、人工接管、严重错误。

只写与项目目标相关且已经确认口径的指标。检查：

- 指标叫什么、衡量什么；
- 基线和结果是否同口径；
- 样本、窗口或数据来源是否足够说明证明范围；
- 团队结果和个人行动是否合理连接；
- 是否存在无法归因的同期变化。

不得从课程示例补入阈值、样本量、成本或提升比例。

## 七、技能区

按“能力 + 实际用法”组织，而不是工具堆砌。例如只有在经历材料支持时，才可写：

- Prompt：模板、版本和 Bad Case 回归；
- RAG：知识治理、检索策略、引用和评测；
- Agent：任务边界、工具契约、人机确认和失败处理；
- 模型评测：测试集、Rubric、指标与回归；
- API/MCP：能力接入、数据/工具契约和权限；
- 训练/LoRA：训练数据、实验与验收。

不写“熟悉大模型”“精通 AI”等无法核验的等级词。

## 八、专项质量门

生成前后逐项检查：

- 每个 AI 技术词都能在所选经历深挖材料中定位；
- 每个强数字都能解释口径与证明范围；
- Demo、PoC、MVP、试点和上线没有跨级；
- 团队技术实现没有变成候选人个人实现；
- 业务问题、产品判断和技术方法至少形成一条连接；
- 没有为了 JD 添加未使用的模型、框架或工具；
- 简历中的每个强主张至少能承受“为什么、具体例子、你做了什么”三层追问。

任一红线失败，先弱化或删除表达；事实需要补充时建议回到 `experience-deepthink`。
