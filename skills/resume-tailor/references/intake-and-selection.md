# Resume Tailor 输入与经历选配

## 1. 岗位输入

只把“岗位名称”作为硬输入。优先接收公司、完整 JD、招聘类型和城市，但缺少这些信息不阻塞。

有 JD 时提取：

- 学历、专业、年级、到岗时间、出勤天数等硬门槛；
- 三至六项核心能力；
- 主要工作对象、任务、产出和指标；
- 工具、方法和领域关键词；
- 文件命名要求。

没有 JD 时，向用户确认招聘方最应看到的三至六项能力，不联网猜测具体公司的要求。

## 2. 候选经历卡

列候选时使用紧凑格式：

```markdown
1. 经历名称｜岗位方向
   - 可证明：用户研究、需求判断、跨团队落地
   - 证据强度：强 / 中 / 弱（说明一条依据）
   - 建议：核心 / 辅助 / 压缩
```

候选卡只帮助选择，不能代替用户决定。默认建议 2–4 段，优先满足：

1. 与岗位核心能力直接相关；
2. 有清楚的个人行动；
3. 有可核实的规模、结果或反馈；
4. 与其他经历提供不同证据，避免重复。

让用户回复编号、经历名或自行组合，并确认每段主打角度。用户选择弱相关经历时说明版面代价，
但仍尊重选择。

## 3. 固定信息卡

经历选择后一次展示；用户可跳过所有可选项：

```markdown
请补充或确认以下信息。没有、暂不展示或稍后补都可以：

1. 基本信息：姓名｜手机｜邮箱｜当前城市
2. 教育背景：学校｜专业｜学历｜起止/预计毕业时间
3. 学业信息（可选）：GPA/排名｜3–5 门相关课程
4. 获奖荣誉（可选）：奖项全称｜级别｜时间｜名次/比例
5. 专业技能：工具/方法｜使用场景或熟练证据
6. 语言与证书（可选）：名称｜等级/分数｜取得时间
7. 自我评价（可选）：不展示 / 展示；若展示，请给 3 个能被经历证明的特点
8. 求职约束（JD 要求时）：到岗时间｜每周天数｜可持续时长
```

用户已经提供的项目改为“已记录”，不要重复索取。

## 4. 信息规范

- 奖项写正式名称、级别和时间；无法确认级别时不自行升级。
- 技能写成“技能 + 实际用法”，例如 `SQL（多表 JOIN、窗口函数）`；没有证据时不写“精通”。
- 自我评价优先改为经历中的证据。确需单列时控制在一行，使用具体、可验证的表达。
- 联系方式只保留一组手机和邮箱。
- 作品集、GitHub、个人网站只有与岗位相关且用户确认公开时才展示。

## 5. 生成前摘要

使用以下结构请求最终确认：

```markdown
- 目标：<公司可选>｜<岗位>
- 版本依据：<JD 日期/文件名，或“无 JD 的方向版”>
- 经历顺序：<经历 A> → <经历 B> → <经历 C>
- 主打能力：<每段一条>
- 其他区块：教育｜荣誉（是/否）｜技能｜自我评价（是/否）
- 文件名：<最终名称>.pdf
```
