# 简历内容来源与撰写方法

本文件的项目逐字稿契约用于**从零制作模式**。如果用户已经提供自己的简历并要求只优化排版，原简历
就是内容源：完整保留文字、事实、日期、指标、顺序和信息取舍，只处理 OCR 歧义、模块映射和视觉格式，
不要求补做经历深挖，也不按本文件改写项目正文。原简历中的“产品思考”文字原样并入“项目经历”。

## 1. 项目内容来源契约

实习经历和项目经历中的每一个项目，都必须对应一份 `experience-deepthink` 生成并经用户确认的
《面试逐字稿》。简历项目描述的直接内容源只能是其中第一题“请介绍一下这个项目”；对应的
《细节复原稿》是最终事实依据，用于核对责任边界、指标口径和事实状态。

固定链路为：

`用户真实讲述 → 细节复原稿 → 面试逐字稿第一题 → 简历项目描述`

- 旧简历、JD、岗位常识和写作模板只能帮助选择、排序或压缩，不能提供新的项目事实。
- 逐字稿其他六题默认不进入项目介绍，避免把失败复盘、重来设想和未来计划写成已经完成的成果。
- 缺少第一题逐字稿时，不生成正式项目描述；提示用户先使用 `experience-deepthink` 完成该项目深挖。
- 逐字稿与细节复原稿冲突时，以细节复原稿为准，并先请用户确认，不静默修正。

将逐字稿第一题压缩为简历书面语时按下表映射：

| 逐字稿结构 | 简历用途 |
| --- | --- |
| 起始句 | 项目名称与一句话定位 |
| S | 背景、用户问题与项目目标 |
| T | 个人职责与贡献边界 |
| A | 核心判断、产品方案与关键动作 |
| R | 验证方式与结果证据 |
| L | 通常不进项目正文；可作为项目补充证据或自我评价候选 |

压缩可以删除口语连接、重复背景和次要例子，但不得改变角色、因果、时间身份、数字或归因范围。

## 2. 实习经历结构

每段实习只写一次岗位职责摘要，再展开一个或多个项目：

```markdown
公司｜部门｜岗位｜日期

岗位职责：一句话说明所在业务、主要负责方向和工作范围。

项目名称｜一句话定位

- 背景与目标：……
- 核心判断与动作：……
- 验证与结果：……
```

岗位职责摘要综合该段实习中用户选定项目逐字稿的起始句、T 和用户确认的正式岗位范围，不提前罗列
项目结果，也不扩大为团队或部门全部职责。多个项目共用一句岗位职责摘要，不逐项目重复。

## 3. 项目经历结构

独立项目、竞赛、创业、校园项目或 AI Coding 项目不写岗位职责摘要，直接进入项目：

```markdown
项目名称｜个人角色或一句话定位

- 背景与目标：……
- 产品设计与关键动作：……
- 验证与结果：……
- 项目链接：存在可靠公开链接时保留
```

项目正文同样只能压缩对应的面试逐字稿第一题；不能因为是个人项目就默认写成独立主导或 `0→1`。

## 4. 补充素材发现

读取目标岗位或 JD 与用户选定的逐字稿后，先列出：

1. 已被当前经历证明的岗位能力；
2. JD 高度重视但证据仍弱或缺失的能力；
3. 值得向用户定向询问的补充材料类型。

必须进行一次有缺口依据的询问，例如：

> 当前经历已经证明【能力】，但对【缺口能力】的证据较弱。你是否还有相关的产品思考、行业研究、
> 竞品分析、用户研究、PRD、原型、Demo、作品集、公开文章、竞赛或校园项目，希望作为本次简历的
> 候选材料？

不得笼统扫描用户全部历史文件或知识库。只读取用户主动提供、明确选择，或在完整模式下明确授权读取的
材料。拿到补充材料后默认归入“项目经历”候选，再根据证据类型给出推荐，最终由用户确认：

- 完整产品实践：作为项目经历候选；如要写成项目，仍须先完成对应经历深挖与项目介绍逐字稿。
- 用户问题、核心判断、方案取舍和验证方式：并入对应项目；没有对应项目时作为新的项目经历候选。
- 对既有项目的原始证据：补充对应逐字稿或用于事实核验，不单独包装成新项目。
- 可验证的工具、语言或学习证据：作为个人技能与自我评价候选。
- 与目标岗位相关性弱或无法核验：不进入简历。

补充素材可能改变模块选择或顺序时，必须再次请用户确认最终模块、顺序和采用材料。

## 5. Markdown 内容确认

正式排版前先生成 `resume-content.md`，并附一份不进入最终简历的来源与缺口清单。内容稿至少标明：

- 每个项目对应的面试逐字稿名称；
- 岗位职责摘要使用了哪些已确认项目；
- 新增项目或其他补充材料的来源；
- 仍待确认的责任、指标、时间或链接。

用户确认 Markdown 后才能写入 HTML。后续为控制页数进行删减时，只压缩已确认内容；不得回到旧简历或
岗位常识补写新事实。
