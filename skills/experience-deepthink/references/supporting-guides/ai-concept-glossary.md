# AI 产品面试概念与经历追问词典

本参考用于两类情况：

1. 面试准备中，用户直接询问某个 AI 术语或需要演练术语突袭；
2. 经历深挖中，必须澄清概念才能判断项目机制、方案取舍或个人贡献。

它不是默认加载的知识大全，也不是按目录顺序盘问的题库。

## 使用方式

每个概念统一按六层组织：

`一句话本质 → 简明机制 → 相邻概念对比 → PM 决策点 → 经历追问 → 易错边界`

直接回答面试术语时，优先用前四层组成 30–60 秒答案；若有用户经历，再补一句真实项目连接。
经历深挖时，以“经历追问”验证用户是否真的应用过该概念，不要求背诵定义。

## 模型与生成基础

### LLM（大语言模型）

- **一句话本质**：基于大规模数据训练、按上下文预测后续 Token，并由此表现出语言理解与生成
  能力的模型。
- **简明机制**：输入被编码为 Token，模型结合上下文计算下一 Token 的概率分布并逐步生成。
- **相邻概念对比**：LLM 是模型能力底座；Agent 是围绕模型加入目标、状态、工具和运行循环的
  系统形态。
- **PM 决策点**：能力、上下文、时延、成本、部署、隐私与生态是否适配任务。
- **经历追问**：你使用模型解决了链路中的哪一步，换模型后什么指标或体验发生变化？
- **易错边界**：模型名称或参数量不能直接证明任务效果；具体能力会随版本变化。

### Token

- **一句话本质**：模型读取和生成文本时使用的基本离散单位，不等同于固定数量的字或词。
- **简明机制**：分词器把文本切成 Token；输入和输出 Token 共同影响上下文占用、成本与时延。
- **相邻概念对比**：字符、汉字、单词是人类文本单位；Token 是模型和分词器定义的计算单位。
- **PM 决策点**：长文档、历史对话和结构化输出是否超限，如何压缩、检索或分段。
- **经历追问**：你的产品如何控制输入长度、输出长度、成本和关键信息丢失？
- **易错边界**：不同模型/分词器的换算不同，不应使用固定字数比例作为通用事实。

### Context Window（上下文窗口）

- **一句话本质**：模型一次推理可共同处理的 Token 范围。
- **简明机制**：系统指令、用户输入、历史消息、检索内容、工具结果和输出预算共同占用窗口。
- **相邻概念对比**：上下文是本次推理可见信息；长期记忆是跨任务保存、选择并重新注入的信息。
- **PM 决策点**：哪些信息必须常驻、按需检索、摘要压缩或移出模型上下文。
- **经历追问**：超长对话或文档导致过什么失败，你如何选择保留和丢弃的信息？
- **易错边界**：窗口更长不等于模型一定能同等关注所有位置，也不等于拥有永久记忆。

### Embedding（向量表示）

- **一句话本质**：把文本、图片等内容映射为可计算相似度的稠密向量。
- **简明机制**：语义相近内容通常在向量空间更接近，可用于检索、聚类、去重和推荐。
- **相邻概念对比**：Embedding 负责表示；向量数据库负责存储、索引和检索这些表示。
- **PM 决策点**：表示模型、切片粒度、召回方式、语言/领域适配和更新成本。
- **经历追问**：你怎样验证相似度召回的是“任务相关”而不只是字面相近？
- **易错边界**：向量相近不等于事实正确；Embedding 本身不会完成答案生成。

### Vector Database（向量数据库）

- **一句话本质**：面向向量存储和近似相似度检索优化的数据系统。
- **简明机制**：保存向量及元数据，通过索引召回相近条目，并可结合关键词或过滤条件。
- **相邻概念对比**：它是 RAG 检索层的一种实现，不等同于完整知识库或 RAG 系统。
- **PM 决策点**：数据规模、更新频率、过滤权限、召回延迟、混合检索和运维成本。
- **经历追问**：为什么使用向量检索，元数据过滤和权限如何避免召回错误内容？
- **易错边界**：不是所有检索都需要向量库；结构化精确查询可能更适合传统数据库。

### Temperature / Top-K / Top-P

- **一句话本质**：控制生成时从候选 Token 概率分布中如何采样的一组参数。
- **简明机制**：Temperature 调整分布尖锐程度；Top-K 限定概率最高的 K 个候选；Top-P 选择
  累计概率达到阈值的候选集合。
- **相邻概念对比**：它们改变生成随机性和多样性，不直接增加知识或推理能力。
- **PM 决策点**：稳定抽取、客服回答通常偏保守；创意生成可允许更多多样性，并用评测验证。
- **经历追问**：你调整采样参数解决了什么失败，是否与 Prompt、模型版本分开做过对照？
- **易错边界**：Temperature 设为 0 也不应被承诺为跨版本、跨基础设施的绝对确定性。

### Hallucination（幻觉）

- **一句话本质**：模型生成流畅但缺乏可靠依据、与事实或给定材料不一致的内容。
- **简明机制**：生成目标是预测合理后续，不天然执行事实校验；信息不足、冲突或错误上下文会
  放大问题。
- **相邻概念对比**：事实错误是结果；幻觉强调缺少依据的生成机制，不能覆盖所有业务错误。
- **PM 决策点**：是否需要 RAG、引用、拒答、规则校验、工具查询、人工复核和风险分级。
- **经历追问**：你如何定义和分类幻觉，哪类最影响用户，治理后怎样回归验证？
- **易错边界**：RAG 只能降低特定幻觉风险，不能消除幻觉；“没有投诉”也不是无幻觉证据。

## AI 产品架构

### Prompt

- **一句话本质**：向模型表达任务、上下文、约束和输出要求的输入设计。
- **简明机制**：通过角色、目标、示例、步骤、格式和边界引导模型行为，可与结构化校验配合。
- **相邻概念对比**：Prompt 是推理时控制；微调通过训练改变模型参数或适配参数。
- **PM 决策点**：任务是否可仅靠提示稳定完成，版本、变量、模板、评测和注入风险如何管理。
- **经历追问**：你根据什么 Bad Case 改了哪一处 Prompt，如何证明不是偶然变好？
- **易错边界**：长 Prompt 不必然更好；泄露系统提示也不是唯一安全风险。

### RAG（检索增强生成）

- **一句话本质**：先从外部知识源检索相关证据，再让模型基于证据生成答案。
- **简明机制**：常见链路为知识处理、索引、查询理解、召回、重排、上下文拼装、生成和引用。
- **相邻概念对比**：RAG 主要补充可更新知识和依据；微调更适合改变稳定行为、风格或任务能力。
- **PM 决策点**：知识是否频繁更新、能否检索、是否要求引用，以及召回、权限、时延和维护成本。
- **经历追问**：一次错误到底出在知识、切片、召回、排序、上下文还是生成层？
- **易错边界**：RAG 不等于向量库，也不能保证检索内容正确或生成严格忠于证据。

### Agentic RAG

- **一句话本质**：让检索链根据中间结果动态拆解、选源、重检索、调用工具或验证证据。
- **简明机制**：Agent 观察当前证据是否充分、一致和可用，再决定下一项检索或澄清动作。
- **相邻概念对比**：普通 RAG 执行相对固定链路；Agentic RAG 必须存在反馈驱动的路径变化。
- **PM 决策点**：复合查询是否值得增加规划、时延、成本、日志和失败治理。
- **经历追问**：哪个中间结果触发过换源、重检索、工具计算或向用户追问？
- **易错边界**：一次 Query Rewrite、固定多路召回或多个检索节点不自动等于 Agentic RAG。

### Workflow

- **一句话本质**：按预设节点、条件和顺序执行的相对确定性流程。
- **简明机制**：将模型、规则、检索、工具和人工节点编排起来，并显式管理输入输出与异常。
- **相邻概念对比**：Workflow 路径主要由设计者预先定义；Agent 通常拥有更动态的规划和工具选择。
- **PM 决策点**：任务是否稳定可拆、何处允许模型判断、何处必须规则化、失败如何恢复。
- **经历追问**：哪个节点需要 LLM，哪个应使用规则或人工，为什么？
- **易错边界**：在流程中放入多个 LLM 节点不自动等于 Agent。

### 数据契约（Data Contract / JSON Schema）

- **一句话本质**：对跨节点数据的字段、类型、必填性、来源、取值和校验作出的可检查约定。
- **简明机制**：上游按契约生产，下游按契约消费，系统对缺失、格式错误和版本变化显式处理。
- **相邻概念对比**：JSON 是一种数据格式；数据契约还包含语义、校验、责任和兼容规则。
- **PM 决策点**：哪些字段必须稳定、谁负责、失败如何降级、版本如何兼容。
- **经历追问**：拿一份真实输入说明第一个 JSON 如何形成，哪个字段因真实样本而修改？
- **易错边界**：Prompt 中展示一个 JSON 示例，不代表已建立可运行的数据契约。

### Agent

- **一句话本质**：围绕目标，利用模型进行规划或判断，并结合状态、工具和反馈循环完成任务的
  系统。
- **简明机制**：通常包含目标理解、计划/路由、工具行动、结果观察、状态更新与停止条件。
- **相邻概念对比**：聊天机器人可能只生成回复；Agent 强调行动闭环和任务状态。
- **PM 决策点**：是否真的需要自主性，权限、预算、最大轮次、人工确认和可观测性如何设计。
- **经历追问**：一次任务如何从输入走到完成，模型在哪些节点拥有选择权？
- **易错边界**：调用一次工具或套用 Agent 框架不等于形成可用的 Agent 产品。

### Tool / Function Call

- **一句话本质**：模型以结构化参数选择外部能力，由运行系统真正执行并返回结果。
- **简明机制**：系统向模型暴露工具描述和 Schema，模型提出调用，宿主校验权限与参数后执行。
- **相邻概念对比**：模型决定“想调用什么”；真实权限和执行结果由运行时系统控制。
- **PM 决策点**：工具可见范围、参数校验、确认、幂等、错误处理、审计和回滚。
- **经历追问**：模型选错工具、填错参数或重复写入时，你如何发现并处理？
- **易错边界**：模型输出一个调用意图不代表调用已成功，更不代表端到端任务完成。

### 状态机（State Machine）

- **一句话本质**：对业务对象允许的状态、合法动作、执行角色、前置条件和转换结果作出的确定性
  约束。
- **简明机制**：后端根据当前状态和权限校验动作，成功后更新状态并留下变化记录。
- **相邻概念对比**：对话状态描述“聊到哪里”；业务状态机决定“系统允许发生什么”。
- **PM 决策点**：非法转换、并发修改、重复提交、撤销与补偿如何处理。
- **经历追问**：谁能在什么状态执行哪个动作，模型误判时哪一层会拦住？
- **易错边界**：把状态写在 Prompt 或聊天历史里，不等于系统强制执行了状态机。

### 审计记录（Audit Record）

- **一句话本质**：为业务责任和过程还原保存每次关键查看或状态变化的主体、依据、时间和结果。
- **简明机制**：记录代表谁操作、确认内容、工具调用、旧值/新值、成功或失败原因。
- **相邻概念对比**：运行日志主要用于调试；审计记录面向责任、合规和业务过程。
- **PM 决策点**：哪些事件必须留痕、谁可查看、保存多久、如何关联模型与用户行为。
- **经历追问**：一次 Agent 发起、用户确认、系统写入分别留下什么记录？
- **易错边界**：只保存最终状态或一行错误日志，无法证明过程可审计。

### Skill

- **一句话本质**：为 Agent 封装某类任务方法、知识、步骤或工具使用规范的可复用能力单元。
- **简明机制**：Agent 根据任务加载适合的 Skill，再按其中的流程、边界和资源完成工作。
- **相邻概念对比**：Tool 偏向可执行接口；Skill 偏向“怎样完成一类任务”的方法与上下文组织。
- **PM 决策点**：触发条件、输入输出、职责边界、资源复用、冲突处理和质量验收。
- **经历追问**：为什么拆成这个 Skill，它与 Agent 和 Tool 各自负责什么？
- **易错边界**：不同生态对 Skill 的定义不同；面试时应先说明所处产品或框架语境。

### API

- **一句话本质**：不同软件系统按约定的请求、响应和认证方式交换能力或数据的接口。
- **简明机制**：调用方按地址、认证、参数和 Schema 发起请求，服务方返回状态、数据或错误。
- **相邻概念对比**：聊天界面是供人使用的产品；API 是系统集成接口；接通 API 不等于完成
  产品化。
- **PM 决策点**：契约、权限、限流、成本、错误、重试、版本、日志和数据安全。
- **经历追问**：模型响应经过什么后处理和校验，最后触发了哪个真实业务动作？
- **易错边界**：请求成功只证明连接可用，不证明回答质量、流程闭环或业务价值。

### MCP

- **一句话本质**：让 AI 应用以较统一方式发现和连接外部资源、工具与提示能力的协议。
- **简明机制**：客户端与 Server 按协议协商能力，并在身份和运行权限约束下读取资源或调用工具。
- **相邻概念对比**：普通 API 定义某项服务接口；MCP 进一步标准化 AI 应用发现和使用多种能力
  的方式。
- **PM 决策点**：是否需要多客户端/多工具复用，认证、权限、兼容、供应链与运行治理如何处理。
- **经历追问**：相比直接接 API，MCP 在你的项目中减少了什么成本，又新增了什么风险？
- **易错边界**：协议接通不代表任务完成；精确字段和版本行为应以当时官方规范为准。

### A2A

- **一句话本质**：面向独立 Agent 之间能力发现、任务协作和状态/产物交换的交互方式。
- **简明机制**：协作方描述能力，任务经历提交、执行、追问、完成、失败或取消，并返回消息或
  产物。
- **相邻概念对比**：Tool 通常是较确定的能力调用；Agent 可能拥有独立判断和长任务生命周期。
- **PM 决策点**：是否需要独立 Agent，任务状态、认证、超时、预算、冲突和降级如何管理。
- **经历追问**：为什么不用一个 Agent 或普通工具，拆分后获得了什么可验证增量？
- **易错边界**：协议和生态仍可能演进；具体能力、字段和兼容性必须结合版本说明。

## AI Coding 与软件交付

### AI Coding

- **一句话本质**：让模型或 Agent 参与理解、规划、修改、测试和交付软件的工作方式。
- **简明机制**：模型结合项目文件、指令和工具生成改动，运行环境负责执行，测试和人负责验证。
- **相邻概念对比**：代码生成只返回代码；AI Coding 可以覆盖项目环境中的多步开发活动。
- **PM 决策点**：哪些任务可交给 AI，规格、权限、验收和技术责任如何保留在人或团队。
- **经历追问**：你定义和验收了什么，Coding Agent、模板、平台和研发分别完成什么？
- **易错边界**：使用 AI 生成代码不等于独立研发或拥有全部技术成果。

### Coding Agent

- **一句话本质**：能读取软件项目、调用开发工具并迭代推进开发目标的 Agent。
- **简明机制**：观察代码与任务，规划修改，执行命令或测试，根据结果继续修正。
- **相邻概念对比**：智能编辑器可提供局部辅助；Coding Agent 更强调跨文件行动和目标推进。
- **PM 决策点**：环境权限、修改范围、上下文、版本隔离、失败停止和人工验收。
- **经历追问**：Agent 做错过什么，你用什么外部证据发现并回退？
- **易错边界**：Agent 自称完成不等于功能或业务验收通过。

### Agent Harness

- **一句话本质**：让模型能够在受控环境中持续行动的一组上下文、工具、状态、验证和治理机制。
- **简明机制**：保存目标与进度，暴露有限工具和权限，用测试、审计、回退和人工判断闭环行动。
- **相邻概念对比**：模型提供推理与生成能力；Harness 决定它能看见什么、做什么和怎样被校验。
- **PM 决策点**：长任务连续性、工具契约、权限、可观测性、成本和接管条件。
- **经历追问**：换成相同模型但移除项目规则、进度或测试后，哪类失败会增加？
- **易错边界**：不能把 Agent 效果完全归因于模型版本。

### Vibe Coding / Spec Coding

- **一句话本质**：前者以自然语言快速探索；后者先明确规格、方案、任务和验收再实施。
- **简明机制**：Spec Coding 把需求变成可检查的阶段，并连接实现、测试、人工验收和版本记录。
- **相邻概念对比**：两者不是工具名称，也不是绝对优劣；探索和高风险交付需要不同约束。
- **PM 决策点**：需求不确定性、错误代价、协作人数、维护周期和合规要求。
- **经历追问**：哪条规格因真实验收而修改，哪些非目标防止了范围漂移？
- **易错边界**：文档完整不等于需求正确，也不等于生产交付。

### E2E 测试

- **一句话本质**：从用户入口模拟完整业务主链路并检查最终结果的端到端测试。
- **简明机制**：跨越前端、接口、后端和数据等模块执行真实步骤，验证关键结果。
- **相邻概念对比**：单元测试定位局部；集成测试验证模块连接；E2E 最接近用户但定位更慢。
- **PM 决策点**：哪些主链路和高错误代价路径必须覆盖，如何与其他测试和人工验收组合。
- **经历追问**：说出一条 E2E 的输入、步骤、预期、实际失败和修复。
- **易错边界**：E2E 通过不代表权限、安全、性能和所有边界条件都已验证。

### CI/CD

- **一句话本质**：代码变化后自动执行检查、构建和部署的持续集成与交付机制。
- **简明机制**：提交触发测试和构建，通过后进入目标环境，失败则阻止或告警。
- **相邻概念对比**：CD 自动化发布动作；生产治理还包括环境、监控、回滚、安全和责任。
- **PM 决策点**：准入检查、环境、发布权限、失败阻断、回滚和通知。
- **经历追问**：哪些检查会阻止发布，谁决定例外和回滚？
- **易错边界**：自动部署成功不等于生产质量或业务上线成功。

### 生产运行

- **一句话本质**：产品在真实用户、数据和责任约束下持续提供服务的状态。
- **简明机制**：除部署外，还需要权限、监控、告警、故障处理、恢复、合规和持续运营。
- **相邻概念对比**：本地可运行、可分享部署、Demo、MVP、试点和生产运行是不同成熟度。
- **PM 决策点**：准入、用户范围、数据风险、服务目标、监控、回滚和业务结果。
- **经历追问**：谁持续使用、运行多久、发生过什么故障、如何发现和恢复？
- **易错边界**：公网链接、测试账号或名为 production 的部署环境不能单独证明生产运行。

## 训练与对齐

### Pretraining（预训练）

- **一句话本质**：在大规模通用或领域数据上学习基础表示和生成能力的训练阶段。
- **简明机制**：常通过自监督目标学习语言或多模态规律，成本和数据规模通常较高。
- **相邻概念对比**：预训练建立底座能力；微调在已有模型上适配更具体任务或行为。
- **PM 决策点**：是否真的需要自建底座，数据、算力、周期、许可和长期维护是否成立。
- **经历追问**：项目为何不能使用现有基座模型，预训练目标与产品价值如何对应？
- **易错边界**：领域继续预训练、SFT 和从零预训练不是同一件事。

### Fine-tuning（微调）

- **一句话本质**：在已有模型基础上，用特定数据继续训练以适配任务、领域或行为。
- **简明机制**：更新全部或部分参数，使模型在目标数据分布上的输出发生稳定变化。
- **相邻概念对比**：RAG 在推理时补知识；微调改变模型行为，两者可组合而非必然互斥。
- **PM 决策点**：目标是否稳定、数据是否足够可信、收益是否覆盖训练和回归成本。
- **经历追问**：你希望微调改变什么，独立测试怎样证明变化可泛化？
- **易错边界**：微调不适合单纯固化频繁更新事实，也不保证自动消除幻觉。

### SFT（监督微调）

- **一句话本质**：用带有期望输入—输出示例的数据对模型进行监督训练。
- **简明机制**：模型学习在给定输入下更接近示范答案或行为格式。
- **相邻概念对比**：SFT 学习示范；偏好优化利用“哪个回答更好”的比较信号。
- **PM 决策点**：示范标准、标注一致性、场景覆盖、数据泄漏和回归风险。
- **经历追问**：高质量示范由谁定义，标注分歧和错误样本如何处理？
- **易错边界**：示范数量不能替代质量与覆盖；固定数据量不是通用成功门槛。

### LoRA

- **一句话本质**：冻结大部分原模型参数，用低秩适配参数实现较低成本微调的方法。
- **简明机制**：在部分权重变化上学习低秩增量，训练和存储开销通常低于全量微调。
- **相邻概念对比**：LoRA 是参数高效微调方法；SFT 是训练信号/阶段，两者可以同时出现。
- **PM 决策点**：资源约束、效果目标、部署合并、多个适配器管理和版本治理。
- **经历追问**：为什么选择 LoRA，和不训练或全量微调相比验证了哪些取舍？
- **易错边界**：LoRA 不等于“小模型”，也不天然保证效果、稳定性或无回归。

### RLHF

- **一句话本质**：利用人类偏好信号和强化学习，让模型行为更符合期望的对齐方法族。
- **简明机制**：经典流程可包含偏好数据、奖励模型和基于奖励的策略优化，具体实现会变化。
- **相邻概念对比**：SFT 学示范答案；RLHF 更关注偏好与行为优化。
- **PM 决策点**：偏好标准、标注成本、奖励投机、安全副作用和评测设计。
- **经历追问**：偏好由谁定义，模型是否只优化了代理指标而损害真实体验？
- **易错边界**：不能把所有偏好训练都统称为同一套 RLHF 流程。

### DPO

- **一句话本质**：直接利用成对偏好数据优化模型更偏向优选回答的对齐方法。
- **简明机制**：通过优选/劣选回答的相对目标进行训练，通常不需要显式训练奖励模型并运行
  标准强化学习循环。
- **相邻概念对比**：与经典 RLHF 目标相近但训练路径更直接；仍依赖可靠偏好数据。
- **PM 决策点**：偏好对质量、覆盖、冲突、计算成本和行为回归。
- **经历追问**：偏好对如何产生，哪些行为改善、哪些能力可能退化？
- **易错边界**：不要把 DPO 简化称为“标准强化学习”；具体实现需结合项目说明。

### Overfitting / Generalization（过拟合与泛化）

- **一句话本质**：过拟合是模型过度贴合训练样本；泛化是面对未见但相关输入仍能有效工作。
- **简明机制**：数据单一、泄漏、训练过度或评测相似都可能制造虚假的高分。
- **相邻概念对比**：记住训练样本不等于学会可迁移规律；离线高分不等于线上泛化。
- **PM 决策点**：独立切分、场景外测试、重复运行、回归集和上线监控。
- **经历追问**：哪些测试能证明模型不是只会训练集模板？
- **易错边界**：一次验证集结果不能充分证明泛化，训练/测试污染会让指标失真。

## 评测指标

### Confidence 校准

- **一句话本质**：用独立标准答案检验模型或系统给出的置信分数与实际正确率是否匹配。
- **简明机制**：将样本按分数或等级分桶，比较每桶实际正确率，再据错误代价设置分流阈值。
- **相邻概念对比**：模型自报 Confidence、检索相似度和答案正确概率不是同一个量。
- **PM 决策点**：自动放行、拒答和人工复核怎样平衡漏错与人工工作量。
- **经历追问**：`high` 桶实际正确率是多少，谁标注，阈值变化会造成什么业务后果？
- **易错边界**：没有独立标注和分桶验证时，Confidence 只能作为调试信号。

### Accuracy（准确率）

- **一句话本质**：全部样本中预测正确的比例。
- **简明机制**：正确数除以总样本数，直观但对类别极不均衡问题可能误导。
- **相邻概念对比**：Precision 关注预测为正的结果有多准；Recall 关注实际为正的样本找回多少。
- **PM 决策点**：错误成本是否对称、类别分布是否均衡、是否需要分场景看指标。
- **经历追问**：你定义的“正确”是什么，错一次的业务代价是否都一样？
- **易错边界**：生成式任务常无法仅用 Accuracy 覆盖质量。

### Precision（精确率）

- **一句话本质**：被模型判为正的结果中，真正为正的比例。
- **简明机制**：TP / (TP + FP)，强调减少误报。
- **相邻概念对比**：Recall 强调减少漏报；两者经常需要取舍。
- **PM 决策点**：误报代价高的审核、风控或推荐场景是否应更重 Precision。
- **经历追问**：误报会触发什么下游动作，阈值变化如何影响用户和业务？
- **易错边界**：Precision 高不代表覆盖充分，可能以大量漏报为代价。

### Recall（召回率）

- **一句话本质**：实际为正的样本中，被模型成功找到的比例。
- **简明机制**：TP / (TP + FN)，强调减少漏报。
- **相邻概念对比**：检索系统中的 Recall 也表示相关内容被召回的覆盖程度，需说明具体口径。
- **PM 决策点**：漏掉一个目标的代价、候选集大小、后续重排和人工处理能力。
- **经历追问**：你们最不能漏掉什么，提升 Recall 后带来了多少噪声？
- **易错边界**：Recall 高不代表结果都相关，不能脱离 Precision 和下游容量解释。

### F1

- **一句话本质**：Precision 和 Recall 的调和平均，用于同时关注误报与漏报。
- **简明机制**：当两者任一较低时 F1 会明显受限。
- **相邻概念对比**：F1 默认两者同等重要；真实业务可能需要不同权重或成本函数。
- **PM 决策点**：业务是否真的同等看待误报和漏报，是否应分场景或使用其他指标。
- **经历追问**：为什么选 F1，它与真实损失或产品指标如何连接？
- **易错边界**：单个 F1 会掩盖类别、场景和高风险样本差异。

### 产品与业务指标

- **一句话本质**：衡量 AI 是否帮助用户完成任务并产生业务价值，而非只看模型输出。
- **简明机制**：可结合任务完成率、采纳率、编辑距离/修改率、重试率、人工接管率、时延、
  成本、留存或业务转化。
- **相邻概念对比**：模型指标解释能力表现；产品指标解释使用效果；业务指标解释最终价值。
- **PM 决策点**：建立“模型变化—用户行为—业务结果”链路，并设置安全护栏。
- **经历追问**：用户采纳后是否真的完成任务，重试、修改和人工接管说明了什么？
- **易错边界**：采纳不一定代表正确，编辑距离低也不一定代表业务质量高；必须结合场景。

## 项目验证与上线

### PoC（概念验证）

- **一句话本质**：用最小实验验证关键技术或业务假设是否可能成立。
- **简明机制**：聚焦最高风险假设，用受控样本、原型或最小链路获得证据。
- **相邻概念对比**：PoC 验证“能不能”；MVP 验证最小完整产品是否有人用、能否运行。
- **PM 决策点**：最关键假设、通过/停止标准、样本代表性和下一阶段决策。
- **经历追问**：PoC 验证了哪个不确定性，哪些产品与工程问题仍未验证？
- **易错边界**：Demo 成功不等于生产可用，也不等于用户价值已成立。

### MVP

- **一句话本质**：包含最小价值闭环、可供真实目标用户使用和反馈的产品版本。
- **简明机制**：以最少范围覆盖核心任务、基本交互、必要异常处理和测量机制。
- **相邻概念对比**：原型主要表达方案；MVP 要承载真实使用和验证。
- **PM 决策点**：核心人群、最小闭环、不可缺失的安全/降级和成功指标。
- **经历追问**：哪些能力被刻意砍掉，真实用户反馈改变了什么判断？
- **易错边界**：MVP 不是粗糙功能合集，AI MVP 也必须说明不可用边界。

### Golden Test Set（黄金评测集）

- **一句话本质**：经明确标准确认、用于稳定比较版本质量的一组代表性高可信样本。
- **简明机制**：覆盖核心、长尾和风险场景，带期望结果或评分标准，并随错误发现受控更新。
- **相邻概念对比**：普通测试集可能一次性使用；黄金集强调质量、代表性、版本和回归价值。
- **PM 决策点**：样本来源、专家标准、分层覆盖、污染防止和更新审批。
- **经历追问**：谁定义金标准，新增 Bad Case 如何进入评测集而不污染当前结论？
- **易错边界**：黄金集不是只挑“标准题”；公开给训练流程后需警惕测试泄漏。

### Bad Case

- **一句话本质**：能够暴露系统失败模式、用户损失或产品边界的具体错误样本。
- **简明机制**：收集后按场景与链路分类，排序影响，定位根因，修复并加入回归。
- **相邻概念对比**：单个投诉是信号；Bad Case 管理要形成可复现、可归因的错误闭环。
- **PM 决策点**：按频率、严重度、可修复性和业务风险排序，选择正确修复层。
- **经历追问**：讲一个错误从发现、分类、归因、修复到回归验证的完整过程。
- **易错边界**：为单一样本改 Prompt 可能造成其他场景回归，不能只展示修复后的好案例。

### Gray Release / Rollback（灰度与回滚）

- **一句话本质**：先让有限流量或用户使用新版本，并在风险出现时恢复到稳定方案。
- **简明机制**：按人群、流量、场景或版本逐步放量，监控核心指标和护栏，触发停止或回退。
- **相邻概念对比**：离线评测控制输入；灰度验证真实环境；A/B 更强调可比较的因果实验。
- **PM 决策点**：分流单位、监控指标、停止条件、版本兼容、数据和用户影响。
- **经历追问**：灰度期间什么信号会让你暂停，回滚后怎样处理已产生的状态或错误？
- **易错边界**：固定灰度比例和阈值不是通用标准，应由风险与业务条件决定。

## 通用边界

- 概念定义用于帮助表达，不替代项目证据；用户没有做过的机制不能因“懂术语”写入经历。
- 涉及模型版本、价格、上下文长度、协议字段、平台能力和监管要求时，优先使用项目当时证据或
  最新官方来源，不把本词典当实时规格表。
- 术语存在多种行业口径时，先说明本次语境；Skill、Agent、记忆、准确率等尤其需要界定。
- 面试回答应结论先行、机制够用、取舍落地。除非岗位要求算法推导，不用堆公式证明“技术感”。
