# Agent / Skill 类 AI 产品经历深挖

本参考只在经历真实涉及 Agent、Skill、工具调用、工作流编排、多智能体或任务路由时加载。
它是 `../role-playbooks/ai-product.md` 和 `ai-technology-application.md` 的条件视角，不是固定
题库；每轮只选择会改变产品判断或个人贡献判断的一个关键缺口。

## 1. 任务价值与形态选择

查明目标用户原本要完成什么任务、原链路的失败或成本，以及为什么选择 Agent + Skill、工作流
或多智能体，而不是单次 Prompt、固定规则、普通自动化、搜索或人工流程。确认需要的是开放式
规划、专业方法复用、工具执行、动态路由还是多步骤状态管理，不能用“更智能”代替选择依据。

先用控制权与失败代价判断形态：

- 步骤和分支可以预定义时，为什么不使用确定性 Workflow；
- 人掌握关键动作、AI 只提供建议时，为什么不是 Copilot；
- 下一步必须根据环境动态判断时，Agent 获得了多大自主权；
- 自主判断失败会造成什么影响，沙盒、审批、降级或人工接管如何约束；
- 主流程固定、局部开放时，为什么采用 Workflow + Agent 混合。

还要确认它面对的是一个**可重复任务族**，而不是被包装成产品的一次性需求：

- 相似任务出现的频率、覆盖的用户范围和变化程度；
- 哪些输入、判断、流程与交付可以稳定复用，哪些必须逐案处理；
- 从单次 Prompt 升级后，实际减少了多少重复配置、人工操作、返工或质量波动；
- 新增的触发、版本管理和维护成本是否值得。

用至少一个真实案例建立 **Prompt 失效证据链**：是否反复补充相同要求、换主题或上下文后
跑偏、遗漏关键步骤、不知道何时调用工具、输出格式漂移，或完成后仍需大量返工。不能只用
“Prompt 不稳定”或“以后可能复用”证明产品化成立。

继续检查**任务颗粒度与 MVP 范围**：最初的宽泛任务如何按用户、输入、判断、输出和完成标准
拆分，为什么首版选择当前最小闭环，主动砍掉了什么；如果拆成多个 Skill，如何避免职责重叠、
路由冲突和过度碎片化。不能只用“范围小”证明颗粒度合理，还要有真实使用、稳定交接或迭代
成本证据。

完成标准：能说明哪类任务复杂性要求这种产品形态、可重复任务族和可复用单元是什么、何时
值得产品化，首版为何选择当前颗粒度，以及更简单方案为什么不足或其实更合适。

## 2. 端到端运行链路

按真实系统还原：

`用户请求 → 任务/意图识别 → Skill/流程路由 → 指令与上下文加载 → 规划和执行 → 模型/工具调用
→ 状态或记忆更新 → 结果检查 → 用户交付`

只保留实际存在的环节，并追问关键输入输出、状态、上下游接口、异常分支和人工介入。框架名称、
演示视频或流程图不能替代真实运行机制。

完成标准：能解释一个真实请求如何穿过系统、在哪些节点发生判断，以及本人负责哪些节点。

## 3. 路由、触发与职责边界

确认系统如何判断任务类型、选择 Skill 或流程，以及触发契约是否明确：

- 哪些用户表达、输入条件或上下文应触发；
- 输出目标和不负责的事项是什么；
- 多个 Skill 同时匹配时如何排序、组合或澄清；
- 误触发、漏触发、路由置信度不足时如何发现和降级；
- 路由规则来自描述、分类器、模型判断、规则还是混合方案，为什么如此选择。

当系统依赖名称、描述等元数据选 Skill 时，把元数据当作**产品入口**继续深挖：它如何表达目标
用户、输入、输出、适用与排除场景；与相似 Skill 如何消歧；描述过宽或过窄造成过哪些误触发、
漏触发；修改后如何验证。不能把元数据只当成命名或文案工作。

完成标准：至少有一个真实路由决策、失败案例或验证证据，不能只说“Agent 会自动判断”。

## 4. Skill 产品设计

先用**判断—执行—交付三段契约**还原用户所称的 Skill：

- **判断**：执行前需要识别哪些对象、条件和约束，不同判断如何改变后续路径；
- **执行**：包含哪些步骤、输入输出、分支与失败处理；
- **交付**：输出采用什么 schema、哪些字段必填、信息缺失时如何处理、由谁继续消费。

再拆成四类可验证设计，追问其真实存在和本人贡献：

1. **职责边界**：负责什么、不负责什么、何时转交；
2. **执行流程**：步骤、分支、材料不足处理、停止和重试条件；
3. **专家判断**：普通 Prompt 不具备的领域规则、取舍原则或经验；
4. **质量检查**：输出格式、事实/安全/业务标准和交付门槛。

对“专家判断”至少选一项完成**隐性经验显性化**：查明经验来自谁和哪些真实案例，如何转成
条件、优先级、反例或例外，Agent 是否真的按它执行，以及哪些判断仍无法标准化、必须留给人工。

对于复杂 Skill，还要继续追问资源为何这样分层：

- **主指令 / SKILL**：承载判断、流程与质量约束；
- **脚本**：承载可重复、确定性强、需要精确执行的动作；
- **参考资料 / 知识库**：承载会更新的事实、规范与领域知识；
- **资产 / 模板**：承载可直接复用的交付物骨架。

根据确定性、更新频率、上下文成本、复用范围和维护责任判断分层是否合理，并追问问题发生后
能否定位到对应层。不要为了“架构完整”强迫轻量 Skill 配齐所有资源。

继续还原**渐进式加载契约**：哪些轻量信息始终用于发现，哪些主指令只在命中后加载，哪些参考
资料、脚本或模板只在具体分支按需使用；为什么这样安排，以及如何避免无关内容挤占上下文、
干扰判断或增加时延。只讲“三层加载”概念而没有真实加载路径不算完成。

完成标准：Skill 不是静态说明、长 Prompt 或工具列表；能讲清判断—执行—交付三段契约、至少
一项由用户定义并经验证的专业方法或质量约束，以及复杂 Skill 的资源分层取舍。

## 5. 模型、Agent、Skill 与工具分工

区分各层真实职责：

- 模型负责理解、生成、推理、分类或规划中的什么；
- Agent 负责怎样的调度、状态管理、循环与收敛；
- Skill 提供怎样的任务方法、专业知识、流程和质量标准；
- 工具执行了哪些检索、读写、计算、调用或外部操作；
- 产品经理本人定义了哪些需求、边界、策略、交互、评测、验收或推进动作。

若候选人借助 Skill Creator、模型或其他 AI 生成过 Skill，必须做**AI 辅助创建归属**拆分：
哪些用户、场景、判断、流程、边界和质量标准由本人或领域专家定义；哪些只是生成器提供的通用
骨架；本人如何审查、修改和用测试结果迭代。仅提交自动生成文件不能证明完成了 Skill 产品设计。

只有经历真实涉及工具调用时，才继续检查**工具选择策略**：什么条件下选择哪个工具，输入输出
和权限如何约束，失败时如何重试、降级或转人工，以及调用是否真正提升任务完成度。没有工具
调用时跳过，不为了体现技术复杂度强行追问。

涉及 MCP、API、本地脚本或外部系统时，再检查**指导与执行边界**：哪些专业方法和行为约束
属于 Skill，哪些真实查询、写入或状态变更必须由工具执行；为何选择现成工具、自建接口或脚本；
授权、数据范围和副作用如何控制。重点查找“Skill 会指导但无法执行”或“工具能执行但缺少业务
判断”的断层，不预设 Skill 或工具哪一方天然更安全。

完成标准：不能把“能调用工具”当成 Agent 产品价值，也不能把模型、平台或研发实现冒认为本人
产品贡献。

## 6. 多 Skill / 多 Agent 编排与交接

存在多个 Skill 或 Agent 时，查明为什么拆分、各自职责、依赖或并行关系，以及中间产物、进入
条件、共享上下文和状态如何传递。追问冲突、循环、上下文污染、部分失败、超时、重试、回滚、
人工接管和最终收敛机制。

交接物本身也要作为产品接口深挖：输出 schema 是什么，哪些字段必填或可选，缺失与冲突如何
表达，版本如何兼容，由哪个下游直接消费。若下游仍需人工复制、重排或猜测含义，说明交付
接口还不稳定。

完成标准：能用一个真实任务解释编排图，说明拆分相比单一 Agent 的收益、额外成本和边界，
并举出至少一次下游直接消费稳定交付接口的证据。

## 7. 多角色内容生成的质量闭环

经历涉及 Planner、Writer、Reviewer 或其他生成角色时，先判断为何需要拆分，而不是用角色数量
证明系统更高级：

- Planner 是否产生可执行计划、依赖关系、顺序、必需输入和信息缺口；
- Writer 是否只消费约定上下文，并对无来源事实显式标记待补充；
- Reviewer 是否使用可定位、可验证、可修改的质量标准，而非“更专业、更深入”等主观意见；
- 每个角色是否有独立输入输出、工具/权限、单模块基线和失败处理；
- 结构化交接是否能被下游直接消费，Schema 变化如何兼容。

审核问题应区分阻塞与非阻塞：事实缺失、证据冲突、结构不完整等可阻塞；风格偏好通常只提示。
循环必须有局部修改范围、重试预算、停止条件和人工出口，不能让 Writer 与 Reviewer 无限互相
重写。长任务还应说明阶段产物、检查点、失败续跑和重复执行保护。

完成标准：能用一个真实失败说明多角色拆分解决了什么，展示一份稳定交接物和一条 Reviewer
反馈如何变成可验证修改；没有对照时，不把多角色架构本身写成质量提升证据。

## 8. 质量评测与“真的完成”

区分流程执行成功与用户任务真正完成，先建立四层验证矩阵：

1. **触发与路由正确性**：该触发时是否命中，不该触发时是否避开，模糊请求如何处理；
2. **流程遵循度**：关键步骤、分支、工具调用、检查点和停止条件是否按设计执行；
3. **输出契约稳定性**：schema、必填字段、格式、证据与缺失信息行为是否稳定；
4. **真实任务泛化**：面对新用户、长尾输入、环境变化和真实上下游时是否仍能完成任务。

先按证据判断**成熟度与证据阶梯**，不要由候选人自行命名为“上线”：

1. **概念**：识别问题和目标任务；
2. **草稿**：具备场景、流程、输出和质量标准；
3. **可用原型**：经过真实任务测试和人工修改；
4. **稳定能力**：触发、流程、输出和泛化得到系统验证；
5. **规模化应用**：进入真实上下游，并有版本、监控、反馈和持续迭代。

只认可已有证据对应的层级；单次 Demo、教学示例或一份生成的 `SKILL.md` 不等于稳定能力，
更不等于规模化上线。

尽量建立 **Prompt 与 Skill 的同任务基线**：使用同一类代表性任务和可比输入，比较升级前后
的遗漏、重复沟通、输出漂移、返工、耗时与成本。若模型版本、输入材料、人工介入或环境同时
变化，要说明归因边界，不能把所有改善都归功于 Skill。

如果采用按需加载，还要检查实际运行证据：是否读取了无关资源、关键资料是否及时加载、脚本
是否按预期执行，以及加载策略对上下文占用、时延、成功率和上下文污染的影响。平台无法提供
精确 Token 或加载轨迹时，可以使用任务日志、失败案例和对照实验，不编造精确数字。

再按真实产品选择指标：

- 意图/任务分类与路由的正确性；
- Skill 选择、工具调用和步骤执行成功率；
- 输出事实性、完整性、格式、安全与专业质量；
- 用户是否需要大量返工、任务是否可直接交付；
- 端到端完成率、人工接管率、时延、成本和稳定性；
- 关键失败类型、评测样本、基线、护栏和归因边界。

完成标准：不能只用“运行成功”“用户觉得不错”或单个演示案例证明质量；必须解释如何拦截
“看起来完成、实际不可用”的结果，指出四层中最薄弱的一层，并区分“没有选对能力”和
“选对后没有执行好”。

## 9. 反馈回流与持续优化

从真实失败或下游反馈判断问题位于任务识别、路由、Skill 指令、上下文、模型、工具、编排还是
质量标准，再说明如何修改上游设计并重新验证。只做措辞润色而不修根因不算有效迭代。

完成标准：至少有一个“结果暴露问题 → 定位层级 → 修改设计 → 重新验证”的闭环；没有真实
迭代时如实记录计划和待验证项。

## 10. Harness 与生产控制面

当候选人声称搭建了可用 Agent，而不只是调用现成平台时，继续还原模型之外的控制系统：

- **主循环**：接收任务、观察状态、规划、调用工具、检查结果和停止；
- **状态容器**：当前计划、已完成步骤、未决问题、中间产物和恢复点；
- **工具管理**：全量注册、模型可见集合和运行权限是否分离；
- **权限事件**：拒绝、请求授权和用户确认是否结构化、可审计；
- **上下文管理**：核心约束、工作信息、历史摘要和大型工具输出如何分层；
- **压缩与恢复**：上下文缩减或任务中断后如何继续；
- **失败处理**：超时、工具不可用、权限拒绝、循环失控和部分成功如何收敛；
- **扩展边界**：新增 Skill、工具、Hook 或模型时是否破坏既有能力。

要求至少用一个真实任务说明这些组件如何协作，并区分模型能力提升与 Harness 改进带来的效果。
若经历只是在平台内配置 Agent，不要求候选人冒认底层 Harness；改为追问其可配置的路由、状态、
权限、评测和异常体验。

同时检查“写—跑—看—修”是否形成外部验证闭环：凡是可执行、可查询或可校验的产物，Agent
是否真正运行并检查结果，而不是一次生成后自行宣称完成。高风险动作必须在权限与隔离环境内
执行。

当 Agent 查询私有业务数据或改变外部对象状态时，继续读取 `ai-action-agent-products.md`，
不要只在 Harness 层泛问权限和日志；必须落到真实业务对象、状态机、执行前确认、幂等/恢复和
业务审计。

## 11. 追问优先级与边界

优先追问：

1. 会影响“为什么需要 Agent / Skill”判断的形态选择；
2. 用户刚提到但没有说明机制的路由、编排或质量动作；
3. 能区分本人产品判断与团队实现的交付和权限；
4. 会推翻成功结论的失败案例、评测口径或不可用结果；
5. 能形成决策、冲突、协作、失败或重来改进故事的真实事件。

避免进行框架名词考试，不要求用户复述 Agent 概念。仅使用 ChatGPT、Prompt 或通用 AI 工具
辅助写作、整理和分析，不等于做过 Agent / Skill 产品；此时回到通用 AI 产品或普通产品流程。
