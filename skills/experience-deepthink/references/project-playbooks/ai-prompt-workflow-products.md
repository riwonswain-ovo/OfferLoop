# Prompt / Workflow 类 AI 产品经历深挖

本参考在经历真实涉及 Prompt 系统化设计、LLM 节点、固定流程编排、Dify/Coze 工作流或从
一次性生成升级为稳定流程时加载。普通使用 ChatGPT 写作不触发。重点验证失败驱动的迭代、
确定性与概率性步骤分工，以及从 Demo 到生产的能力。

## 1. Prompt 不是一句文案

先从一次真实失败开始：缺少背景、目标不清、格式漂移、事实编造、边界失守还是跨样本不稳定？
再还原 Prompt 中真实存在的：

- 角色与任务；
- 必要上下文和参考资料；
- 适用范围、禁止事项和不确定时行为；
- 输出 Schema、字段类型、缺失值与边界情况；
- Few-shot 或反例为何被加入。

不要因为候选人使用了 RTF、CoT 等名称就判断其能力；必须说明某项设计修复了什么问题。

## 2. Prompt 资产化闭环

确认 Prompt 是否被当作可维护产品资产：

`失败样本 → 根因假设 → 单变量修改 → 测试集回归 → 指标/人工评审 → 版本记录 → 灰度 → 回滚`

继续追问变量模板、版本负责人、变更原因、代表性测试集、模型升级回归和线上反馈。多处同时修改
时保留归因限制；迭代次数本身不证明质量。

## 3. Workflow 与 Agent 的边界

根据控制权判断产品形态：

- 步骤、分支和结果可预定义时，优先固定 Workflow；
- 人掌握关键控制、AI 只提供建议时，更接近 Copilot；
- 只有下一步必须根据环境动态判断时，才把局部交给 Agent；
- 主流程固定、局部开放时，允许 Workflow + Agent 混合。

追问为什么某一步需要模型、某一步使用规则或代码，以及自主性增加后引入了什么风险和治理成本。

## 4. Workflow 运行与状态

按真实流程还原：

`输入与校验 → 数据/知识准备 → 模型节点 → 条件分支 → 工具或业务节点 → 结果校验 → 交付`

确认节点输入输出、变量传递、分支条件、循环与停止、状态保存和人工节点。重点寻找：

- 分类错误进入错误分支；
- 空检索或上游字段缺失；
- 模型输出不符合下游 Schema；
- 节点超时、重复执行或部分成功；
- 下游仍需人工复制和重排。

## 5. 概率生成与确定校验

让模型承担开放理解和生成，让规则、代码或人工承担可确定验证。只有实际存在时才追问：

- 输入过滤和材料完整性检查；
- JSON Schema、字段范围和业务规则校验；
- 工具调用前的权限与参数检查；
- 生成后的事实、安全、格式或合规检查；
- 失败后的自动修复、重试、降级或人工接管。

不能把写在 System Prompt 中的约束等同于已经实现安全防护。

## 6. 产品化与评测

从“能跑通”继续追到：

- 基线任务和代表性/边界/失败用例；
- 节点级与端到端成功率；
- 多次运行稳定性、人工返工和任务完成度；
- 时延、Token、模型与工具成本；
- 超时、重试、幂等、限流、告警和降级；
- Prompt 与流程版本、灰度和回滚。

完成标准必须由外部结果或验收规则判断，不能仅由模型输出“已完成”。

## 7. 追问选择

优先追问一次真实失败对应的机制和修复、一次 Workflow/Agent 边界选择、一次可复现评测，或一次
上线异常治理。用户只搭建了教学 Demo 时，如实定位为原型，不把课程示例、预计节省或配置参数
写成真实产品结果。
