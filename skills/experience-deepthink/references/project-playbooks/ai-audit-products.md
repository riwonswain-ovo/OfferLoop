# AI 审核 / 风控 / 质检产品经历深挖

本参考只在经历真实涉及合同审查、内容审核、风控、质量检查、合规判断、材料预审或其他
“依据标准发现问题并给出结论”的 AI 产品时加载。它补充 AI 产品通用路线，不把普通问答、
信息整理或主观创意评价强行归为审核。

若经历是纯规则、关键词或正则审核，但用户仍要深挖该产品，可复用“审核五问、规则来源、
证据、错误代价和人工复核”，同时不得加载 AI 技术链或把它改写成 AI 项目。

每轮只追一个最能改变项目真实性、方案有效性或个人贡献判断的缺口。

## 目录

1. 审核五问
2. 首个真实样本与数据契约
3. 规则体系与技术路由

6. 失败模式与追问优先级

## 1. 审核五问

先回答：

1. **审什么**：对象是合同、图纸、图片、文本、表单还是跨文档组合，实际格式和最小判断
   粒度是什么；
2. **谁来审**：现有角色、职责、权限、工作量和协作关系是什么；
3. **依据什么审**：法规、企业制度、行业标准、历史案例或专家经验分别来自哪里；
4. **审出什么**：通过/不通过、风险等级、问题清单、证据、建议或待人工判断如何表达；
5. **审错了怎么办**：漏检、误检和无法判断分别造成什么后果，谁承担最终责任。

第五问决定召回与精确的取舍、人工复核范围、输出分级和上线护栏。不能只问“准确率多少”，
必须先确认不同错误是否等价。

完成标准：五问都能落到真实业务对象、角色和错误后果，不能只用行业常识或课程模板回答。

## 2. 首个真实样本与数据契约

在功能列表或架构图之前，要求候选人拿一份其实际处理过的输入，还原**第一个结构化样本**：

- 原材料中的实体、字段、单位、位置和缺失状态；
- 哪些字段必填、可空、多值或需要人工确认；
- 每个字段由解析、规则、模型、用户还是外部系统产生；
- 下游哪个节点消费，格式或校验失败时如何处理；
- 真实样本出现后，Schema 改过什么、为什么改。

“输出 JSON”不等于数据契约。稳定契约还要说明字段类型、取值、来源、版本、校验和兼容。
没有真实样本时可把设计记录为方案，但不能冒认已完成数据建模或联调。

## 3. 规则体系与技术路由

按强制性和判断性质区分：

- **硬规则**：有明确条件、公式或禁止项，优先由程序、规则引擎或结构化查询执行；
- **软规则**：存在灰度和风险提示，需要说明判断 Rubric、例外和复核方式；
- **经验规则**：来自专家隐性经验或历史案例，必须保留来源、适用范围和待验证状态。

每条规则至少追到：

`规则 ID / 描述 → 来源与版本 → 所需字段或证据 → 判断方式 → 输出 → 例外 → 最终解释人`

法规不是全部规则；企业制度和专家经验也可能构成依据。反过来，没有可靠来源的启发式不能被
包装成权威规则。确定性计算不要交给 LLM；语义判断也不能只靠一句 Prompt 而没有校验。

## 4. 规则—证据—判断—复核链

把以下对象分开：

1. 规则：当时有效的标准及其版本；
2. 证据：未经模型改写的原文、字段、图片区域或外部数据；
3. 映射：这条规则需要什么证据，实际证据位于哪里；
4. 判断：通过、不通过、存疑及解释；
5. 复核：谁确认、修改了什么、为什么。

审核结果不能只给结论。至少应能随机抽一条结论，回到原始证据和当时规则版本。若验证 AI
结果仍需人工重新翻完整材料，产品的效率价值尚未成立。

按真实链路定位错误：

`输入 → 解析 → 字段提取 → 规则/知识获取 → 判断 → 输出 → 人工复核`

不要把解析错、漏召回、规则错和模型判断错统一归为“幻觉”或“Prompt 不好”。

## 5. 评测、Confidence 与人工分流

先由错误代价确定指标和分流，再设置目标值。至少确认：

- 标准答案由谁、依据什么产生，争议如何处理；
- 测试集是否覆盖正常、长尾、冲突、缺字段和高风险样本；
- Precision、Recall 或其他指标对应哪种真实损失；
- 严重错误是否设为阻塞项，避免被平均分掩盖；
- 哪类结论自动通过、抽检、强制复核或直接拒绝。

模型自报 `high / medium / low` 或一个小数，不等于已校准概率。若项目使用 Confidence 驱动
放行或复核，继续追问各分桶的实际正确率、标注来源、阈值变化对漏检和人工量的影响。没有
独立标准答案时，只能把 Confidence 当调试信号，不能当可靠性证据。

人工复核也不是一句“人工兜底”。确认复核人、触发条件、操作界面、修改记录、版本更新审批、
回归测试和回滚。未经治理的用户反馈不能直接进入规则库、知识库或训练集。

## 6. 失败模式与追问优先级

优先识别：

- 没有明确审核标准，却把信息整合或主观评价称为审核；
- 先画 UI、Agent 或 RAG 架构，拿不出首个真实样本和字段契约；
- 规则很少却强行上 RAG，引入漏召回；
- 让 LLM 计算公式、阈值或合法状态；
- 结论没有原文证据、位置和规则版本；
- 直接使用模型自报 Confidence；
- 将课程阈值、行业示例或目标值写成个人实测结果；
- 只有 Demo 成功路径，没有真实材料、失败样本和领域人员确认。

选择下一题时优先抽查一条具体规则或一次真实错误，因为它比继续询问功能列表更容易验证业务
理解、技术路由、个人贡献和项目成熟度。

## 边界

- 具体法律、税务、医疗、施工规范和行业阈值必须按项目当时的权威来源核验，不固化为默认事实。
- 不得使用课程中的固定阈值、样本量、参数或目标值替用户作答。
- 规则分层名称可以变化，不要求所有项目机械使用“三层规则”。
- 用户未参与底层解析或算法实现时，转向其定义的数据契约、规则、交互、评测、验收和推动，
  不诱导冒认团队实现。
