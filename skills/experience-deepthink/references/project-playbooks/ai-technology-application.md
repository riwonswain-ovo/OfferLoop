# AI 技术应用经历深挖

本参考在经历中出现真实 AI/算法应用信号时跨岗位加载。它用于选择下一条高价值线索，不是固定
题库；继续遵守一次只问一个问题，并把确认内容合并进 `../detail-reconstruction-schema.md` 已有的背景、目标、
方案与行动、结果或故事位置，不新增输出章节。

## 触发与深度

触发信号包括但不限于大模型、机器学习、推荐/搜索、计算机视觉、语音、智能体、RAG、AI API、
Prompt、微调、模型评测、智能决策或由算法驱动的自动化。AI 只是无关紧要的辅助工具时，不必
机械走完所有维度；AI 是核心方案、关键约束或主要成果来源时，必须形成完整证据闭环。

深度由“目标岗位需要证明什么”和“用户真实参与了什么”共同决定：

- 产品、运营、商业等岗位：重点证明对能力边界的理解、场景与链路设计、输入输出定义、方案
  取舍、评测准入、异常治理、跨团队落地以及业务价值连接；
- 算法、数据、研发等技术岗位：在上述基础上深入数据构造与质量、模型/算法与架构选择、训练
  或推理、实验设计、工程实现、性能与线上监控；
- 复合岗位：保留实际交叉贡献，正向记录用户与协作方分别完成的动作，不把真实技术实现降格为
  “协作”。这条规则用于内部验真，成稿不输出责任排除声明。

## 证据闭环

### 1. 业务问题与 AI 适用性

查明原流程、用户或业务痛点、基线与约束，以及为什么 AI 比人工、规则、搜索、模板或其他简单
方案更合适。确认 AI 解决的是识别、生成、预测、排序、决策还是流程自动化中的哪个环节；如果
未比较非 AI 方案，如实记录判断依据不足，不反向补造方案论证。

### 2. 端到端技术链路

用用户能够准确承担的深度还原：

`业务输入 → 数据/知识与预处理 → 模型或算法 → Prompt/检索/工具调用/策略编排 → 输出与后处理
→ 人工审核或降级 → 下游业务动作`

只追问实际存在的环节。必须解释关键输入输出、上下游接口和 AI 在链路中的真实作用，不能用
模型、框架、平台或供应商名称代替机制。RAG、智能体、多模型路由、微调等名词出现时，继续问
它解决了什么具体问题、如何验证有效，而不是考察概念背诵。

对文档、多模态、审核或跨节点系统，优先寻找一个真实输入形成的**首个结构化样本**：字段从
哪里来、哪些必填、缺失如何表达、谁生产和消费、校验失败怎么办、真实样本推动过哪些 Schema
变化。页面、架构图或“输出 JSON”不能替代可检查的数据契约。

### 3. 选型、取舍与个人贡献

确认比较过的方案、约束和决策标准，例如效果、数据条件、开发周期、成本、时延、稳定性、
可解释性、安全、隐私与可维护性。区分：

- 团队或协作方决定和实现了什么；
- 用户提出、分析、设计、实现、评测或推动了什么；
- 用户拥有建议权、方案权、验收权还是最终决策权；
- 能证明个人贡献的 PRD、原型、数据集、Prompt/策略、代码、评测报告、实验、监控或上线模块。

用户只会调用工具不等于没有价值，但必须说清其在问题拆解、链路设计、验证或业务落地上的真实
增量；使用复杂技术本身也不自动构成贡献。

### 4. 评测、实验与错误分析

把“效果不错”“准确率提升”追到可核验口径：

- 基线和对照方案是什么；
- 评测集/样本如何获得，规模、分布、标注或人工判断标准是什么；
- 离线技术指标、人工质量标准、线上产品指标和业务指标分别是什么；
- 是否覆盖关键场景、长尾与高风险样本，如何避免数据泄漏或只挑好案例；
- 主要错误类型、失败案例和根因是什么，迭代后在哪些样本上改善或退化；
- 上线前准入、灰度/A-B、护栏与停止条件是什么。

用户未参与或不知道某层评测时停止深挖该层，优先深挖其亲自定义、执行或据此决策的部分；成稿不主动
声明用户没有参与什么。

若产品使用 Confidence、相似度或风险分数驱动自动放行、拒答或人工复核，不能默认该分数代表
真实正确概率。继续确认分数来源、独立标准答案、分桶后的实际正确率、阈值变化对错误和人工量
的影响。未校准分数只能作为调试或排序信号；高后果错误应设独立阻塞指标。

进一步确认评测是否形成可复用资产，而不是一次性展示：

- 建立覆盖核心、长尾、高风险和不可回答场景的场景矩阵；
- 将训练/调试数据与独立验证、测试数据分离，避免模板、文档、用户或时间维度的泄漏；
- 对高可信样本明确期望答案或评分 Rubric、来源、版本和争议处理，形成 Golden Test Set；
- 新增 Bad Case 先保留为独立回归样本，再按受控规则进入评测集，避免边测边改污染结论；
- 版本、Prompt、模型、知识库和评测集必须可对应，才能解释改善与回归。

指标按四层建立连接，不要求每个项目机械凑齐：

`模型/链路质量 → 产品任务与体验 → 业务价值 → 安全与风险护栏`

例如模型层可看召回、精确率、人工质量或工具选择；产品层可看任务完成、采纳、修改、重试和
人工接管；业务层可看效率、成本、风险、留存或转化；安全层关注严重错误、越权、隐私和内容
风险。单一“准确率”不能替代这条指标链。

Bad Case 必须尽量形成闭环：

`收集与复现 → 按场景和链路分类 → 按影响与频率排序 → 定位根因 → 选择修复层 → 回归验证`

修复层可能是数据、知识、检索、Prompt、模型、规则、交互、工具或人工流程。只修一个案例而
没有检查其他场景回归，不能证明系统改善。

### 5. 上线治理与持续迭代

确认真实发生的幻觉、误判、偏见、内容安全、隐私泄漏、提示注入、越权调用、不可解释输出、
时延、成本或稳定性风险。只选择与该经历相关的风险继续追问，并查明监控、人工复核、规则兜底、
拒答、回退、限流、版本回滚或反馈闭环；未上线项目则追问真实验收和拟定边界，不把计划写成
已完成治理。

当输出依赖规范、医疗、法律、财务或企业制度等权威知识时，继续确认知识服务为空、冲突、过期
或超时时能否**失败关闭**：哪些问题必须拒绝、重试、追问或转人工，哪些低风险内容允许明确
标记后降级，以及谁承担最终专业责任。不能让模型用预训练记忆静默补答并继续高风险动作。

### 6. 技术结果到用户和业务价值

把技术指标与用户行为、流程效率、质量、风险、收入或成本连接起来，说明中间机制和归因边界。
同时确认：

- 相比原流程或非 AI 基线产生了什么增量；
- 效果、成本与时延是否达到可用门槛；
- 负向影响、未覆盖场景和规模化限制；
- 结果属于整体系统、本人负责模块还是个人交付；
- 技术升级是否真的带来业务改善，还是只改善了离线指标。

没有线上或业务结果时，可以使用真实的离线评测、用户测试、交付验收或风险消减结果，但不能
编造转化、收入或效率提升。

## 项目成熟度判断

同一技术结果在不同阶段代表的证据强度不同，必须区分：

- **实验/原型**：验证局部想法或展示交互，尚未证明关键假设；
- **PoC**：用最小实验验证最高风险的技术或业务假设；
- **MVP**：形成可供目标用户使用、可测量的最小价值闭环；
- **试点**：在受限真实组织、用户或流程中验证运行与协作；
- **灰度**：以有限真实流量验证质量、稳定性和风险护栏；
- **生产运行**：具备持续监控、版本治理、异常处理和稳定业务结果。

不能把 Demo、PoC 或内部试用写成“规模化上线”。追问每次阶段升级所依赖的证据、未通过时的
停止条件，以及仍未解决的风险。

## 追问选择规则

每轮从下列优先级中只选一个问题：

1. 会改变项目价值判断或个人贡献判断的事实缺口；
2. 用户刚提到但尚未解释机制、依据或验证的关键技术动作；
3. 质量、成本、时延、安全等决定能否上线的关键取舍；
4. 技术指标与用户/业务结果之间缺失的连接；
5. 能形成失败、决策、协作或重来改进故事的真实事件。

避免概念考试、术语盘点和与用户职责无关的底层追问。用户卡壳时，可给二至三个回忆入口，例如
“一次错误案例、一次方案取舍、一次上线验收”，但不得把示例暗示成用户做过的事实。
