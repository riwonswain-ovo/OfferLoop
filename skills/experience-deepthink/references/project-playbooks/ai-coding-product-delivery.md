# AI Coding 与产品交付经历深挖

当经历涉及用 Codex、Claude Code、Cursor、低代码平台或其他 Coding Agent 构建原型、应用、
内部工具或 AI 产品时读取。目标是确认用户实际参与的产品交付，不考察代码语法，也不把工具
使用自动等同于工程能力。

## 一、先确认参与层级

从用户原话判断并继续核实：

1. **观察/学习**：理解流程或观看演示；
2. **跟做/复刻**：使用既有 PRD、仓库、提示词或完整教程；
3. **配置/集成**：选择并连接模型、数据库、API、托管服务或插件；
4. **AI 辅助实现**：由用户定义需求和验收，Coding Agent 生成或修改实现；
5. **独立产品交付**：用户完成问题定义、关键取舍、规格、验收和迭代；
6. **团队生产交付**：与研发等角色协作，对真实运行、风险和结果承担明确责任。

层级只描述事实，不评价高低。允许同一项目在不同模块处于不同层级。

## 二、交付证据链

沿当前最薄弱的一环纵向追问：

```text
用户/业务问题与约束
→ 需求规格与非目标
→ 阶段和任务拆分
→ 本人、AI、模板、平台、研发的分工
→ 实现与接口/状态/权限
→ 测试和人工验收
→ 版本、部署与运行
→ 失败、修复、结果与局限
```

优先追真实物证：PRD/Spec、原型、任务记录、提交或版本、测试用例、报错与修复、部署记录、
监控、用户反馈和业务数据。物证只能证明其覆盖的阶段，不能反推全部所有权。

## 三、PM 级系统边界

不要求用户写代码；要求其能把一个真实业务动作说明白：

- 前端让谁完成什么交互；
- API 接收什么输入，返回什么结果，失败如何呈现；
- 后端执行什么业务规则；
- 数据库保存哪些对象、关系和状态；
- 哪些任务异步执行；
- 如何认证身份、限制角色权限、记录审计；
- 哪个动作必须人工确认，如何撤销或恢复。

用户只会说架构名词时，回到一条实际输入或一次失败，不顺序考试术语。

## 四、Harness 与可靠性

涉及 Coding Agent 时检查：

- 工作环境和项目规则如何提供；
- 长任务如何保存目标、进度和上下文；
- 工具、权限和可修改范围如何约束；
- 是否小步拆分、分支隔离、提交留痕；
- 测试和人工验收由谁定义、谁实际执行；
- Agent 自称完成但结果不对时如何发现、回退和修复。

把效果归因于“模型 + Harness + 人类判断”的组合，不把成功或失败简单归于模型强弱。

## 五、成熟度证据

沿用统一成熟度，但对软件交付增加证据要求：

| 阶段 | 可用证据 | 不足以证明 |
|---|---|---|
| 本地可运行 | 本机主链路、截图或录屏 | 他人可访问、稳定运行 |
| 可分享部署 | 公网/内网环境、部署记录 | 真实用户、生产治理 |
| Demo/PoC | 核心假设和验证结果 | 完整业务闭环 |
| MVP | 最小角色、状态与主链路验收 | 规模、持续稳定 |
| 试点 | 真实用户/数据、反馈与迭代 | 全量生产 |
| 生产运行 | 持续用户/流量、权限、监控、故障、回滚和结果 | 超出证据范围的规模或归因 |

“有链接”“有测试账号”“一键 production deploy”最多证明可访问部署，不自动等于生产运行。

## 六、安全与验收

只追与经历相关的高价值项：

- 密钥是否仅通过服务端环境配置管理，是否曾进入前端或仓库；
- 每个数据读写是否校验身份和对象权限；
- 普通用户、管理员和跨项目角色是否分别验证；
- 单元、集成、E2E 或人工验收为何这样组合；
- 一条真实 Bad Case 如何发现、定位、修复和回归；
- 高风险动作如何确认、审计、撤销和人工接管。

课程中的固定测试优先级、灰度比例和工具默认值不能当成通用标准。

## 七、成稿质量门

成稿前确认：

- “开发、搭建、实现、独立完成、主导、上线、生产级”均有匹配事实；
- 跟做、复用、配置、AI 生成和本人设计没有混写；
- 至少有一项本人产品判断和一项本人实际验收；
- 技术词能连接真实输入、动作、输出、异常或权限；
- 项目阶段由证据决定，不由课程标题、部署按钮或仓库说明决定；
- 未发生的测试、监控、用户反馈和业务结果明确标为缺口。

缺少证据时保留诚实的较低成熟度表述，不替用户补造工程过程。
