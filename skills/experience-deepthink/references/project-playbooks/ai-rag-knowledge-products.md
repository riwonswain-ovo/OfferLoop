# RAG / 知识产品经历深挖

本参考只在经历真实涉及知识库、企业搜索、文档问答、检索增强、引用溯源或基于外部知识生成时
加载。它用于定位候选人在数据、检索、生成、评测和产品治理中的真实判断，不进行 RAG 名词考试。
每轮只追一个会改变项目价值、方案有效性或个人贡献判断的缺口。

## 1. 知识问题与路线选择

先查明原问题究竟是知识缺失、检索困难、内容生成、判断逻辑还是输出风格问题。确认为什么选择
RAG，而不是搜索、规则、长上下文、Prompt、微调或人工流程；重点追问知识更新频率、可溯源性、
数据条件、定制深度、成本和时延约束。

完成标准：能说明 RAG 解决了链路中的哪一个瓶颈，以及更简单方案为何不足；不能因“资料很多”
就默认需要向量数据库。

## 2. 数据治理与入库

沿真实数据链路追问：

`来源与范围 → 清洗去重 → 结构识别 → 切块 → 元数据 → 索引/存储 → 版本与更新`

重点确认：

- 资料由谁提供，哪些内容被排除，可靠性和授权如何确认；
- Chunk 为什么按段落、条款、章节、表格或其他语义单元切分；
- 过大导致噪声、过小导致语义断裂时，如何发现并调整；
- 来源、标题、章节、时间、地域、权限、生效/失效状态等元数据如何使用；
- 新旧版本、重复内容、废止文档和解析失败如何处理。

不把“上传了多少文档”当作知识库质量。用户未负责数据工程时，转向其定义的数据范围、验收规则、
错误样本或跨团队推动。

## 3. Query 理解

不要默认把用户原话直接送入检索。只有实际存在时才追问：

- 如何区分清晰、模糊、复合、带指代或带错误前提的问题；
- 何时追问，何时补全实体、时间、地域和业务条件；
- 是否做意图分类、Query 改写、子问题拆解或多路查询；
- 改写前后如何验证召回改善，是否引入语义漂移。

完成标准：至少用一个真实问题解释 Query 如何转成检索输入，以及该判断由本人、规则、模型还是
其他团队负责。

## 4. 召回、过滤与排序

还原实际检索机制及其选择依据：

- 向量、关键词/BM25、结构化查询或多路召回分别解决什么；
- 元数据硬过滤发生在何处，如何避免越权或过时内容进入候选；
- Top-K、相似度阈值和召回规模如何确定；
- 是否使用融合或 Reranker，解决了哪些“召回了但排不前”的问题；
- 漏召回、错召回和排序错误如何从日志或测试集被发现。

框架名称和参数值不能代替选择依据。没有做过对照或归因时，将结论标为待验证。

## 5. 上下文拼装与生成

确认候选知识如何去重、排序、截断和组装进模型上下文，以及生成端如何：

- 区分资料事实、用户问题与系统约束；
- 保留来源和引用关系；
- 处理多个来源之间的冲突；
- 在证据不足、低相关或超出知识范围时拒答、追问或转人工；
- 对关键数字、标题、链接或标识做后处理校验。

重点寻找“检索正确但回答错误”和“回答看似合理但没有证据”两类失败，避免把所有问题都归为
模型幻觉。

## 6. 分阶段评测与错误归因

将“RAG 准确率”拆成可验证的评测漏斗：

1. **Query 层**：分类、改写或拆解是否保留原意；
2. **召回层**：正确证据是否进入候选，关注 Recall、命中率与覆盖；
3. **排序层**：正确证据是否排到可用位置，关注 Precision、MRR、NDCG 或人工相关性；
4. **生成层**：答案是否正确、忠实、完整、可引用并遵守拒答；
5. **端到端层**：任务完成、人工返工、时延、成本和业务结果。

必须继续确认测试集来源、样本量、场景分布、标注标准、基线和目标。优化时优先使用
“现象 → 根因层 → 修改杠杆 → 控制变量验证”，不要同时更换模型、切块、检索和 Prompt 后把
全部改善归因于某一个动作。

## 7. Agentic RAG 真实性门

只有经历明确声称 Agentic RAG，或单次检索无法完成复合、多源、需工具计算或需验证的知识任务
时继续深挖。名称成立至少要指出一种由中间反馈驱动的动态行为：

- 根据问题拆解子任务并调整计划；
- 根据数据类型、权限或阶段选择不同知识源；
- 发现证据不足、冲突或噪声后重写、换源或再次检索；
- 调用结构化查询、计算或其他工具补齐证据；
- 验证引用、交叉来源或向用户澄清后再决定下一步。

一次 Query Rewrite、固定多路召回、多个检索节点串联或换用 Agent 框架，都不足以证明
Agentic RAG。要求候选人给出普通 RAG 的真实失败样本，指出哪个中间结果改变了后续动作，
再用同类任务验证新增循环是否改善质量，以及时延、成本、可观测性和失败面增加了多少。

小规模规则库、单一语料和单跳问题通常优先普通 RAG、结构化查询或全量规则；不为了简历标签
强行升级架构。

## 8. 更新、权限与上线治理

经历进入真实使用后，追问：

- 数据更新频率、增量索引和失效内容清理；
- 用户、部门、租户或文档级权限是否贯穿检索链路；
- 无结果、低置信、来源冲突、服务超时和索引异常的降级；
- 质量、零结果率、引用有效性、时延、成本和用户反馈如何监控；
- 版本、灰度、回滚和人工纠错如何闭环。

高准确性场景必须追问证据阈值和人工接管，但不得使用课程中的固定阈值替用户作答。

## 9. 追问选择

优先选择：

1. 会推翻“为什么需要 RAG”的路线选择；
2. 能定位一次真实 Bad Case 所在层级的事实；
3. 能证明本人定义了数据、检索、评测、交互或验收标准的动作；
4. 能说明技术改进如何影响用户任务和业务结果的连接；
5. 会暴露权限、时效、来源或拒答缺陷的上线证据。
6. 声称 Agentic RAG 时，能证明中间反馈真实改变检索或验证动作的案例。

不顺序询问全部链路，不要求产品岗背算法指标。若用户只使用了现成知识库能力，重点深挖其场景、
数据范围、质量验收、交互兜底和业务落地。平台底层实现只作为内部验真信息，最终只写已确认的正向
项目事实。
