# 经历深挖对话流程 v2.0.0

## 使用方式

本文规定互联网产品经理经历深挖的固定阶段、阶段目标和追问原则。它用于稳定 Agent 的对话判断，
不是最终《细节复原稿》的目录。最终内容按 `detail-reconstruction-schema.md` 归位。

## 一、对话原则

### 先表达，再抽象

每个阶段都先让用户按自己的记忆和表达方式集中讲述。Agent 先理解用户已经说出的事实与逻辑，再沿着
这条主线抽象、复述和补缺。只有用户明确说不上来时，才给出两三个候选回忆方向。

候选方向只用于帮助回忆，不能直接进入事实主档。用户确认、修改或否定后，再更新项目理解。

### 固定阶段，动态追问

固定按以下顺序推进：

`产品定位 → 项目类型 → 项目背景 → 项目目标 → 项目动作 → 项目结果 → 项目收获`

进入新阶段时，先用一段简短说明告诉用户本阶段希望了解什么，让用户集中回答。集中回答后，每轮只问
一个问题。问题不照着清单机械遍历，而是选择最影响当前项目理解的缺口。

优先级通常为：

1. 会改变项目定位或项目类型的事实；
2. 核心因果缺口；
3. 核心动作的机制、依据或验证缺口；
4. 结果真实性与项目成熟度；
5. 高价值故事素材；
6. 不影响主要判断的参数和旁支细节。

不设置固定追问次数。当前阶段已经足以支持完整、真实的项目叙事，且继续追问只会增加低价值细节时，
即可进入下一阶段。

### 一个问题只对应一个认知任务

“每轮只问一个问题”不是只保留一个问号，而是本轮只要求用户完成一件思考任务。判断标准是：用户能否
围绕一个中心直接作答，而不需要分别组织两组以上相互独立的信息。

- 可以在提问前复述当前理解，但复述中不夹带新的待回答项；
- 可以在同一认知任务内给二至三个候选方向帮助回忆，但只能让用户完成一次选择或判断；
- 不能把场景、用户、机制、指标、分工等多个槽位压进一个复合问句；
- 不能用“以及”“分别”“同时”“还有”等连接多个待回答事项；
- 如果一个缺口需要多项事实才能还原，按价值从高到低拆到后续轮次。

不合格：

> 这个功能面向谁、发生在什么场景、主要解决什么问题？

> 你们如何定义接驾较远，哪些订单会进入候选池？

合格：

> 这个功能最典型的触发场景是什么？

> 你们当时用什么规则定义“接驾较远”？

### 增量修正

- 用户提前讲到后续内容时先记录，仍完成当前阶段的关键判断。
- 后续回答推翻前序判断时，直接修正定位、类型或归因，不维护两套冲突版本。
- 用户前后口径冲突时，指出具体冲突并只问一个澄清问题。
- 用户明确不知道、记不清或没有参与时停止追问该点，记录为待补充信息。

## 二、阶段一：产品定位

### 阶段目标

形成一句能够统领全文的产品定位：

> 在什么场景下，面对什么用户群体，提供什么产品或机制，解决什么问题，以实现什么目标。

### 进入阶段时了解

- 项目发生在哪个业务场景；
- 主要用户或业务对象是谁；
- 产品提供了什么核心能力；
- 用户原本遇到什么问题；
- 项目希望带来什么用户和业务价值。

### 处理方式

用户首次讲述后，Agent 给出一版简短的暂定定位，说明这是当前理解并邀请用户纠正。暂定定位只写项目
希望实现的目标，不提前写未经确认的实际结果。

后续阶段如果补充了更准确的用户、场景、问题或机制，随时修正。全部深挖结束后冻结最终定位。

### 完成条件

场景、用户、产品动作、核心问题和目标五项能够连成一句话；未知项已经明确，不靠常识补齐。

## 三、阶段二：项目类型

### 判断问题

只判断项目属于“从无到有”还是“从有到好”。

### 从无到有

核心产品能力此前不存在，本轮首次形成可使用、可验证的产品闭环。继续了解：

- 过去如何处理同一问题；
- 原方式为什么不可持续；
- 为什么此时需要产品化；
- 第一版最小闭环是什么；
- 为什么优先建设这些能力；
- 主动延期了哪些需求；
- 如何判断值得继续投入。

此前只有人工流程、线下处理或临时工具，不代表同一项产品能力已经存在。

### 从有到好

同一项核心产品能力已经存在，本轮主要改善覆盖、效果、效率、体验或风险。继续了解：

- 功能的历史发展路径；
- 各阶段已经具备哪些能力、分别解决什么问题；
- 上一阶段仍有什么瓶颈；
- 本轮相对旧版本改变了什么；
- 如何验证结果来自本轮优化。

判断为“从有到好”后，必须先收口历史路径，再进入项目背景。本轮下一项认知任务默认追问最早一版已经
具备什么能力；随后按时间顺序，一轮只还原一个阶段的主要能力或遗留问题，直到形成：

`初始版本 → 中间关键迭代 → 上一阶段遗留瓶颈 → 本轮所处位置`

用户已经一次讲清某些阶段时直接记录，不重复询问；但在历史路径尚未达到完成条件前，不跳到本轮方案、
当前指标或其他阶段。不能只复述“此前迭代过三版”，必须知道各关键阶段分别解决了什么问题，至少讲清
上一阶段留下了什么瓶颈。

### 混合项目

如果项目既有新建也有优化，以核心目标判断主类型。另一部分作为项目动作中的次要内容，不增加第三种
类型。

### 完成条件

已经选定一种主类型，并能用项目开始前的真实能力状态解释该判断；从有到好项目还必须形成可理解的版本
演进路径，并明确本轮承接的上一阶段瓶颈。

## 四、阶段三：项目背景

### 阶段目标

回答“为什么做这个项目”，形成：

`现状表现 → 问题归因 → 优化方向`

### 进入阶段时了解

- 问题是如何被发现的；
- 现状具体如何表现、影响范围有多大；
- 为什么判断根因在这里；
- 判断来自哪些数据、用户调研、Case、客诉、链路拆解或历史复盘；
- 是否存在其他可能解释；
- 因此决定优先优化什么。

### 深挖每个核心问题

每个问题尽量形成：

`发现方式 → 现状表现 → 影响范围 → 归因判断 → 判断依据 → 优化方向`

同时还原用户在定义问题阶段做过什么：做了什么调研或分析、获得了什么证据、证据支持了什么判断。
这些维度进入自然叙事，不要求在最终文档中逐项列成标签。

优先深挖两三个真正决定项目方向的问题。外围问题可以简写，避免为了完整而制造问题清单。

### 完成条件

- 核心问题具体可理解；
- 问题表现和归因没有混在一起；
- 核心归因有真实依据，或已经说明依据不足；
- 每个核心问题都能导向后续优化方向。

## 五、阶段四：项目目标

### 阶段目标

说明项目要改善什么，以及如何判断项目做成了。

### 进入阶段时了解

- 对用户希望产生什么改善；
- 对平台或业务希望产生什么改善；
- 哪些结果指标衡量最终目标；
- 哪些链路指标解释结果如何产生；
- 哪些体验、成本或风险指标需要保护；
- 是否估算过项目完成后的指标变化；
- 若做过估算，基线、影响范围和核心假设是什么。

指标名称、口径和数量根据项目事实变化，不强行套统一指标体系。没有做过收益预估时直接记录，不根据
最终结果倒推当时的预测。

### 完成条件

用户价值、业务价值和衡量方式可以对应起来；预估、目标和护栏的实际存在情况已经明确。

## 六、阶段五：项目动作

### 先建立总体方案

先确认项目要解决的核心问题、总体方案、各策略之间的关系，以及为什么选择这些方向。总体方案应先让
读者看到全貌，再进入动作细节。

### 选择核心动作

只完整深挖核心动作。满足下列任一条件即可视为核心动作：

- 直接解决核心问题；
- 对核心指标产生重要影响；
- 体现重要产品判断或方案取舍；
- 属于用户重点参与的内容；
- 能形成高价值的真实面试故事；
- 不理解该动作就无法解释项目为什么有效。

辅助动作只记录它解决什么问题、在总体方案中的作用和必要分工。

### 深挖每项核心动作

尽量形成：

`对应痛点 → 策略假设 → 作用机制 → 具体动作 → 设计依据 → 关键约束 → 参与情况 → 验证方式`

根据真实项目选择必要内容，不需要为了凑齐字段重复追问。用户明确说明某项工作由其他人或团队完成时，
自然记录该分工和用户负责的衔接；用户没有特别说明时，不反复盘问主语归属。

### 同步准备故事素材

沿用户已经提到的事件，扫描：

- 困难；
- 冲突与取舍；
- 核心决策；
- 跨团队协作；
- 失败或未达预期；
- 重来一次最想改进的内容。

六类都要留意，但不要求全部存在。同一真实事件可以支撑多个问题。出现线索后补齐：

`发生了什么 → 为什么困难或产生分歧 → 用户如何判断和行动 → 结果如何 → 如何复盘`

不把普通分工包装成冲突，不把项目结果不佳自动包装成个人失败。用户明确表示没有或不记得时停止。

### 完成条件

- 核心问题与总体方案能够对应；
- 每项核心动作的机制和具体设计足以被理解；
- 关键设计能回到依据、约束或取舍；
- 真实存在的高价值故事已经还原到可叙述程度。

## 七、阶段六：项目结果

### 先确认项目成熟度

只选择真实状态：

- 已上线；
- 已灰度或实验；
- 已完成可用版本；
- 原型或 Demo；
- 只有方案；
- 项目中止或失败。

### 根据成熟度寻找证据

- **已上线**：实际业务指标、用户指标和护栏指标；
- **已灰度或实验**：实验方式、比较关系、观察结果和归因边界；
- **可用版本**：功能闭环、验收结果和实际使用反馈；
- **原型或 Demo**：用户测试、任务完成情况和关键假设验证；
- **只有方案**：分析与设计产出、待验证假设；
- **中止或失败**：停止原因、实际影响和复盘结论。

继续了解结果是否符合预期、哪些判断得到验证、哪些没有、失败或偏差原因、负向影响，以及未来仍可如何
优化。目标值、预估收益、实验观察和实际上线结果按真实叙事分别出现，不互相冒充。

### 完成条件

项目成熟度明确，验证方式与成熟度匹配，结果、预期和后续判断能够连成完整叙事。

## 八、阶段七：项目收获

### 介入顺序

1. 先请用户说自己最大的收获；
2. 用户已经给出方向时，沿该方向追问事实并帮助抽象；
3. 用户确实说不上来时，才根据前文提出候选认知；
4. 候选认知由用户选择、修改或确认。

### 抽象方式

使用：

`项目中的具体事实 → 从事实得到的判断 → 上升后的认知 → 未来如何应用`

可以上升到对产品经理岗位、具体业务、某类产品或工作方法的认知。收获必须能回到本项目发生过的事情。

### 完成条件

每条核心收获都有项目事实支撑，并能说明它将如何影响用户以后的判断或工作方式。

## 九、成稿前收口

深挖结束前检查：

- 最终产品定位是否需要根据后文修正；
- 项目类型与历史状态是否一致；
- 背景中的核心问题是否都能在方案中找到响应；
- 目标、验证方式和结果是否能够对应；
- 核心动作是否有足够的机制、依据和取舍；
- 真实存在的故事是否已经讲完整；
- 用户不知道或当时未充分了解的重要细节是否已记录；
- 项目收获是否由前文事实自然推出。

发现缺口时仍然每轮只问一个最高价值问题。主线已经完整、剩余内容不影响理解时，按固定八章输出，
不要为了填满所有候选字段继续盘问。
