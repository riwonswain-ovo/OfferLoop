## 核心原则

所有项目使用同一目录母版。项目类型只决定每节写什么，不决定整份文档采用什么结构。

> Deep-dive mechanisms determine what information should be discovered.
>
> Canonical Schema determines where that information should be stored.

Story Recovery、Personal Failure Gate、Experiment Attribution Matrix、End-to-End State & Fallback、
Rule Trace、Evidence Ledger 和 Ownership Audit 是内部深挖与审计工具，不是正式文档的平级目录。

> Internal mechanism determines judgment. Publication layer expresses the conclusion.

最终《细节复原稿》必须像正常的项目复盘或 PRD 深挖文档，只呈现机制产出的结论，不呈现 Agent 如何
得到结论。事实严谨性、因果边界、责任边界和证据缺口必须保留，内部机制名称与状态标签必须移除。

判断目录一致性时，忽略 Markdown `#` 数量，只检查章节名称、父子关系、内容归属、章节顺序和是否产生
不必要的新平级目录。

默认标题：

`# 细节复原稿｜<经历名称>｜<完整岗位方向>`

## Analysis Layer 与 Publication Layer

### Analysis Layer｜只供 Agent 使用

保留 Story Recovery、`recovery-exhausted`、Personal Failure Gate、Experiment Attribution Matrix、
Evidence Ledger、Rule Trace、Ownership Audit、Causality Audit、State & Fallback Pass 和
`confirmed / supported / explained-not-sourced / unknown / conflict`。这些工具只用于找缺口、验真、
归因、判断贡献边界和决定是否继续提问。

### Publication Layer｜最终交付

只写项目事实、数据、业务判断、策略、实验、结果、贡献、风险、复盘和当时未充分了解的细节。按下列
关系翻译内部判断，禁止复制内部工作流名称：

| 内部机制 | 只决定 | 最终表达 |
|---|---|---|
| Story Recovery | 是否存在真实故事 | 直接写故事；事实不足时写“当前材料不足以还原完整事件” |
| Personal Failure Gate | 负向结果能否归因于本人 | 写个人责任边界与因果边界 |
| Experiment Attribution Matrix | 实验比较关系 | 写实验正文；复杂时写“关键实验结果及归因口径” |
| State & Fallback Pass | 异常链路是否完整 | 写“核心状态与异常流程” |
| Evidence Ledger | 事实可信度 | 写事实、证据来源和证据边界 |
| Ownership Audit | 团队与个人贡献边界 | 写“团队负责 vs 我负责” |
| Causality Audit | 结论能与不能证明什么 | 直接写归因边界，不写审计过程 |

## Canonical Content Placement Rules

### 第一章｜项目概述

- 只保留“项目名称、产品定位、历史发展与既有机制”三块母结构。
- 把状态链、异常、fallback、超时、过期和最终决策权放入“历史发展与既有机制 → 核心状态与异常流程”。
- 用一段正文简述本人角色；详细 ownership 主要进入第四章各策略和第五章实验。
- 不创建与“历史发展与既有机制”平级的“AI 架构”“状态链”“风险治理”或“本人角色”目录。

### 第二章｜项目背景与优化方向

每个问题形成：

`发现方式 → 现状表现 → 数据/用户/Case 证据 → 问题归因 → 证据边界 → 优化方向`

这些字段可以用加粗正文，不强制继续增加标题。

### 第三章｜项目目标与数据指标

- 指标体系只允许“结果指标”和“链路指标”两个母类。
- 把业务价值、效率、体验、偏航、ETA、客诉和安全护栏放入结果指标的合适子类。
- 把 ASR、召回、识别、候选、规则、模型准出和产品漏斗放入链路指标。
- 不创建与二者平级的“风险护栏”“AI 指标”或“机制指标”第三套体系。

### 第四章｜方案及动作

每个主要策略优先只保留四个直接子块：

`对应痛点 → 具体动作 → 团队负责 vs 我负责 → 故事素材`

- 把作用机制、输入输出、流程、规则、准入、阈值、状态、fallback 和验证思路放入“具体动作”内部。
- 第四章只回答“设计了什么、为什么这样设计”。验证部分只写验证思路，不完整复述样本量、实验周期、
  对照关系、显著性或结果数字；统一指向第五章。
- “团队负责 vs 我负责”优先包含“团队共同负责、我负责 / 重点参与、贡献边界”。
- 故事素材按真实情况组织冲突、失败、核心决策或跨团队协作。
- 没有完整故事时直接写“当前材料不足以还原完整事件，因此不将常规分工包装成故事”，不输出内部
  搜索过程或状态标签。

### 第五章｜实验与收益

只保留三个核心模块：

`实验设计 → 最终收益结果 → 团队负责 vs 我负责`

- 把离线、人工、单策略、组合、Shadow、A/B、W 组比较和定向质检放入“实验设计 → 实验分层”。
- Experiment Attribution Matrix 只在内部维护。信息简单时把比较关系写入实验正文；复杂时在实验设计中
  使用“关键实验结果及归因口径”或“实验结果及归因口径”人类可读表格，只保留“指标、比较关系、
  结果、能说明什么、不能说明什么”。
- 把 Personal Failure Gate 得出的事实边界翻译后放入“最终收益结果 → 风险与负向结果”，直接写因果
  与个人责任边界，不出现 Gate 名称。
- 把实验 ownership 的最终事实源放在本章“团队负责 vs 我负责”。

### 第六章｜项目未来的优化方向

每个方向只保留四个直接子块：

`解决的问题 → 优化方案 → 预期价值 / 核心取舍 → 重点关注`

- “预期价值 / 核心取舍”吸收为什么有效、预期收益、新风险、机会成本与 trade-off。
- “重点关注”吸收验证指标、实验方式、优先级、上线标准、stop condition 和 rollback 条件。

### 第七章｜项目收获

按“对一种工作方式 / 产品类型的认知”和“对另一种业务 / 系统类型的认知”组织。认知数量可按真实
价值增减，不写泛化能力提升。

### 第八章｜Unknown

把无法确认的阈值、参数、规则来源、因果、算法目标、fallback、实验设置、ownership、
故事缺口和状态链信息统一归入本章，继续使用“已知事实、当前缺失、如何验证”。最终正文不输出
`unknown`、`recovery-exhausted` 等内部状态标签。

## Fact Ownership Map 与 Single Source of Truth

在 Analysis Layer 为每个高价值事实指定唯一 `Primary Home`。该表只供 Agent 使用，不进入最终文档：

| Fact | Primary Home | Secondary Allowed | Repeat Level |
|---|---|---|---|
| 问题规模 | 第二章 | 第一章项目概述 | 一句话 |
| 核心目标 | 第三章 | 第一章 | 一句话 |
| 策略机制 | 第四章 | 第一章 | 一句话 |
| 实验设计 | 第五章 | 第四章 | 只讲验证思路 |
| 实验数字 | 第五章 | 故事素材 | 必要结果一句 |
| 最终结果 | 第五章 | 第一章 | 最多 2–3 个核心数字 |
| Ownership | 第四章策略、第五章实验 | 第一章 | 简短概述 |
| 未来方案 | 第六章 | 无 | 不重复 |
| 项目认知 | 第七章 | 面试逐字稿 | 不在前文提前展开 |
| 当时未充分了解的细节 | 第八章 | 对应正文 | 只写“依据待确认” |

选择 Primary Home 时先判断该事实回答什么问题：是什么→第一章；为什么做→第二章；目标与衡量→第三章；
设计了什么及为什么→第四章；如何验证和发生了什么→第五章；未来怎么做→第六章；形成什么认知→第七章；
当时缺什么依据→第八章。一个事实即使支持多个判断，也只有一个完整版本。

## Content Placement Check

最终输出前逐项检查并自动重排：

1. **第一章**：状态链是否错误提升为与历史机制平级；fallback 是否脱离具体机制；ownership 是否重复展开。
2. **第三章**：指标体系是否只含结果指标和链路指标；风险是否错误成为第三个母类。
3. **第四章**：每个策略的直接子块是否优先为痛点、动作、ownership、故事；机制、fallback、验证是否
   错误与四块平级。
4. **第五章**：是否只保留实验设计、最终收益结果、团队负责 vs 我负责；Matrix、Failure Gate、Shadow、
   人工评测是否已正确归位。
5. **第六章**：每个未来方向是否只保留问题、方案、价值/取舍、重点关注四块。
6. **重复检查**：同一 ownership 是否在第一、第四、第五章重复；同一实验结果是否重复解释；正文与
   第八章是否对同一 Unknown 给出冲突口径。

Content Placement Check 只移动内容，不删除确认事实、不自动修复 Unknown、不新增推断。

## Deduplication Pass

完成全文后，逐项检查数字、实验、规则解释、贡献、项目结论和当时未充分了解的细节是否在多个章节
完整重复：

1. 保留 Primary Home 中的完整版本；
2. Secondary Home 删除，或压缩成一句引用，例如“后续通过三层评测验证，具体结果见第五章”；
3. 第四章不得复制第五章的实验表格、样本口径或结果分析；
4. 故事素材可引用维持因果链所必需的一个结果，但不得复制结果分析；
5. 高价值数字全文出现超过两次时必须人工判断；完整解释原则上只出现一次，概述或故事最多再引用一次。

去重只改变表达位置和重复程度，不删除唯一事实、不改变归因、责任或证据边界。

## Publication Hygiene Pass

最终输出前全文检查下列内部词汇；若来自 Skill 工作流，必须转换成人类项目语言。业务本身确实使用同名
术语时除外：

`Story Recovery`、`Story Recovery Pass`、`recovery-exhausted`、`Personal Failure Gate`、
`Failure Gate`、`Experiment Attribution Matrix`、`Evidence Ledger`、`Rule Trace`、
`Ownership Audit`、`Causality Audit`、`Content Placement Check`、`Directory Conformance Check`、
`Question Relevance Gate`、`State & Fallback Pass`、`confirmed`、`supported`、
`explained-not-sourced`、`unknown`、`conflict`。

同时删除“当前 Skill 判断”“Agent 认为”“经某项检查后”“根据内部状态”“这一项标记为”等元话语，
直接陈述项目事实。最后反问：不了解 AI 生成流程的产品经理，是否仍能从正文看出明显 Agent 工作流
痕迹；如果能，继续清洗，但不得删除事实边界。

## 匿名目录测试

成稿前隐藏项目名称、业务名称和具体策略名称，只观察目录树：

- 是否仍能明显还原到本文件的八章母版；
- 不同策略是否都还原为“痛点—动作—ownership—故事”；
- 第五章是否仍只有三个核心模块；
- 第六章是否每个方向都只有四个核心子块；
- 是否因 AI、策略、中台或其他项目类型长出新的平级报告结构。

若匿名后明显像另一套报告结构，先自动重排再输出。项目越复杂，内容可以越深，但目录不能越长越自由。

## 强制写作规则

1. 始终保留固定八章及顺序，不新增同级大章节。
2. 事实、当前解释、复盘建议分离；历史机制与本轮新设计分离。
3. 团队成果与个人贡献分离，不把协作方实现或团队拍板归为本人。
4. 每个策略回指前文痛点；深挖内容进入“具体动作”，不扩张策略母结构。
5. 每个重要“因为”有证据或明确归因不足；每个重要阈值有来源或进入第八章。
6. 不为了完整度补造异常流程、算法机制、数据口径、冲突或协作故事。
7. 每个重要实验数字绑定 Treatment、Control、人群、周期、实验类型、归因边界和 Cannot Prove。
8. 单策略、组合、A/B、Shadow、前后对比和人工定向抽样分开表达，不拼成严格漏斗因果。
9. Personal Failure Gate 只控制事实归因，不生成正式平级目录。
10. 未来优化保留 trade-off、验证指标、优先级和上线判断，但统一归入四块母结构。
11. 项目收获由前文事实推出，不写“沟通能力提升”等泛化结论。
12. 完成 Content Placement Check、Deduplication Pass、Publication Hygiene Pass 与匿名目录测试后才输出。
13. 内部机制决定判断，最终文档只表达结论；删除内部术语不等于删除事实、因果或责任边界。
14. 不默认生成“附：连贯文章版”；口语表达由独立《面试逐字稿》承担。
