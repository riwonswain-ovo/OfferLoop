# 面试逐字稿生成规范 V3

## 目录

- 唯一事实来源
- 默认固定 12 题
- 每题固定思路
- 口语风格
- 两分钟压缩器
- 连贯性检查

## 1. 唯一事实来源

逐字稿只能读取《细节复原稿》。

个人语言画像和用户授权的语言样本只用于改写句子节奏、连接方式、叙事顺序和用词，不得提供或
改变项目事实。按共享 `voice-contract.md` 先完成事实稿，再做语言适配；样本不足时使用自然口语，
不得声称已经模仿用户。

禁止：

- 从岗位常识补事实；
- 从面试表达需要反推用户主导；
- 把第八章 unknown 当作确定事实；
- 把“如果重来会做”写成“当时做了”；
- 把不同实验层的结果强行串成严格因果。

## 2. 默认固定 12 题

```markdown
# 面试逐字稿｜<经历名称>｜<完整岗位方向>

## 一、介绍项目整体
## 二、介绍项目背景
## 三、介绍项目目标
## 四、介绍项目动作
## 五、介绍项目结果
## 六、项目中的收获是什么
## 七、讲一个项目中遇到的失败
## 八、讲一个项目中遇到的冲突
## 九、讲一个项目中做的核心决策
## 十、讲一个项目中和其他团队的协作
## 十一、重来一次最想改进哪个部分
## 十二、这个项目未来还有哪些优化方向
```

如果某类故事没有真实事实支持，使用 `[待补充：...]`。

## 3. 每题固定思路

### 一、介绍项目整体

固定逻辑：

`一句话背景/产品定位 → 本阶段 2–3 个核心问题 → 2–3 类核心动作 → 核心结果 → 收获钩子`

规则：

- 不展开每个规则；
- 只保留最强 3–4 个数字；
- 结尾可以埋“对策略产品/中台产品理解更深”等钩子，但不主动讲完。

### 二、介绍项目背景

固定逻辑：

`前序阶段做到什么 → 为什么还需要本轮 → 问题如何被调研/数据发现 → 2–3 个问题 → 本轮聚焦`

禁止：

- 重复长篇解释产品定位；
- 只罗列“问题一、问题二”而不说明问题怎么发现。

### 三、介绍项目目标

固定逻辑：

`最终目标分层 → 如何衡量 → 链路指标 → 结果指标 → 护栏 → 一句话原则`

重点：

- 先讲目标，不要一上来只讲指标；
- 中间指标与最终结果必须分清。

### 四、介绍项目动作

固定逻辑：

`前文 2–3 个问题 → 对应 2–3 类动作 → 每类一句机制 + 用户关键动作/边界 → 总结`

禁止：

- 把所有品类、阈值、异常全部塞进去；
- 团队算法策略写成用户主导。

### 五、介绍项目结果

固定逻辑：

`怎么验证 → 组合实验核心结果 → 独立实验结果 → 非 AB 的灰度/前后对比结果 → 总结`

必须明确：

- 哪个数字来自组合实验；
- 哪个来自单策略；
- 哪个来自上线前后对比。

### 六、项目中的收获是什么

固定逻辑：

`最大的两类认知 → 认知一 + 项目例子 → 认知二 + 项目例子 → 总结`

优先：

- 对目标岗位工作方式的认知；
- 对业务/中台/系统类型的认知。

不要写“学会沟通、数据分析”。

### 七、失败故事

固定逻辑：

`失败结论先行 → 情境目标 → 我的错误判断 → 为什么造成风险 → 如何发现 → 如何修正 → 结果 → 我承担什么责任 → 形成什么新习惯`

允许包含“第二次错误”，但必须压缩。

### 八、冲突故事

固定逻辑：

`冲突是什么 → 双方诉求 → 我如何把争议拆成不同问题 → 分别处理 → 最终取舍 → 后续方案 → 认知`

不要写成“我说服了对方”。

### 九、核心决策

固定逻辑：

`决策问题 → 备选/争议 → 判断标准 → 我的核心判断 → 团队最终选择 → 为什么不是理论收益最大 → 结果/后续`

没有最终拍板权时说“我提出/推动/参与收敛”。

### 十、跨团队协作

固定逻辑：

`为什么必须多团队 → 参与方与阻塞 → 我做的 2–3 个串联动作 → 资源/评审/落地 → 结果 → 协作认知`

### 十一、重来一次

固定逻辑：

`最想改什么 → 为什么 → 2–3 个具体改变 → 这些改变如何验证 → 一句话原则`

优先提升到“思考方式/流程”层面，不重复失败故事。

### 十二、未来优化

固定逻辑：

`还有 2 个方向 → 方向一：机制 + 价值 → 方向二：机制 + 核心 trade-off → 优先级/判断指标 → 总结`

未来方案必须来自细节复原稿第六章。

## 4. 口语风格

逐字稿必须：

- 优先遵循用户画像中已确认的个人语言特征，而不是统一套用下列默认口语；
- 第一人称；
- 像真实面试回答，不像 PRD；
- 使用短句和自然连接词；
- 同一段最多承载一个核心判断；
- 避免“基于上述”“如下”“分别如下”等书面措辞；
- 可以使用“我当时主要做了三件事”“这个问题核心在于”等自然口语；
- 不使用过多括号、公式和枚举编号；
- 规则参数只有在它是故事核心时才口述；
- 技术/业务术语第一次出现时用一句通俗解释，之后不重复。

## 5. 两分钟压缩器

生成初稿后强制进行 Compression Pass。

### Pass 1｜删除重复背景

如果面试题是“背景/目标/结果/动作”，不要重复完整产品定义。

### Pass 2｜只保留 load-bearing facts

数字优先级：

1. 能证明问题规模；
2. 能证明项目结果；
3. 能证明关键取舍；
4. 其他数字删除。

### Pass 3｜压缩解释

把：

“因为 A，所以 B，而 B 又会导致 C，因此我们……”
压成：
“A 会直接导致 C，所以我们……”

### Pass 4｜限制支撑点

每题最多 2–4 个主支撑点。

### Pass 5｜长度检查

建议：

- 背景/目标/结果：350–500 中文字符；
- 动作/收获/未来优化：420–550 中文字符；
- 失败/冲突/决策/协作：450–580 中文字符；
- 项目整体：500–580 中文字符；
- 硬上限：600 中文字符左右。

如果超限：

1. 删除非关键定义；
2. 删除第二层例子；
3. 删除重复结论；
4. 缩短数字解释；
5. 保留“判断—动作—结果—边界”。

目标口述时长 90–110 秒，绝不为了完整度主动写到超过 2 分钟。

## 6. 连贯性检查

每份稿件生成后检查：

- 第一段是否直接回答问题；
- 前后是否使用因果衔接；
- 是否存在“第一/第二/第三”但层级不一致；
- 每一段是否能回答“所以呢”；
- 结尾是否收束；
- 有没有把需要留给追问的细节一次讲完；
- 是否保留 1–2 个自然追问钩子。
