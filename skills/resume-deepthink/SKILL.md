# Resume Deepthink

围绕一段真实经历逐层追问，先建立事实证据，再训练用户形成可口述、可追问、能守住个人贡献
边界的项目表达。不得替用户编造职责、数字、技术细节、决策权或业务结果。

运行本 Skill 内任何相对路径前，先从当前 `SKILL.md` 定位 Skill 根目录。

## 前置读取

1. 完整读取 `references/questioning-and-output.md`。
2. 从本 Skill 根目录定位兄弟 `offerloop-workspace`，完整读取其
   `references/artifact-contract.md`。
3. 读取 `lark-wiki` 和 `lark-doc` Skill；需要读取关联 Base 时再读取 `lark-base`。
4. 运行共享 `artifact_contract.py` 检查 `current_resumes` 和
   `resume_deepthink` 目录。
5. 目录或 schema v4 未就绪时，路由到 `offerloop-setup` / `offerloop-workspace`。首次创建
   节点前展示目标并取得确认。

## 确认方向与简历

1. 开始深挖前，先询问并确认这份简历的目标投递岗位和投递方向。用户已经给出时也要复述确认，
   不把文件名中的词当作用户选择。
2. 列出 `01｜当前简历` 中的版本，让用户选择；用户给出版本名时按标题精确匹配。
3. 零命中或多个同名文档时停止并消歧，不自动取“最新版”。
4. 读取选定简历全文。只有用户要求续写、复习或避免重复追问时，才读取与同一简历版本匹配的
   既有简历深挖文档。
5. 可按需读取用户提供的目标 JD；不得读取历史简历、其他个人材料或无关训练文档。

## 深挖流程

1. 列出本次要处理的经历，一次只聚焦一段。
2. 第一个问题必须让用户完整介绍项目。不要先展示 STAR、标准答案或完整问题清单。
3. 按背景、目标、动作、结果依次补齐主干，同时追问个人职责、证据口径和团队边界。
4. 主干形成后，依次覆盖六类问题：方案实现细节、异常问题归因、决策判断权衡、项目推进经历、
   产品价值拔高、个人规划认知。每类至少提出一个与该项目相关的问题，不得跳过。
5. 每轮只问一至三个紧密相关的小问题。用户答不上一个大问题时，将其拆成更小的事实问题并
   提供回忆角度；围绕同一大问题最多追问三轮，随后记录缺口并继续，不得逼迫用户编造。
6. 追问必须引用用户前文，围绕“你亲自做了什么、为什么这样做、如何验证、结果如何归因”
   推进；不得机械念题。
7. 每完成一个主题，简短复述“已确认事实 / 待确认信息 / 个人贡献边界 / 高风险表述”，让
   用户纠正。只有用户确认后才标记为 `confirmed`。
8. 六类覆盖完成后，检查问题地图与主干缺口；只补问影响成稿可信度的内容。

## 成稿与迭代

1. 先生成 1 分钟和 3 分钟项目介绍，再展开背景、目标、动作、结果。
2. 按六类问题归档；每个问题必须保留用户原始回答，并分别给出回答诊断和 AI 参考逐字稿。
3. 参考逐字稿优先使用已确认事实。事实不足时明确输出“回答框架”或“示范回答”，不得伪装
   成用户经历。
4. 用户不满意时允许其直接修改 Markdown；事实变化必须重新确认，不得把措辞调整当成新事实。

## 完成与保存

用户完成或明确提前结束时：

1. 用共享脚本生成并保留 `run_id`、标题和目标目录。
2. 按 reference 生成完整 Markdown；完整运行标记 `completed`，明确提前结束标记
   `incomplete`。
3. 用共享脚本校验 Markdown，再通过 `lark-doc` 保存到 `02｜简历深挖`。
4. 文档产物信息必须包含简历版本名、目标投递岗位和投递方向，标题也要能辨认对应简历版本。
5. 从本轮追问中整理值得继续准备的候选面试题，展示题目和理由并询问用户要加入哪些题。
6. 只把用户确认的题交给 `interview-question-bank`；本 Skill 不直接修改题库。
7. 保存失败时仍在对话交付完整 Markdown 和原 `run_id`，明确说明未保存；重试不得生成新
   `run_id`。

普通暂停不生成正式文档。不直接改写用户简历。
