# 笔面试中心单表与视图契约

`OfferLoop 笔面试中心` 只使用一张物理数据表 `笔面试安排`。视图不复制记录；用户在任一视图
编辑字段时，修改的是同一条物理记录。

## 字段

字段顺序与类型以 `recruiting-reminder/SKILL.md` 的“笔面试中心数据契约”为准。禁止创建
`子表 record_id`，也禁止为环节创建同名物理表。

## 受管视图

| 视图 | 筛选 |
|---|---|
| 全部安排 | 无筛选 |
| 笔试 | `环节` 包含 `笔试` |
| 群面 | `环节` 包含 `群面` |
| 一面 | `环节` 包含 `一面` |
| 二面 | `环节` 包含 `二面` |
| 三面 | `环节` 包含 `三面` |
| HR 面 | `环节` 包含 `HR面` |
| 其他面试 | `环节` 包含 `面试（轮次待确认）` |

筛选必须落在 `笔面试安排` 的 view 上。按 `lark-base` 的 tuple DSL 表达时，单值视图使用：

```json
{"logic":"and","conditions":[["环节","intersects",["一面"]]]}
```

`其他面试` 使用：

```json
{"logic":"and","conditions":[["环节","intersects",["面试（轮次待确认）"]]]}
```

所有受管视图统一按 `开始时间 desc, 截止时间 desc, 公司 asc` 排序。修复视图前先读取现状，
只改受管筛选与排序，不删除用户自定义视图。

## 已有七表结构迁移

线上迁移必须单独取得用户确认，本仓库模板更新不自动改动现有 Base：

1. 只读列出现有 `全部安排` 与六张环节表，记录真实 table ID、字段、记录数、workflow 和视图。
2. 以旧 `全部安排` 为优先事实源；按 `来源邮件ID` 去重，并用旧 `子表 record_id` 只做迁移核验，
   不把该字段写入新表。
3. 创建或复用 `笔面试安排`，逐批写入并回读核验字段、记录数、文档链接、日历 ID 与完成状态。
4. 创建上述八个受管视图，验证同一 record ID 在不同视图修改后无需同步即可看到相同值。
5. 将 `reminder_base_url` 和运行时 `REMINDER_TABLE_ID` 切换到 `笔面试安排` 的 `全部安排`
   视图，把六条子表 workflow 替换为一条单表 `完成状态` workflow；发布和启用遵守妙搭自动化
   状态门禁。
6. 完成合成事件、卡片和求职进展验收前，旧表与旧 workflow 保持停用但不删除。只有用户再次
   明确批准删除并确认备份后，才清理旧表。

如果旧主表与子表同一事件的状态不一致，迁移时不得猜测。报告 record ID、两个状态和来源，等待
用户选择最终值后再写入单表。
