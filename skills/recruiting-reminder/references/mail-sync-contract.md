# v2.0.0 邮件事务与外部联动契约

## 状态与主事务

字段定义以 `event-schema.md` 为准。高置信度新事件的顺序固定为：

正文抽取至少包含 canonical `source_mail_id`、来源链、`message_kind`、事件类型/原始环节、公司、
岗位、开始/结束/截止原文、归一化为带时区 ISO 时间的邮件 `received_at`、`delivery_mode`、平台、链接、备注、`classification` 与
`uncertain_fields`；`classification` 只表示是否属于招聘事件，考试类型不确定使用 `exam_type`，不得
复用 `classification`；邮件写了预计用时时额外传
`estimated_duration`，要求预约/选时间时传 `requires_time_selection=true`。补测传
`message_kind=retest`。

截止原文写“72 小时内”等小时表达时，从 `received_at` 精确相加；写“N 个工作日内”时，邮件
日期不计作第 1 天，从下一天起按中国大陆法定工作日计数，包含调休工作日，排除周末和法定节假日，
落在第 N 个工作日 23:59 Asia/Shanghai。只有日期时按当天 23:59；原文缺年份时结合 `received_at`
取最近的未来日期。读取 `china-workdays.json`；
超出已发布并收录的年份必须停止并报告，不得退化成只排除周末。

先识别前置邀请：需要用户预约、选择或确认面试时间且没有给出明确开始时间的邮件，规划器返回
`action=skip_and_mark_processed` 和唯一的 `required_actions`。该结果是待执行命令，不是完成状态；严格按以下
顺序收尾：

1. 实际调用当前邮件提供方的 `mail.mark_processed`，传入 canonical `source_mail_id`。工具不存在的
   原生 IMAP 脚本模式才执行 `state_store.py mark-processed`，因为该文件是 `fetch_mail.py` 的来源状态；
2. 只有工具成功响应后，才用 `record-mail-outcome` 保存 `skipped_preliminary`；
3. 核验成功后结束，不写 Base、不建日历、不通知或询问。

本地 `processed_emails.json`、`mail_outcomes.json`、模型回复里的 `processed=true` 或“已处理”文字，都
不能代替运行环境已提供的 `mail.mark_processed` 调用。邮件工具失败时按临时错误规则当场最多尝试
3 次；仍失败则记录精确失败步骤并告知用户，不得保存 `skipped_preliminary` 或声称已经处理。
所有扫描分支共用最终关闭门：在最终回复、通知摘要或运行环境 finalize 前，比对本轮应处理来源与
成功的 `mail.mark_processed` 响应；存在差集时必须先补调用，差集非空时不得 finalize。
等包含明确时间的正式通知再处理；正式通知引用该来源时按新事件
创建，不按缺失原 Base 事件报改期歧义。来源链在 Base 未命中时先用 `get-mail-outcome` 查询被引用
ID，并把结果放进规划器 `source_outcomes`。若邮件只是要求确认
是否参加但已经给出明确时间，仍作为正式面试。

1. 来源去重与唯一关联；同一来源命中多条 Base 记录也属于歧义，需要确认时当轮停止该事件。
2. 每个外部写入先生成稳定幂等键并调用 `begin-operation`。已有 `pending` 时先按业务键回读外部
   状态，不得盲写；已有 `succeeded` 时 no-op。
3. 创建或更新 `笔面试安排`；Base 新建使用来源邮件 ID 派生的稳定 `client_token`，初始明确写
   `完成状态=待完成`、`日历状态=待安排`。Base 失败时不执行后续动作。
4. Base 成功后，先按每个精确记录 ID 执行 `progress.read_current` 并用新读到的状态重算补丁，再更新
   求职进展，最后执行日历，不能交换、并发或跳步。Base 写入前的 `progress.query` 不能代替写入后的
   当前值读取；邀请写规范待办状态，例如一面邀请写 `待一面`。固定事件按招聘方时间建/改
   日历，成功后立即将真实 event ID 和 `日历状态=已建日程` 回填同一 Base。异步邮件只保存真实
   截止和时长，邮件里的开放时间不作为个人计划，只有用户卡片回调传 `planned_by_user=true` 后才
   创建/更新日历。
5. 回读核验 Base、进展和日历最终状态，并以 `base.verify_views` 确认所有视图仍来自同一物理表后标邮件
   已处理；存在最终失败时由失败清单管理该来源，普通扫描不得重新执行
   已成功部分。写完失败清单后才结束，避免中断后既被跳过又没有失败记录。
6. 核心状态完成并核验后，按已授权配置发送至多一条脱敏摘要；通知是最后一个非回滚分支。

若 `lark-base` 的便捷 upsert 不能把规划器 `base_plan.client_token` 传给创建接口，改用同一 Skill
提供的原子 OpenAPI 创建，并在响应不明确时按 `来源邮件ID` 回读；不得退化为无令牌的“先查再建”。

求职进展或通知失败不回滚 Base。每个外部写步骤成功后立即通过 `scripts/state_store.py record-success`
保存幂等键和最小结果引用，供当前执行
重试或以后用户手动重试；已处理邮件必须调用当前邮件提供方的 `mail.mark_processed` 写入；只有
未提供该工具的原生 IMAP 脚本模式才使用 `state_store.py mark-processed`。非招聘邮件、永久忽略邮件和
已跳过的前置邀请也要写入。

面试、测评和笔试统一采用邮件时长优先级：明确单值时使用该值，区间取上限；完全没写时面试默认
60 分钟、测评/笔试默认 90 分钟。归一化分钟数始终写入 `预计时长（分钟）`；异步事件首次排期
使用该字段，后续调整优先保留原开始/结束时间差。

## 来源链与幂等

- `来源邮件ID` 永远保留首封 canonical ID；新 ID 去重追加到 `关联邮件ID`。
- 同一 ID 已存在时 no-op。
- 唯一命中的普通提醒只追加 ID 并标已处理，不改业务状态、日历或重复通知。
- 来源链唯一命中的改期更新原 Base 与 `已建日程ID` 对应日历。
- 来源链唯一命中的取消写 `事件状态=已取消`，取消原日历并保留 ID；不改完成状态或求职进展。
- 来源链无法唯一命中时确认，不用公司和环节猜测。
- 拼多多补测是明确例外：唯一原测评存在时只更新该记录的链接、真实截止与关联邮件 ID；多条原
  测评时确认，没有原记录时才创建新测评。

## 进展与日历

邀请待办顺序：待测评 < 待笔试 < 待群面/待一面 < 待二面 < 待三面 < 待面试 < 待 HR 面 < 待 OC。
完成节点顺序：投递完成、测评完成、笔试完成、群面完成、一面完成、二面完成、三面完成、面试完成、
HR面完成。邀请到达时才按待办顺序推进；“已完成”不是下一轮邀请，普通活跃申请完成当前事件后
统一写 `进展状态=待反馈`，同时单调推进 `latest_completed_node`。完成较早事件时保留更晚完成节点；
Offer、未通过、主动放弃、岗位关闭等人工终态状态不得覆盖；已错过、已取消不修改求职进展。

完成状态回调必须先读精确提醒和全部 `求职记录ID` 当前值，再写提醒，再写进展，最后依次执行提醒
与进展回读核验。核验只能使用写后的返回状态；不得用写前读取代替。人工终态保留状态，已有更晚
完成节点也保留。例如二面完成后，普通 `待二面` 申请写为 `二面完成 + 待反馈`，不能写 `待三面`。

公司级无岗位笔试在 Base 写入前必须执行求职进展查询；关联集合是同公司全部活跃记录的精确 ID，
排除所有人工终态，并把排除的终态 ID 保留在规划证据中。不得把岗位名称、可读标签或模型生成别名
写入 `求职记录ID`。没有执行查询就不能写该事件。

固定事件即使冲突也按招聘方时间创建，不自动移动。异步计划结束不得晚于真实截止。任何已有计划
必须按原 `已建日程ID` 更新。邮件改期时，原记录已有计划时间但缺 ID 应停止并报告，不能创建第二个
日程；每日卡片为尚未排期或历史缺 ID 记录首次建日程时，按 `daily-card-contract.md` 的恢复流程执行。
邮件日历统一使用用户配置的目标日历和原生 `idempotency_key`，不自动创建飞书会议或默认提醒；
新建成功后按规划器 `result_mapping` 把响应中的真实 `event_id` 回填到 `已建日程ID`，不得写占位值；
描述只写平台、参与链接、必要提醒和 OfferLoop 幂等标记，不复制邮件正文。改期冲突检查必须排除
该记录自己的 `已建日程ID`。取消成功后回填 `日历状态=已取消` 并保留日程 ID。
若 `lark-calendar` 的便捷创建命令不能同时控制原生幂等键、会议和提醒字段，就使用其原子 OpenAPI
入口提交规划器给出的最小 payload，不得接受便捷命令附带的默认飞书会议或提醒。
固定事件发现冲突时，脱敏摘要的 `warning` 明确写“招聘事件已按原时间创建，请调整原有日程”；
不得省略冲突提醒，也不得自动移动招聘事件。

## 失败与手动重试

外部写操作遇到临时错误时当场重试，包含首次尝试最多 3 次。三次仍失败后：

- 保存 run ID、来源邮件/事件 record ID、失败步骤、幂等键、错误类别、时间和已成功步骤；不保存正文或凭证；
- 将相应日历操作写为 `操作失败`（Base 已存在时），并向用户报告；
- 不启动每 30 分钟检查、定时对账、后台补偿或任何后续自动运行。

只有用户明确要求重试刚才失败内容时，才按失败清单逐项恢复；先回读目标当前状态，已成功项 no-op，
只执行失败步骤，每个步骤仍最多尝试 3 次。全部失败项补齐后先 `mark-processed` 再
`resolve-failure`；不得全表扫描或重复创建。
若发现写前意图仍为 `pending`，先按 Base 来源 ID、日历幂等标记或消息发送结果核实；能证明成功则
补记 success，能证明未发生才标 failed 并允许手动重试，无法判断时报告结果未知且不得盲重发。

## 飞书消息通知

`notifications` 与每日卡片配置相互独立。只在 `status=enabled` 且接收方、模板和身份已持续授权时
发送；实际操作前读取 `lark-im` Skill。摘要不含正文、邮箱、Message-ID、UID、凭证或未确认候选；
超过 10 条只发计数与最近截止的 10 条；统一通过 `scripts/notification_summary.py` 生成。本轮无新增/
更新不发送。发送前以扫描 run ID 原子 claim，发送工具使用
`offerloop-recruiting-reminder-<扫描 run ID>` 作为幂等键；未取得 claim 时 no-op，同一轮重试逐字复用
该键。发送成功后写 sent。API 明确
返回“未发送”时可视为已核实目标群中不存在该消息，执行 `release-notification --verified-absent`
供本次显式重试；通知失败不回滚其他结果。只有明确收到发送失败时才释放 claim；若进程
在发送后、写 sent 前中断，claim 保持 `sending` 并按结果未知处理，手动重试也不得擅自重发，以免重复通知。
结果未知时让用户先检查目标群：确认已存在则 `mark-notification`；确认不存在后才允许执行
`release-notification --verified-absent` 并重试。
