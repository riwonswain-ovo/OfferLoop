# v2.0.0 每日群卡片契约

`daily_checkin` 独立于邮件扫描通知，固定在 `22:10 Asia/Shanghai` 发送 Card 2.0。群成员可查看，
只有配置的 owner open_id 可以操作。没有待完成事件时仍发送“今日没有待完成事件”和简短祝福。
单卡最多放 25 条事件，超过时按分组顺序拆成多张卡，保证所有待办都展示且不超过 Card 2.0 的
200 元素上限。每张卡使用“群 ID + 上海日期 + 分页序号”生成不超过 50 字符的稳定消息幂等键，
并在 `OfferLoop运行状态` 逐页记录发送中、已发送、失败或结果未知。已发送页永久跳过；结果未知页
先由用户核实群消息，不能盲重发。因此不能只依赖飞书一小时内的 UUID 去重窗口。
核实已发送时把该页账本改为 `已发送`；确认群内不存在时才改为 `发送失败`，随后手动重试只发送
未成功页。不得删除账本记录来绕过去重。
Python 规划器、独立 JS Runtime 与妙搭 TS 模板必须共同通过
`contracts/daily-checkin-cases.json`，修改任一实现时同步验证三端。

只读取 `事件状态=有效 && 完成状态=待完成`，互斥分组：

1. 今天计划完成；
2. 计划结束已过、真实截止未过；
3. 真实截止已过（最高优先级）。
4. 尚未安排计划时间的异步测评/笔试。

不统计今日已完成。异步的今天计划事件提供“已完成”“暂未完成”；异步测评/笔试点“暂未完成”后才显示
日期和开始时间，结束时间优先保留原计划时长；没有原计划时读取 `预计时长（分钟）`，历史记录连
该字段也没有时才默认 +90 分钟。尚未排期事件可直接点“调整日程”。第一次点击只打开日期和开始
时间表单，不执行时间计算；无效、过去或超过截止的选择以卡片提示返回，不得产生 HTTP 500。调整后不得晚于
真实截止；有个人冲突时警告并让 owner 确认。固定事件不可调整，始终提供“已完成”“标记已错过”。真实截止已过仍保留这两个按钮，
是否错过只能由 owner 点击。

“已完成”写 Base 并推进求职进展；“已错过”只写 Base。尚未安排计划时间或历史记录缺
`已建日程ID` 时，owner 选定开始时间后先回填稳定 pending 键，再按该键查找已有日程；未找到才创建并
回填真实 ID；创建请求同时把该稳定键作为飞书日历原生 `idempotency_key`，避免并发双击或“日程成功
但 Base 回填失败”后重复创建。已有真实 ID 时只更新原日程。
回调必须携带完整 Base record ID，以 record ID + 动作 + Base `last_modified_time` 作为一次状态变更的
幂等键，校验 owner、回读精确记录，并根据
当前时间、事件状态、完成状态和分组重新计算该动作是否仍可执行；不得信任卡片中旧的 group，也不得按
标题或邮件 ID 扫描全表定位。Base workflow 与卡片回调推进同一条求职进展前，必须在
`OfferLoop运行状态` 用同一稳定键原子 claim；`待执行` 只允许一个 owner，成功永久 no-op，失败仅由
显式重试接管，避免两个入口并发执行。
冲突检查必须排除该记录当前 `已建日程ID`，避免把事件自己的旧时间识别为冲突。日历描述写平台、
参与链接和必要提醒，不复制邮件正文，也不自动创建飞书会议。
如果 Base 已标为已完成而求职进展联动失败，再次点击只重试幂等的求职进展联动，不重复写 Base；
Base 状态写入或求职进展联动最终失败时，卡片必须指出具体失败步骤并提供手动重试按钮。

日历查询、创建或更新的临时错误在当前回调内最多尝试 3 次；仍失败则写 `日历状态=操作失败`，在
原卡片展示手动重试按钮并告知用户，之后不自动补偿。只有 owner 主动点击或用户明确要求重试时，才
按原回调幂等键、pending 键与日程 ID 只补失败步骤。
