# Job Collection 通知与待确认写入状态

本文件定义「信息源登记」中的持久化待确认状态、Agent 简版回复和固定飞书群通知。群消息是持久化状态的展示投影，不是恢复真源。实际发送前读取 `lark-im` Skill。

## 1. 固定群

固定群、机器人身份和权限由初始化流程配置并验证。日常同步读取现成的 `target_id` 和 `identity`，不临时选择或切换群。

固定群配置缺失或权限失效时保留已写入数据、旧正式游标和恢复检查点，转入初始化修复。初始化同步、增量同步、零新增、部分完成、失败和待确认写入都发送通知；清单查询和纯结构审计不发送。

## 2. 持久化状态

每个来源在「信息源登记」保存：

- `待确认状态`：`无待确认` 或 `等待确认`；
- `待确认批次数据`：包含内部批次 ID、稳定编号、完整标准化候选快照、来源 ID、来源记录 ID、来源高水位、恢复检查点、决定、处理状态、已提交来源，以及通知 run ID、阶段、内容哈希和成功分片；
- `同步状态` 与 `恢复检查点`。

一次同步的所有来源共用一套连续编号。保存时使用 `to_source_json` 把状态拆到对应信息源行；新同步开始前使用 `merge_source_json` 合并同一批次。来源行的通知内容哈希必须一致；某次持久化中断造成成功分片不一致时合并其并集。存在未决编号时重建一张合并清单，不读取群历史，也不扫描新岗位。来源片段批次 ID 冲突、来源重复、编号重复或消息内容哈希冲突时暂停恢复并报告状态损坏。

「待确认批次」视图固定筛选 `待确认状态=等待确认`，只显示存在未决候选的来源。`scripts/sync_pipeline.py` 从这些字段恢复批次；写入回读成功后标记候选，全部候选处理完后记录完成通知结果，再逐来源开放正式游标提交。全部来源提交成功后清空候选明细与待确认状态；`last_sync_result` 保留最终计数。

## 3. 状态标题

按以下优先级选择标题：

1. 待确认写入数大于 0：`招聘信息待确认写入`；
2. 无待确认写入，且部分来源成功、部分失败：`招聘信息部分完成`；
3. 无待确认写入、没有成功来源且存在失败：`招聘信息同步失败`；
4. 其余情况：`招聘信息同步完成`。

## 4. Agent 简版模板

```text
<状态标题>

已写入 N 条｜待确认写入 N 条｜失败来源 N 个
```

按条件追加：

```text
失败来源：来源名称｜失败原因｜恢复状态
请查看飞书群中的待确认写入清单，并在这里回复要写入或跳过的编号。
飞书群通知发送失败：原因
```

多个失败来源各占一行。群通知成功不显示通知状态；不附目标 Base URL；不在 Agent 对话重复候选详情。零新增仍发送完成摘要。

## 5. 飞书群模板

无待确认候选时发送与 Agent 相同的摘要和失败来源。

有待确认候选时按整条飞书消息的最大长度拆分，标题、摘要、失败来源、页码、候选和回复提示都计入长度：

```text
招聘信息待确认写入

已写入 N 条｜待确认写入 N 条｜失败来源 N 个
创建时间：YYYY-MM-DD HH:MM

待确认写入 1/2
01｜公司名称｜招聘岗位｜待确认原因｜[公告](URL)｜[投递](URL)
02｜公司名称｜招聘岗位｜疑似重复｜公告缺失｜[投递](URL)

请回到 Agent 对话，回复“全部写入”“全部跳过”或指定编号。
```

编号在全部来源和消息分片中连续。内部批次 ID 不向用户展示。岗位或链接缺失时使用“岗位未明确”“公告缺失”“投递缺失”。公司、岗位、原因和失败文字先转为单行安全文本；链接只接受带主机名的 HTTP/HTTPS URL，并编码 Markdown 结构字符。来源内容不能新增标题、链接或消息指令。

部分处理后只展示剩余编号：

```text
待确认写入更新

已写入：01、03｜已跳过：02｜剩余 2 条
04｜公司名称｜招聘岗位｜待确认原因｜[公告](URL)｜[投递](URL)
```

全部处理后发送：

```text
待确认写入已完成

已写入 N 条｜已跳过 N 条
```

## 6. 回复语义

使用 `scripts/sync_pipeline.py` 解析明确动作：

- “留下”“写入”“保留”表示写入；
- “不要”“跳过”表示跳过；
- “先别处理”“晚点再看”保留未决项并继续阻止新同步；
- “除了 03 都留下”等排除式表达只对有效编号执行；
- 含糊回复、编号不存在或动作互相冲突时不改变状态，并请用户重新确认。

处理写入动作前逐条复核来源记录，并把本次复核结果传给 `plan_confirmation_decision`；缺少复核结果时脚本不生成写入动作。该函数只生成本轮安全动作，实际写入和回读成功后调用 `mark_write_verified`；跳过调用 `mark_skipped`。写入或回读失败时编号仍保持未决。

## 7. 发送、重试与游标

开始发送前创建并持久化 `NotificationState`。`run_id` 在整个同步及恢复期间保持不变；阶段固定使用 `summary`、`pending-initial`、`pending-update-<revision>` 和 `completion`。调用 `prepare(stage, messages)` 固定每条消息的 SHA-256 内容哈希，并生成 `offerloop-job-collection-<run_id>-<stage>-<part>`。同一分片重试复用该键，内容变化必须创建新的更新 revision，不能覆盖既有阶段。

待确认批次把 `NotificationState` 保存到每条来源的 `待确认批次数据`；每个分片发送成功后立即调用 `mark_succeeded()`，再把更新后的状态写回该批次全部来源行。无待确认候选（包括零新增、部分完成和失败摘要）把相同状态保存到各来源 `恢复检查点`。任务恢复时先读取状态并调用同一阶段的 `prepare()`，只发送返回的未成功分片；不得仅因任务重启生成新 run ID。

通知临时失败最多重试三次。全部候选处理完成且完成通知成功后调用 `mark_completion_notification_succeeded`；随后只提交 `committable_sources` 返回的来源与高水位，每次成功调用 `mark_source_committed`。持续失败时：

1. 保留已成功写入的数据；
2. 不提交受影响来源的正式游标；
3. 保存恢复检查点和待确认状态；
4. 在 Agent 对话说明数据结果与通知故障；
5. 下一次从旧正式游标重扫、去重并补发。

群消息不得包含凭证、token、Cookie、完整错误堆栈或用户私人画像。
