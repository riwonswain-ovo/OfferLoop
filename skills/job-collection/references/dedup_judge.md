# 跨来源招聘信息去重

本规则只处理用户登记的飞书 Base 和腾讯 Smartsheet。主表与分类子表之间的双写不是重复；去重只判断目标主表中是否已存在同一招聘条目。

## 判定顺序

1. 规范化 `投递链接` 完全一致：`high` confidence 重复。
2. 规范化 `公告链接` 完全一致：`high` confidence 为同一来源条目。
3. URL 不同：比较规范化公司、招聘批次、招聘项目和公告标题。
4. 同公司不同真实批次，例如“暑期实习”和“秋招提前批”：不是重复。
5. 公司或批次无法确认：低置信度，不自动合并。

URL 规范化应移除普通页面锚点和常见跟踪参数，但必须保留影响资源定位的业务 query 与 hash route
（例如 `#/jobs`、`#/ey=<岗位标识>`）。可复用 `scripts/sync_utils.py`。

## 与目标主表比较

普通增量同步先从来源窗口得到候选，再对目标主表做定向查询并建立本批索引：

- 用候选原始 `投递链接`、`公告链接` 和公司分块构造服务端 OR 等值过滤；每块最多 10 个条件，
  避免 Base 在大条件块中忽略尾部条件；返回后再规范化 URL 建索引。
- 对未命中链接的候选，按候选公司使用 `+record-search` 定向查询，再在本地复核
  `公司 + 招聘批次 + 招聘项目/标题` 指纹。
- 查询字段必须包含 `投递进度`、`信息更新时间` 和主子表 record ID，以继续复用历史终态和映射。
- 命中主记录后只按其 `子表 record_id` 定向回读对应子记录，不默认读取整张子表。

两个来源按同一份索引处理。每写入一条记录后立即更新内存索引，避免同一轮两个来源互相重复写入。

只有用户显式要求 `--full-audit` 时才完整读取企业主表和五张子表，检查孤儿、反向映射、错表和
状态不一致。

## 明确重复

命中已有记录时直接按重复跳过，不更新已有业务字段。主子表映射异常属于写入恢复问题，按
`failure-handling.md` 修复，不把映射修复解释为新岗位同步。

## 不确定冲突

中低置信度冲突进入待确认写入，不自动合并、删除或写入。群消息按 `notification.md` 使用稳定编号、
公司、岗位、待确认原因和两个链接；Agent 对话只提示数量。

用户明确判为同一条后按重复跳过；判为不同条后再新增。

## 语义复判输出

需要语义复判时只输出：

```json
{
  "is_duplicate": true,
  "confidence": "high",
  "reason": "公司、届次、批次和项目一致，仅来源页面不同"
}
```

`confidence` 仅允许 `high`、`medium`、`low`。只有 `high` 且
`is_duplicate=true` 时自动按重复跳过；`medium`、`low` 或结论冲突都进入待确认写入。
