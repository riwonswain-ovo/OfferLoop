# Interview Prep

以用户真实投递材料和本轮 JD 为核心生成准备文档。不要用“最新简历”替代实际投递简历，
不要提供与用户经历无关的万能答案。

运行相对路径前先从当前 `SKILL.md` 定位 Skill 根目录。

## 前置读取

1. 完整读取 `references/preparation-template.md`。
2. 完整读取 `references/quality-gates.md`。
3. 完整读取 `references/interview-source-search.md`。
4. 完整读取 `references/round-preparation.md`。
5. 完整读取 `references/answer-logic.md`。
6. 定位兄弟 `offerloop-workspace`，完整读取其 `references/artifact-contract.md`。
7. 定位兄弟 `recruiting-reminder`，完整读取其 `references/event-contract.md`。
8. 读取 `lark-wiki`、`lark-doc`、`lark-base` Skill。
9. 检查 `current_resumes` 和 `interview_prep` 目录；首次创建节点前展示目标并取得确认。

schema v4、依赖或权限未就绪时路由到 `offerloop-setup`，不要自行扩大权限。

## 确认事件和材料

1. 用户给出事件链接或 record ID 时优先使用，并展示公司、岗位、环节、时间供确认。
2. 否则调用 `recruiting-reminder/scripts/event_lookup.py resolve --json` 获取候选；不得复制其
   公司/岗位匹配规则。唯一候选也要展示确认，多候选让用户选择；零候选时从求职进展中列出
   公司/岗位候选，让用户选择精确记录，不按名称猜。
3. 使用 `lark-base` 读取事件关联的 `求职进展` 记录，至少取得 `公司`、`投递岗位`、
   `岗位 JD`、`投递简历版本` 和 `投递记录 ID`。求职进展是 JD 与简历版本的事实源。
4. 同时读取笔面试中心的 `投递简历版本` 供用户核对；两边非空但不一致时展示冲突并让用户
   确认，不自动覆盖任一 Base。准备内容仍以用户确认后的求职进展记录为准。
5. `岗位 JD` 为空时要求用户先补充或直接提供；不得用招聘公告中的聚合岗位文本冒充 JD。
6. 按 `投递简历版本` 在 `03｜当前简历` 中精确匹配标题并读取全文。字段为空、零命中、重名
   或用户认为选项有误时停止并让用户修正；不得用其他版本或“最新简历”替代。
7. 读取同一求职记录中可用的上一轮准备和真实面试复盘；按需读取同一简历版本的简历深挖文档，
   默认不读取其他个人材料或无关历史。
8. 笔试事件停止本流程；本 Skill 不生成面试准备文档。

## 判断准备条件

开始研究前把输入分为“已确认”“可推断”“待补充”，至少检查公司、岗位、JD、实际投递简历、
面试环节、时间和可用经历证据。

- 能从事件或现有材料确定的信息直接使用，不重复询问。
- 能通过官方或可靠公开来源补齐的信息先检索，并标注推断依据和置信度。
- 按事件中的轮次名称直接应用 `references/round-preparation.md` 的固定深度：一面为 +1 业务面，
  二面为 +2 业务面，三面如有为 VP 面，最后为 HR 面。
- 默认从业务一面开始，不设置或生成 HR 初筛。
- 一场已确认面试生成一份文档；轮次不明时只做通用准备，不虚构一面、二面或 HR 面流程。
- 缺少非关键素材时继续生成降级版本，把影响和补充动作写清。
- 缺少目标岗位、JD/岗位画像或简历正文等硬输入，无法可靠生成时只询问最少必要信息。

## 研究与生成

先拆解 JD 的必备能力、加分项和风险，再检索公司官网、招聘公告、财报、官方产品与可靠行业
资料。

按照 `references/interview-source-search.md`，通过用户已有登录态的浏览器分别检索小红书和牛客。
优先同公司、同岗位、同业务线、同环节且时间接近的面经；提取真实问题、追问链、考察点、面试
反馈和可复用提醒，去重后保留来源编号。面经只作辅助证据，标记时效和不确定性。禁止把简历、
ASR、联系方式或私人素材输入搜索框或上传到这些平台。

把每项 JD 要求和面经问题映射到用户已确认经历；证据不足时写“缺口/待补”，不编造匹配点。

为实际投递简历的每个经历要点分配文档内编号。业务面至少为所有可见要点准备事实层口径，并
按照本轮深度重点展开核心经历；HR 面不机械逐条展开，但必须检查动机、履历和时间线一致性。

对数字、强动词、角色边界和技术实现做证据审计。无法确认的内容不得补造数字或细节；应明确
记忆或证据边界，并准备基于已确认事实的诚实回答。按固定轮次模型调整题目权重和回答深度。

按 reference 生成一份适合本轮直接练习的 Markdown。除产物契约要求的标题和简短产物信息外，
正文第一个章节必须是本轮自我介绍。随后列出本轮面经问题；每道采用的问题必须关联来源编号、
本轮深度、考察点、用户经历或简历要点、口语参考回答、证据边界和可能追问。

自我介绍和每道参考回答都必须遵守 `references/answer-logic.md`：先给一句话结论，再列 3–5 个
记忆关键词，标明归纳或演绎逻辑并用箭头写出逻辑骨架，最后给出口语回答。表达自上而下、支撑
点保持同层，避免把原因、动作、结果和例子混在同一组。

在面经问答后执行本轮完整性审计，分别检查面经检索、JD 能力、投递简历、本轮题型、回答深度
和风险口径。发现缺口时生成明确标记为“补充题”的问题及个人参考回答，不得伪装成面经原题。
把面试前快速复习清单放入完整性相关章节，不再输出冗长的独立研究报告。

文档最后一个二级标题必须是“面经原始链接”，按平台列出本轮实际读取并采用的面经直达链接、
发布日期或页面显示时间、岗位/环节相关性及读取时间。不得只给搜索结果页，不得遗漏正文中引用
过的面经来源。

## 交付前检查

完整执行 `references/quality-gates.md`。红线失败时不得交付；核心要求因材料缺失无法满足时，
生成明确标注缺口的降级版本，不得把它称为完整准备。质量检查过程默认只内部执行，不把模板
勾选项原样塞进用户文档。

## 保存与回填

1. 生成 `run_id`、标题和 Markdown，通过质量检查及产物契约校验后保存到固定的
   `04｜面试准备/面试准备文档`；文档必须记录求职记录、岗位 JD 来源和投递简历版本。
2. 独立任务只保存文档，不创建或猜测 Base 记录。
3. 已确认事件通过 `event_lookup.py backfill --kind prep` 回填“面试准备文档”；只传主表
   record ID、明确子表 record ID、文档链接和 `run_id`。
4. 面试类事件同步回填主表和对应子表；“面试（轮次待确认）”只回填主表；笔试不回填。
5. 部分失败时保留已成功写入，并记录精确 record ID 供同一 `run_id` 补偿。
6. 从准备过程整理候选题，向用户确认哪些题要加入统一面试题库；只把确认题交给
   `interview-question-bank`，不得直接修改题库。
7. 保存失败时交付完整 Markdown 和原 `run_id`，不得声称已写飞书。
