# 面经、公司与岗位资料检索规范

## 安全

使用外部平台前读取并遵守对应浏览器 Skill。使用用户已有登录态，不读取或导出 cookie、密码或
会话文件。验证码、风控和人工确认必须由用户处理。

不在外部搜索框输入简历、经历深挖、联系方式、面试邀请、ASR 或其他私人内容。只做本轮所需的
小规模检索，不批量爬取。

## 动态选择来源

先根据 `role-adaptation.md` 的岗位画像选择来源，不把小红书和牛客视为所有岗位的强制事实源。

| 场景 | 优先来源示例 |
|---|---|
| 中国互联网、技术、产品、运营、校招 | 牛客、小红书、公司招聘官网 |
| 外企或海外岗位 | 公司 Careers、Glassdoor、LinkedIn 公开内容 |
| 咨询、金融、财务 | 公司官网、监管披露、专业协会、行业研究 |
| 制造、供应链、工程 | 年报、产品/技术资料、行业协会、产业研究 |
| 法务、合规、公共事务 | 官方法规、监管机构、专业协会、公司披露 |
| 设计、市场、品牌 | 官方作品/案例、品牌资料、专业社区、作品平台 |
| 科研、研究岗位 | 实验室/机构官网、论文、研究项目和专业社区 |

表中平台只是示例。只能使用当前可访问且与目标岗位高度相关的来源。

中国招聘场景下，小红书和牛客在岗位画像显示可能有覆盖时分别尝试；每个平台最多精读并采用
5 篇高相关面经。没有高相关结果时记录“无有效来源”，不得用低相关内容凑数。其他面经平台也
遵守单平台最多采用 5 篇的上限。

## 查询与相关性

查询从精确到宽泛：

1. `<公司> <部门/业务线/职能方向> <岗位> <面试性质/轮次> 面经`
2. `<公司> <岗位> <面试性质/轮次> 面经`
3. `<公司> <相近岗位> 面试`
4. `<岗位> <行业> <专业面试形式>`

相关性从高到低：

1. 同公司、同组织方向、同岗位、同面试性质；
2. 同公司、同岗位、同轮次；
3. 同公司、相近岗位、同面试性质；
4. 同行业、同岗位、同专业面试形式。

优先前三档。第四档只能作为旁证并说明差异。重复转载、营销软文、无岗位上下文题库和只有标题
没有正文的内容不计入有效面经。

面经来源按平台编号，例如 `XHS-01`、`NC-01`；其他平台使用可识别短码。只提取问题、追问、
考察点和提醒，不长篇复制原文。

## 公司、组织与专业研究

按以下优先级研究：

1. 公司官网、招聘页、部门/业务/职能资料、官方产品或服务；
2. 财报、投资者关系、监管披露、标准和官方政策；
3. 专业协会、论文、技术资料和权威数据；
4. 可靠行业媒体和研究机构；
5. 普通媒体或社区内容只作辅助。

研究范围由岗位画像决定，例如：

- 产品/运营/市场：用户、产品、商业模式、渠道和指标；
- 技术/算法：技术栈、系统场景、工程约束、论文或开源资料；
- 财务/法务/HR：公司阶段、组织职能、监管或专业规则；
- 销售/供应链：客户、产品方案、产业链、成本、履约与风险；
- 设计/研究：作品、方法、目标用户、专业成果与局限。

推断必须标注为推断。找不到部门或职能公开信息时明确说明，不用集团层面的泛化资料冒充。

官方与公司资料编号 `OFF-01`、`OFF-02`；财报、专业和可靠行业资料编号
`PRO-01`、`PRO-02`。

## 研究推理与交叉验证

问题涉及行业、竞品、市场、业务策略或关键数字时，读取 `research-reasoning.md`。至少完成：

1. 明确研究问题和它与目标岗位的关系；
2. 对齐来源的定义、统计对象、时间范围和适用场景；
3. 区分来源直接支持的事实、Agent 推断、候选人判断和未知；
4. 对关键冲突数字使用独立来源或不同计算角度交叉验证；
5. 无法消除冲突时保留区间或并列口径并说明原因。

历史课程、题库和往年案例只能提供检索词、机制或假设，不能证明目标公司的当前事实。

## 来源记录与失败

每条实际采用的来源至少记录标题、发布方、发布日期或未知、岗位相关性、提取内容、直达链接和
含时区的读取时间。

- 平台无高相关结果：记录检索范围，继续其他来源。
- 登录或验证阻塞：让用户处理；用户明确跳过后继续。
- 没有有效面经：可根据 JD、官方和专业资料生成十道题，全部标记为资料生成题。
- 一手资料不足：缩小结论并标记待确认，不用社区推测补成事实。
