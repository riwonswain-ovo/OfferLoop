# 面试准备质量检查

本检查只用于交付前内部验收，不把勾选表原样放入用户文档。

## 红线

出现任一项时停止交付并修正：

- 编造用户经历、职责、数字、结果、技术实现或时间线。
- 未经用户选择自行读取经历深挖或上一轮准备文档。
- 把 Agent 生成题伪装成面经原题。
- 把弱来源、过期面经、社区推测或推断写成公司官方事实。
- 冒充特定面试官或断言未经证实的公司面试流程。
- 在外部平台输入或上传简历、经历深挖、联系方式或其他私人材料。
- 伪造直达链接，或用搜索结果页代替实际采用的来源。
- 未经用户确认就保存飞书、创建记录或回填 Base。
- 正式文档残留提示词、占位符、调试信息、record ID 或 node token。

## 输入与材料

- [ ] 公司、岗位、完整 JD 和当前轮次已确认；轮次未知时已说明限制。
- [ ] 已按 JD 建立岗位画像，未把预设岗位族当作白名单或公司事实。
- [ ] 已把 JD 拆为三至六项核心能力，并识别任务、对象、交付物、指标、协作关系和约束。
- [ ] 已区分轮次和面试性质；性质未知时已标记推断或限制。
- [ ] 用户已明确选择经历深挖产物，或已上传简历。
- [ ] 飞书经历深挖只在用户选择具体候选后读取。
- [ ] 上一轮准备文档只在用户手动指定后读取。
- [ ] 所有个人化内容均可追溯到用户材料；缺失事实已标记待回忆。

## 检索与来源

- [ ] 已先根据 JD 生成检索任务，再开始外部搜索。
- [ ] 已先完成公司、业务领域和岗位背景研究，再搜索面经；未用通用题库或面经反推公司认知。
- [ ] 已形成独立“公司、业务与岗位认知”模块，明确公司做什么、业务如何运转、岗位做什么及
      需要的三至六项候选人能力。
- [ ] 已根据岗位画像选择适合的面经和专业来源。
- [ ] 小红书、牛客适用时已尝试，或记录无覆盖、用户跳过或访问受阻。
- [ ] 任一面经平台实际精读并采用不超过 5 篇。
- [ ] 只采用高相关面经；不足 5 篇时未用弱相关结果凑数。
- [ ] 已研究公司官网、相关组织/职能资料，以及可用的官方、专业或可靠行业资料。
- [ ] 已建立面试情报矩阵，覆盖公司/业务、组织场景、岗位任务、专业判断和高相关面经。
- [ ] 每项核心 JD 能力已连接到公司/业务场景、岗位任务、可能验证方式和来源或明确证据缺口。
- [ ] 关键数字和冲突资料已对齐定义、时间与统计口径，并完成必要的交叉验证。
- [ ] 历史课程、题库和往年案例未被当作目标公司的当前事实。
- [ ] 所有外部事实具有来源、发布日期或未知、相关性/用途和读取时间。
- [ ] 正文使用的每个来源都出现在末尾“信息来源”。

## 产物结构

- [ ] 正文严格按顺序包含 90 秒自我介绍、公司/业务/岗位认知、业务领域专业知识补齐、15 道题、
      候选人反问和信息来源。
- [ ] 正文不显示“产物信息”、生成状态、生成 Skill、`run_id`、locator 或其他内部运行元数据。
- [ ] 正文没有“个人经历战斗卡”或“本轮快速复习”二级章节。
- [ ] 专业知识补齐位于公司认知之后、十五道题之前，覆盖完成岗位工作和应对本轮面试所需的
      5–10 个核心概念、边界、指标或验收方法。
- [ ] 自我介绍约 90 秒，强关联公司、组织场景、JD、个人经历、轮次和面试性质。
- [ ] 自我介绍的学历背景只点明最高学历就读学校和专业，没有展开学校或课程介绍。
- [ ] 自我介绍在学校和专业之后使用一句简短总领句，说明将从岗位契合点和自我评价展开。
- [ ] 差异化契合点采用“结论 → 相关经历递进 → 目标岗位迁移判断”，不是公司名称或任务罗列。
- [ ] 第一个通用能力点从多段经历中抽象出稳定、可复用的工作方法。
- [ ] 第二个通用能力点补齐技术业务连接、跨团队协作或推动落地价值，且未为形式平均篇幅。
- [ ] 自我评价恰好包含 3 个最适合目标岗位的评价点；最有辨识度的一点有成长轨迹或内在动机，
      其余评价有简洁事实和具体工作表现。
- [ ] 三个评价点都来自用户画像中已确认的自我认识，并明确连接当前 JD；没有从岗位标签反推
      用户人格。
- [ ] 自我介绍和个人参考回答已按 `voice-contract.md` 完成个人语言复读检查；样本不足时没有
      声称已经模仿用户。
- [ ] 自我介绍使用连续口语和自然过渡，差异化内容详写、通用内容略写，没有写成六个等长标签。
- [ ] 自我介绍没有堆项目数字和次要实现细节，也没有删掉经历到岗位的迁移逻辑。
- [ ] 自我介绍结尾感谢面试机会，并明确表达希望获得入职机会的意愿。
- [ ] 已先生成 25–40 道候选问题，并记录每题的 E1–E6 信号、预测依据和可用个人证据。
- [ ] 恰好生成 15 道公司、组织场景与岗位强相关的问题。
- [ ] 十五道题固定分为 5 道必练、5 道重点和 5 道了解。
- [ ] 每道正式题至少有两类有效信号，且至少一类来自面经、JD 或公司/业务事实。
- [ ] Q1–Q3 通常有三类以上信号，或属于高度匹配的面经原题。
- [ ] 个人经历只作为自我介绍或相关问题的证据，没有另建经历章节；通用且不依赖目标公司的
      题目没有挤占正式十五题。
- [ ] 十五道题未集中在同一主题或同一段经历，能覆盖本轮主要验证面。
- [ ] 十五道题整体覆盖业务理解、能力迁移、目标业务场景解决方案和投递/转行意图四个验证面。
- [ ] 产品经理及以产品判断为核心的复合岗位，十五道题覆盖行为动机、工作职能、开放业务、
      产品实战和费米估算五类，每类至少一题，顺序和剩余题量由公司赛道、岗位、JD、轮次和面经决定。
- [ ] 十五道题优先采用高相关面经，缺口才按五类母题和可靠资料动态生成。
- [ ] 每题用一行标明来源、优先级、JD 能力和可用个人证据。
- [ ] 十五道题都有较完整、可直接练习的个人参考答案。
- [ ] 必练、重点和了解题都含结论、记忆链、较完整回答和可能追问；优先级只改变排序和篇幅。
- [ ] 经历事实只在需要的位置出现，题目下仅补充与该题直接相关的事实边界和特殊风险。
- [ ] 准备了 4–6 个与本轮和研究事实相关的候选人反问。
- [ ] “信息来源”是最后一个二级章节。

## 回答质量

- [ ] 一句话结论真正回答问题。
- [ ] 第二层包含 2–4 个同类型、同层级支撑点。
- [ ] 十五道题的每个支撑点都紧跟对应事实、机制、业务依据或个人证据，没有将观点与证据分成
      两组集中罗列。
- [ ] 十五道题全部提供可直接练习的金字塔式答案，而非只有关键词、STAR 素材或答题思路。
- [ ] 公司、组织场景或专业判断有可靠事实支持，不是资料堆砌。
- [ ] 公司与业务回答区分事实、条件性推断、候选人判断和未知，没有把推断包装成事实。
- [ ] 回答骨架适合题型和岗位，没有把所有岗位强行套成产品题。
- [ ] 个人经历用于证明能力，没有替代对岗位场景或专业问题的回答。
- [ ] 归纳回答的组结论能概括支撑点；演绎回答的原则、事实和推论连续。
- [ ] 用户文档没有重复展示“逻辑类型”、归纳/演绎标签或其他内部分析字段。
- [ ] 数字、强动词、角色边界和技术实现均有证据或明确不确定性。

## 岗位、轮次与面试性质差异

- [ ] 一面突出事实、执行、基础和数字口径。
- [ ] 二面突出判断、取舍、指标、协作和复盘。
- [ ] 三面/负责人面突出组织/专业/业务影响、系统思考、资源约束和认知边界。
- [ ] HR 面突出动机、经历主线、规划、稳定性和现实条件。
- [ ] 只执行当前轮次适用的一组要求；与默认模型不同的判断有可靠依据。
- [ ] 岗位画像决定考察内容，面试性质决定考察方式，轮次决定追问深度。
- [ ] 指定上一轮文档时保持事实一致，同时减少重复并增加本轮深度。
- [ ] 产品或商业化岗位指南只在 JD 明确命中时读取，未把岗位名称关键词当作充分条件。
- [ ] 候选人反问按已确认面试官性质或宽泛职能适配，未按轮次臆测面试官层级。

## 交付与状态

- `completed`：无红线，硬输入齐全，核心结构与来源要求满足。
- `incomplete`：无红线，但存在个人材料、登录态、面经、官方资料或轮次缺口；正文已说明影响。
- 首次成稿必须先在聊天中交付。
- 只有用户明确确认当前版本并要求保存后，才允许写入 `04｜面试准备`。
