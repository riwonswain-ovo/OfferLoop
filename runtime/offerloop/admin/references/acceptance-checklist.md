# OfferLoop 字段与流程验收清单

本清单用于用户确认后的只读检查和合成端到端演练。真实飞书资源缺字段时只报告差异；不要
自动创建或重排字段。

## 招聘信息 → 求职进展

招聘信息事实源是 `求职企业清单`。主表和企业性质子表的业务字段顺序应为：

1. 信息更新时间
2. 投递进度
3. 公司
4. 招聘批次
5. 招聘项目
6. 招聘岗位
7. 公告链接
8. 投递链接
9. 投递截止时间
10. 城市
11. 行业标签
12. 企业性质
13. 子表 record_id（技术字段，放最后）

投递进度只能使用：`待确认`、`感兴趣`、`已投递`、`已拒绝`。求职进展第一次收到“已投递”
时才创建记录；公司可自动带入，但投递岗位、岗位 JD 保持空白，不能从招聘岗位字段复制长文本。

重复同步不得覆盖用户手填的投递岗位、岗位 JD、首次投递日期或更高面试阶段。
`企业清单 record_id` 是可重复的父级关联键；`投递记录 ID` 是每次岗位投递的唯一键。
同一企业下两个不同岗位必须保留为两条进展，分别拥有不同的 `投递记录 ID`，同步时不得报重、
合并或删除。

求职进展按 `progress-schema-v6.md` 验收：`进展状态` 是当前状态唯一真源，默认新记录为
`待反馈`，`最近完成节点=投递完成`；必须保留 `公告链接`，简历选择不写入业务 Base。

把企业状态从 `已投递` 改为其他值时，未维护的自动默认行应被删除；已有岗位/JD、已推进状态或
人工 `投递记录 ID` 的记录应保留并提示复核。

## 笔面试中心 → 求职进展

`笔面试中心` 只有一张业务表 `笔面试安排`；内部 `OfferLoop运行状态` 不承载事件数据。业务表包含 `全部安排`、`测评`、`笔试`、`群面`、`一面`、
`二面`、`三面`、`HR 面`、`其他面试` 视图；除 `全部安排` 外都只按 `环节` 筛选。同公司不同岗位
及同岗位的多轮面试都应保存为独立记录。

单表字段顺序、类型、枚举与受管视图只读取
`../../recruiting-reminder/references/event-schema.md`，本清单不维护第二份字段列表。启用每日卡片时
同时按该契约验收内部 `OfferLoop运行状态` 表；启用每日卡片时还要验收唯一分页幂等键。

测评/笔试记录的“面试准备文档”和“面试复盘文档”必须为空。普通面试只有在来源去重、唯一关联
完成后才推断轮次；第四次及以后为“面试”。旧“面试（轮次待确认）”只作历史兼容。

待办状态只能单调推进：

```text
待反馈 → 待测评 → 待笔试 → 待群面/待一面 → 待二面 → 待三面 → 待面试 → 待 HR 面 → 待 OC
```

`Offer`、`未通过`、`主动放弃`、`岗位关闭` 不得被自动覆盖。任何迟到、重复或较早轮次邮件都
不能降低状态；已错过和已取消不修改求职进展。

## 端到端最小验收

1. 合成一条招聘信息，并确认企业清单只写入字段契约中的值。
2. 将其投递进度改为“已投递”，确认求职进展创建/更新而不填入投递岗位和岗位 JD，并生成
   唯一 `投递记录 ID`。
3. 合成一封明确轮次的面试通知，确认生成一个独立笔面试事件、关联正确申请并单调推进阶段。
4. 在同一企业父级下保留两条不同岗位申请，再重放“已投递”事件，确认两条都保留、来源链接
   都刷新、岗位/JD/阶段不被覆盖。
5. 将一条未维护的自动默认行对应企业改为“已拒绝”，确认默认行被删除；再对已推进记录执行同样操作，确认记录保留并返回 `review_required`。
6. 合成同公司不同岗位的一面通知，确认不会合并到前一条申请。
7. 合成同公司同时存在测评和笔试，确认两条事件独立存在，标量状态显示待笔试。
8. 合成普通第四次面试，确认环节为“面试”，群面、HR 面、提醒、改期和取消不计数。
9. 合成高置信固定事件，确认无需人工确认即可写 Base 和创建日历；合成歧义关联，确认未确认不写。
10. 合成卡片分组与按钮，确认不统计今日已完成、异步才可调整、固定/过截止可由 owner 标错过。
11. 对唯一关联的面试事件回填一份 `completed` 复盘，确认同一原子 patch 写入“面试复盘文档”和
    `完成状态=已完成`，并由即时 workflow 将求职进展推进到对应“X面完成”；没有下一轮安排时为
    `待反馈`。再用 `incomplete` 复盘确认只回填文档、不推进进展。
12. 验收默认使用 dry-run 或本地合成对象，不碰真实数据；评测任务另行执行。
